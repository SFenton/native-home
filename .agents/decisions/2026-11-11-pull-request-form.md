Decision: A pull request has one plain title, a description of `## Summary` and `## Tests` only, and one step comment per role in three bullet lists. The description shows no step list, no status line, no review block, no device table and no generated-by footer. A fix that lives in another repository or pull request is named with its repository or link and its state. Options judged: A, keep the step list and footer and only warn (rejected: the owner asked for them gone); B, check each section or sentence on its own (rejected: it refused honest text, such as a comment that names the repository in a later bullet); C, refuse a description or comment that points elsewhere unless the whole text holds a repository or link and a state word (chosen). `tools/ship.sh` runs `title-check` and `body-check --strict` before it opens a pull request, and `tools/pr_note.py` applies the same check to comments. The owner's words: "That's not acceptable or good documentation. What's the fix? What repo?"; "'Steps' is not necessary - I can just go read the comments."; "Remove 'Generated with Claude Code' from description." A description that links another pull request, in this repository or another, states its state and is linked back; when the state changes the session that saw it updates every description that links it and posts one step comment on each linked pull request saying what changed and what it means for the pull request and for the person who uses the app. The owner's words: "When this sort of cross-repo work happens, we should update descriptions where we've linked other PRs (perhaps even within the same repo) when their status changes, and/or add comments indicating status changes on those PRs and the implications for the main PR/the user experience."
