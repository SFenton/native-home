Controller-bound controls

About 25 Binding(get:set:) in HassUI forward to a controller. The swiftui-pro review flags them; the first pass skipped them because Home Assistant is the source of truth. This proposal asks how to remove the closures without changing what a control does.

1. What is wrong or wanted

Nothing a person sees. I traced every site: the get already reads controller state including its optimistic overlay (OptimisticActions, revertAfter 2 s, generation rollback). So a control flips at the tap, stays on a confirm, and snaps back on a rejection or a 2 s silence. That behaviour is correct and every option below keeps it byte-for-byte. The ask is code shape only: the pixel output is unchanged, so under propose-first this is a refactor and needs the owner's pick for the pattern, not for pixels.

The sites are not one problem. They fall in four groups, and the right answer differs per group:

2. Options

O1 · Leave as is, codify it

Keep the closures. Add one paragraph to optimistic-actions: a forwarding Binding is allowed only when get reads controller state; local @State + onChange mirrors are a review finding. Triage can then ignore the swiftui-pro rule here.

0 files · 0 risk · finding stays open

O2 · Shared controls (recommended, for A, B, D)

ControllerToggle(title, isOn: Bool, send: (Bool)->Void), ActionToggle(title, isOn: Bool, action: ()->Void), ControllerStepper(value:, range:, step:, send:) (built on Stepper(onIncrement:onDecrement:)), ControllerPicker. Callers pass a plain Bool/Int read and a function; the one internal Binding lives in HassDesign, documented, tested, with the 44 pt row, a11y identifier and a pending hint in one place. Group C: the editors’ closures move to the draft types (draft.setKind, draft.dateValue, name normalised by .onChange since local state is the truth) and ScanItem gets writable model properties used through @Bindable.

~14 view files + 1 new Design file + 2 draft helpers · same pixels

O3 · Writable controller properties

Controllers expose var rainDelay: Bool { get set } whose set sends the command; views use @Bindable and $controller.rainDelay. Removes closures everywhere with no new view type.

~12 controllers touched · setters with side effects · cannot express group B or D · hides that a write is a command

O4 · Local @State + onChange (rejected)

What the review literally suggests. Control flips from its own state, then onChange sends. Shown below as the failure case.

4. VoiceOver

  • Value is announced from the same read as today: “Rain Delay · 24 Hours, switch button, on”. O2 owns the label/identifier/hint so the 14 sites cannot drift (the autoClean accessibilityHint, the .labelsHidden() rows with an explicit label).
  • Rollback: the switch’s value changes back; SwiftUI posts the value change, so VoiceOver speaks “off” again. We add no extra announcement (consistent with “no error UI” in the pattern); the owner may want one, see questions.
  • Stepper keeps the adjustable trait via Stepper(onIncrement:onDecrement:); the displayed “Turn Off In 30 min” is the accessibility value. Check: range clamping moves into the controller (setTimerMinutes already clamps).
  • O4 would announce the flip, then silently never announce the failure.
  • Group D: the Prepared Food switch stays off while the confirmation prompt is up, so VoiceOver reads the true state behind the alert.

6. Recommendation

O2, applied per group. A and B and D use the shared controls; C is fixed at the source (draft/model helpers, because local state really is the truth there); the BedSideSheet scope sheet becomes .sheet(item:) over the controller’s scopeRequest or stays as the one sanctioned isPresented forwarder. Then add the O1 paragraph to the pattern doc so the swiftui-pro rule is documented as “satisfied by ControllerToggle”.

It asks of the app: new HassDesign/Controls/ControllerControls.swift; edits in the ~14 view files above; WakeLight.Alarm draft helpers; update patterns/optimistic-actions.md and the atlas notes for Sprinklers, Humidifier, Vacuums, Climate, Bedroom (no state changes, only source maps). No new motion.

Test plan. Unit (HassDesign hosted UI tests): ControllerToggle shows isOn input regardless of taps until the input changes; tap calls send exactly once with the new value; ActionToggle calls action, not send(!). Core (existing OptimisticActionsTests with RecordingCaller.failNext + ManualScheduler): rollback on failure, 2 s revert, live-change clear; add a controller-level test per migrated controller that the value read after a failed call equals the old one. UX + accessibility on iPhone, Duo, iPad: toggle round-trip, rejected command ends with switch off (stub caller), AX5 row layout unchanged, 44 pt target, VoiceOver label/value/trait (switch; adjustable for the stepper); Prepared Food stays off behind the prompt. Snapshot of the screens before and after must be identical.
