One setup flow: Notifications, Time Sensitive, Location

Goal (owner, 2026-10-27): Time Sensitive notifications become a step of the setup flow that already asks for location. A first-time user sees every step. A user who already accepted location, and has not seen the Time Sensitive step, gets that one step on the next launch. Nothing is built until you pick. The screens below are stand-ins drawn in this page, not device captures.

1. What exists today

  • Location is a one-time page sheet after sign-in (LocationCoordinator.offerPermissionIfNeeded, flag location.offered). Phones only: LocationCoordinator is nil on iPad. Always dark, pre-alert rules (one Continue, no Close, no swipe-down).
  • Notifications are not a sheet step. PushCoordinator.didConnect only reads the answer; the ask lives on the Home banner (Turn On Notifications / Not Now) and the Settings row. The location doc says location waits for the notification alert, but the code does not wait for anything.
  • Time Sensitive is declared (entitlement, profile and build verified on device 2026-10-27) but nothing in the app mentions it.

One fact that shapes the design

iOS has no system alert for Time Sensitive. When notifications are allowed, the app's Time Sensitive switch is on by default; only the person can turn it off, in Settings → Notifications → S+H. The app can read it (UNNotificationSettings.timeSensitiveSetting: enabled, disabled, notSupported) but cannot ask for it. So this step is an explainer plus a status, never a Continue-then-alert: when the switch is on, the action is “Got It”; when it is off, the action is “Open Settings”.

2. Who sees what

The flow keeps a set of steps already shown (setup.stepsSeen). Existing installs migrate: location.offered true counts as “location seen”, so nobody sees the location step twice. Each launch, after sign-in and connection, the flow shows the steps whose condition holds and that are not yet seen.

3. The screens

All three share one always-dark page sheet, like Location today, so the secondary copy stays above 4.5:1. The two asking steps are pre-alert screens (one Continue, no Close). The Time Sensitive step has no system alert behind it, so it may offer Not Now.

4. No progress indicator (owner, 2026-10-27)

The sheet draws no dots, counter or carousel. HIG Privacy, pre-alert screens: “Include only one button, clearly opening the system alert” and “Don't include additional actions”, so nothing may let a person move past an alert without answering it. A swipeable carousel or tappable dots would. The steps are a gated sequence (Time Sensitive needs notifications; the Always step needs While Using), not peer pages, and the HIG puts page controls “near the bottom” for an ordered list of peers. Each step ends in a system alert, which is its own sign of progress. If a position cue is wanted later, the fallback is a read-only, bottom-centred indicator (Page controls, Minimal style) added as a variant of the page-indicator pattern.

7. Settings → Notifications: the way back

The existing Settings → Notifications section gets one Time Sensitive row once notifications are allowed. The row shows the real status and is itself the deep link to this app's notification page in iOS Settings (no separate button, no chevron: a row that leaves the app draws no accessory). It is also where anyone who tapped Not Now in the setup step finds the way back.

8. Recommendation

A1 + B1. One Setup sheet whose steps swap in place; Time Sensitive shows once to everyone who has not seen it and reports its real status. Existing installs migrate location.offered into the seen set, so you get exactly one sheet on the next launch.
  • Files: new SetupFlow (steps, seen set, migration, conditions) in HassUI/App/Setup; LocationCoordinator.offerPermissionIfNeeded becomes a step condition; LocationPermissionSheet becomes the Setup sheet host; PushPlatform gains timeSensitiveSetting; a Time Sensitive view and copy beside the Location ones; the Settings → Notifications section gains the Time Sensitive row, which is itself the deep link (section 7, settings-notifications-time-sensitive); the URL is UIApplication.openNotificationSettingsURLString (iOS 16 and later, opens S+H's notification page), falling back to openSettingsURLString.
  • Tests: unit tests for the step conditions and the migration (every row of section 2); UX and accessibility tests on iPhone and Duo, AX5 included; no new motion (steps swap with no animation, like the location stages).
  • Docs: location.md (offer rules), push.md, the Location sheet mockup and a new flow mockup become the Setup flow, and the stale “waits for the notification alert” sentence is fixed.

9. Open questions

  1. iPad. Location is phone-only, so the flow is today. Time Sensitive and Notifications apply to an iPad too. Recommend the flow runs on iPad with only the notification steps (no Location). Say if you want it phone-only instead.
  2. Notifications as a step. Move the ask from the Home banner into the flow for first-time users (shown above), or keep the banner and let Time Sensitive wait for it. Recommend moving it into the flow; the banner stays as the fallback for “Not Now”.
  3. Copy. “Let Urgent Alerts Through” is a draft. The three points name door, smoke and camera alerts; confirm those are the events the integration actually sends as Time Sensitive.

Cited: HIG Privacy (pre-alert screens), Notifications (interruption levels), Sheets. The Critical Alerts request is separate and not part of this flow yet; when Apple approves it, it becomes a fourth state of the same step.
