# PR lifecycle

> **What:** how a session ends: from a pushed branch to a merged, blocked or failed one-line report, with the review and the gate that stand between. **Read when:** you are about to open a PR, or you were woken by a CI or review event.

Owner decision (2026-10-28, updated 2026-11-10): agents push the branch and open the PR first, the independent reviewer reads the exact head while CI runs, and the PR is armed only once that head has a pass. On SFenton/native-home GitHub is the merge gate (ruleset `main-checks`: a pull request, `pr-checks` from GitHub Actions and `ai-review` from the S+H Reviewer app, both required on the head; squash only, no bypass) and merges by itself; [`tools/pr_land.sh`](../../tools/pr_land.sh) runs only what GitHub cannot (kill switch, app-UI gate, owner-kept set, denylist, author and fork, the reviewer's pass) and arms auto-merge, and a hook stops anything else from merging.

## The standard ending

1. **Ship.** `tools/ship.sh "Subject" --pr --draft [--note TEXT]` commits (trailers `Release-Note:` and `Co-Authored-By:`), pushes the branch (no reviewer pass needed; the pre-push hook runs the house denylist) and opens a **draft** PR (always a draft) with [`.github/pull_request_template.md`](../../.github/pull_request_template.md) as the PR template. `ship.sh` itself does not apply it: right after it opens the PR the orchestrator runs `python3 tools/pr_note.py init --task T` (see PR timeline). `pr_land.sh` marks it ready once the review passes.
2. **Bind and watch.** Claude app sessions bind the PR and turn on auto-fix: `ccd_pr` `get_status` (read the PR and its checks instead of polling `gh pr checks`), `bind_pr` with the URL if the PR bar did not pick it up, `set_monitor` with `auto_fix: true`. CI failures, merge conflicts and review comments then wake the session. Other runners (triage) read `gh pr view` once. Without the app monitor, whenever a PR waits on CI or its auto-merge, start `tools/bg_run.py ci-N --timeout 7200 -- python3 tools/ci_wait.py N` in the background and end the turn (it prints `RESULT:`; exit 0 merged, or green and CLEAN unarmed; 1 failed or closed; 2 no run or `gh` error; 3 blocked, e.g. `ai-review` missing; 4 cancelled).
3. **Fix.** On a failing check or a `changes` verdict, fix with small commits and push to the same branch (CI restarts; the new head gets its own review). Never poll ([token-economy](token-economy.md)). After a `changes` verdict, `python3 tools/jev_hints.py findings build/review/<branch>.json` groups the blocker and major findings into one checklist per kind (nothing when the decision model is unavailable; the findings themselves stay authoritative).
4. **Review.** In parallel with CI, spawn the reviewer on the pushed head: `Agent(subagent_type: "reviewer", prompt: "opus-ok: final review. PR N, branch B, round R ...")`. It is an Opus subagent defined in [`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md), starts from the Jev pre-read (`tools/jev_hints.py review --pr N`, [decision-models](decision-models.md); a guess to verify), runs the ten-item checklist below and records its verdict with `tools/review/record.py verdict.json --pr N`. `changes` sends you back to step 3, then run it again on the new head for round 2. Findings marked `blocker` always stop the merge. With a detached HEAD pass `--pr N` to `record.py`.
5. **Arm.** On a `pass` the reviewer has already posted the `ai-review` check (`python3 tools/review/record.py --post-check HEAD_SHA --repo SFenton/native-home`, right after recording); run `tools/pr_land.sh N` (add `--dry-run` to see the decision). `ship.sh` already tried at open and printed `not armed` because the head had no pass yet; that is expected. An agent runs the project's absolute `tools/pr_land.sh N` from the project checkout; `merge_guard` refuses it unless that checkout's `pr_land.sh`, `pr_land.py`, every tools module it loads (`pr_blockers.py`, `review_verdict.py`, `ruleset_gate.py`, `request_repo.py`, `agent_login.py`, `house_scan.py`; `PINNED_WITH`, enforced by a test) and `tools/triage/config.json` match `origin/<base>`, so fetch or rebase when your base is stale.
6. **Report** one line: `merged #N`, `armed #N`, `blocked #N: reason` or `failed #N: reason`, exactly what `pr_land.sh` printed. Do not summarise the diff again.
7. **Owner-landed PR.** When the PR touches a path in `.github/CODEOWNERS`, the live ruleset needs the owner's code-owner approval, so `pr_land.sh N` also prints the owner-only recipe below (only for such PRs). The agent does not run it: it reports the PR and the recipe. `tools/ci_wait.py` and `tools/pr_land.py` share `blockers(pr)` (`mergeable`, `isDraft`, `reviewDecision` and the CODEOWNERS match), so `ci_wait` exits 3 on the first poll for a `CONFLICTING` PR (GitHub runs no `pull_request` checks on it; merge `main` and push) and names a draft or a missing code-owner review as the reason a PR stays BLOCKED. The owner approves this pull request on GitHub (their review of this exact head) and merges it there; the same steps as commands, with the head SHA `pr_land` printed:

   ```
   gh pr ready N -R SFenton/native-home
   gh pr review N -R SFenton/native-home --approve
   gh pr merge N -R SFenton/native-home --squash --match-head-commit <head sha>
   ```

## PR timeline

A change is followed from the PR alone: the description is the living view (what changed for you, one hero pair, the device table, the status line, the reviewer block) and comments are point-in-time events. `python3 tools/pr_note.py` (spec: `build/research/visual-prs.md` J and K.6) is the one writer. `post pick|evidence|verdict|owner|handoff|shipped --task T --round N --body-file F` finds its earlier comment by marker (`<!-- sh:<kind>:<task>:<round> -->`; evidence adds the class, `iphone`, `duo` or `ipad`, one comment per class per round and none for a class with nothing to show) and edits it only when the body changed. `status --line` and `devices --file` replace only the text between `sh-status` and `sh-devices` markers; the `review:` block belongs to `tools/review/record.py`. Before the PR exists notes queue under `build/pr-notes/<task>/` (keyed by the `--task` id the roles pass) with their original time. Right after `ship.sh` opens the PR the orchestrator runs `python3 tools/pr_note.py init --task T`: it makes the body follow the template (prepends the plain sections if missing, appends missing marker blocks, keeps existing text and the review block) and posts the queue; every later `post` flushes the task's queue first and drops stale queued entries. A `gh` error or a 20 second timeout prints one warning and exits 0. Who posts: the Verifier evidence, the Designer pick and verdict, the Orchestrator handoff (work waiting over 30 minutes or changing hands; `resolve` when it ends), owner, shipped and the status line. Budget: L0 none, L1 about 2, L2 design about 6, more only when a change shows on several device classes.

## Agent identities

Each role can post its PR comments as its own GitHub App (`s-h-<role>[bot]`: orchestrator, researcher, designer, coder, verifier, reviewer, steward, menial, triage), so the owner is notified and the timeline shows who said what (owner, 2026-11-04; design: `build/research/github-app-identities.md`).

- PRs are authored by the machine user `sfenton-agent` (`agent_login` in `tools/triage/config.json`; `pr-checks` accepts it through the repository variable `AGENT_LOGINS`); `.github/CODEOWNERS` lists the agent files for `@SFenton`, and the live ruleset enforces it (`require_code_owner_review: true`): a PR touching those files waits for the owner's approval.
- `python3 tools/pr_note.py post KIND ... --as <role>` posts and edits through the REST API with the role's installation token (`tools/gh_app_token.py`, in memory only, key in `~/.config/fenton-hass/github-apps/<role>.pem`, ids in the non-secret `apps.json`). With no key it says so on stderr and posts as the owner's `gh` login, exactly as without `--as`.
- Each App holds `issues: write` and `pull_requests: read` only. Media upload and PR-body edits (`status`, `devices`, `init`) stay on the owner's login.
- `handoff` and `owner` comments from an app start with `@SFenton`: GitHub Mobile pushes only on a mention.
- Comments are found by marker whoever wrote them. An App edits its own; one by another author (the owner's login before the switch) is replaced: the new comment is posted, then the old one deleted with the owner's login.
- One command sets everything up (owner, 2026-11-04): the owner runs `python3 tools/gh_apps_setup.py serve` (never an agent). It binds `127.0.0.1:8765` only (`--port`), opens a page listing the nine roles (not created, created, installed) and each button POSTs that role's manifest to GitHub with a per-run `state` token. GitHub returns to `/created` with a one-hour `code`; the helper checks `state` and the role, exchanges the code at `POST /app-manifests/{code}/conversions`, writes the key to `<role>.pem` (atomic, mode 600, folder 700), merges `app_id`, `slug` and `client_id` into `apps.json` and sends the browser to the app's install page. GitHub returns to `/installed` with the `installation_id`, recorded too. `client_secret` and `webhook_secret` are never written, and no key is printed or shown. It stops after all nine are installed, or on Ctrl-C, printing one line per role (ids only). Steward and triage may also be installed on the request repo (local setting, [triage setup](triage-agent.md#the-request-repository-local-setting)) (optional). `pr_note` recognises an app by its recorded slug (`s-h-<role>` when none), and `gh_app_token` looks up a missing installation id with the app JWT (`GET /app/installations`, account SFenton). `python3 tools/gh_app_token.py check <role>` prints whether the key is present and the app reachable, never a token. Agents never read the key files directly.

## The gate: `tools/pr_land.sh N`

GitHub enforces `pr-checks` and `ai-review` on the exact head (both required by the ruleset). `pr_land` runs only what GitHub cannot, then arms `gh pr merge N -R SFenton/native-home --auto --squash --match-head-commit <head>`. All of these must hold:

- The PR is open, not conflicting, labelled neither `Needs Decision`, authored by `SFenton` from this repository (not a fork) and based on `main`.
- The reviewer recorded an independent `pass` for **exactly the PR's head SHA** in the trusted store (`tools/review_verdict.has_pass`, the record `tools/review/record.py --lane BRANCH` writes; a pass for an older head blocks with `no independent pass for <sha12>`). The review file under `build/review/` is no longer read.
- The live ruleset passes `tools/ruleset_gate.py` (a pull request, `pr-checks` from GitHub Actions, no bypass).
- The app-UI gate passes ([agent-roster](agent-roster.md#autonomy-levels), "What code enforces today"). Two owner decisions of 2026-11-04 shape it: an `Owner's request: "<quote>"` line in an interactive PR counts as the owner's request when the quote is inside a prompt the owner typed in the last 14 days (logged by the `UserPromptSubmit` hook `tools/hooks/owner_prompt_log.py` to `~/hass-agents/owner-prompts/`; a tripwire, not a boundary: agents run as the owner's user, and `tools/hooks/owner_prompt_guard.py` plus the runner's deny list only make forging it a deliberate act); and a mockup file whose drawn form is unchanged after stripping comments outside `<script>`, citation attributes, `<a>` hrefs and metadata (`lane_land.mockup_drawn_form`) is not app UI, so a citation-only rewrite of the atlas skips the gate.
- No kill switch is set: `$HASS_TRIAGE_PAUSED_FILE` (the triage runner exports its `PAUSED` file) or `~/.config/fenton-hass/NO_LAND` exists. Either one makes it print `blocked: landing paused` and exit 1.
- The house denylist has no new hit on the head (`denylist_gate`).

Checks are GitHub's: `pr_land` neither reads the check rollup nor waits for CI, and `require_checks` is gone from `tools/triage/config.json`. A PR that queues on the runner is simply armed and merges when the checks pass (the aggregate runs on whichever Mac runner is idle, but `scope`, `repo-checks` and `swift-test` run on `hass-mac`, so a PR queues while the MacBook is asleep, off or busy; owner, 2026-11-07). `--review` and `--keep-worktree` are accepted and ignored.

Then it marks a draft ready (only after the gate passed), arms auto-merge pinned to the head and reads the PR once: `merged #N` when GitHub merged at once (GitHub refuses `--auto` with `clean status` when every check already passed, so it retries once without `--auto`, still pinned), `armed #N at <sha8>` otherwise, else `failed #N: ...`. GitHub deletes the branch on merge (`delete_branch_on_merge`) and `ci_hygiene.py prune-worktrees` reaps the lane worktree; `pr_land` does neither. Exit 0 armed or merged, 1 blocked, 2 failed. The logic is in `tools/pr_land.py` and tested in `tools/tests/test_pr_land.py`.

**Merge path for native-home (owner, 2026-11-10): push, then review.** The owner's words: "We should be allowed to push to the intended branch while review is going. No need for scratch branches. That way if review fails, we push to the intended branch and CI restarts; if review passes, we're already in CI on the intended branch anyways." Nothing reaches `main` without an independent `pass` for that exact head, but a branch may be pushed before it: GitHub needs a pull request, `pr-checks` and `ai-review` (the live ruleset `main-checks`, approvals 0; [ci](ci.md#the-merge-gate) has the details, the residual risk and the JSON). The order: the Coder commits, `ship.sh` pushes and opens the draft PR, CI runs while the Reviewer passes the exact head (`tools/review/record.py --lane BRANCH` writes the trusted record that `tools/review_verdict.py` reads), a `changes` verdict means fix and push again, a `pass` means `pr_land.sh N`. Git's own pre-push hook (`.githooks/pre-push` runs `tools/prepush_denylist.py`) refuses a push whose new commits match the house denylist; it no longer asks for a pass. `tools/hooks/push_guard.py` only stops going around it (`--no-verify`, `core.hooksPath`, `send-pack`, `GIT_DIR`, `gh api` ref writes, `gh repo sync`), and `tools/ship.sh` checks the hook is installed, pushes, opens the draft PR, and tries to arm through `tools/pr_land.py` (the gate above: kill switch, app-UI gate and owner-kept set, denylist, author and fork, the pass for the exact head, the live ruleset), which pins `--match-head-commit` to the reviewed head. A UI PR may be parked by the app-UI gate at that point (no design record yet): `ship.sh` prints `not armed` and the orchestrator arms it later with `tools/pr_land.sh N`. `ship.sh` runs the branch's own `tools/pr_land.py`, while `merge_guard` pins `tools/pr_land.sh` to the base copy for a direct agent run. That is acceptable because the gates that matter run from the trusted base inside the app-UI gate (`ui_gate` clones `origin/<base>` and runs its `lane_land.py gate`, so a PR cannot loosen the design record, Jev or owner-kept checks), the ruleset still binds the head, and an edit to `pr_land.py` or `ship.sh` is itself reviewed before it merges. `merge_guard` refuses the raw `--auto` form (only `--disable-auto` on your own PR, by `SFenton` or the configured `agent_login`, remains), `--admin`, and every `gh api` write to the rulesets, branch protection, repository settings or App installations, so `pr_land` is the only arm. A CI failure or a `changes` verdict means fix and push again. After the push `ship.sh` posts the `ai-review` check run only when the pushed sha already has a pass (otherwise it does nothing), and the reviewer posts it right after its pass (the ruleset requires it, owner, 2026-11-09). SFenton is the only collaborator; the reviewer app posts comments and that check, never an approval. Tests: `test_prepush_denylist.py`, `test_push_guard.py`, `test_merge_guard_automerge.py`, `test_ruleset_gate.py`, `test_lane_ship.py`.

The `merge_guard` PreToolUse hook (`tools/hooks/merge_guard.py`, registered in `.claude/settings.json`) blocks a bare `gh pr merge`, `gh api …/pulls/N/merge` (and `…/merges`) and a `git push` to `main` or `primary` unless the command goes through `tools/pr_land.sh`. The owner can still merge by hand. `.claude/settings.json` allows `tools/pr_land.sh` and `tools/ship.sh` in the relative, `./` and this repo's absolute-path forms so none prompts; `tools/clean.sh` is allowed in the relative and `./` forms. There is no `rm` allow: remove stale build output with `tools/clean.sh PATH...`, never bare `rm -rf`. It deletes only strictly inside `build/`, `apple/.build` and `apple/.build-*`, the same under `.claude/worktrees/<name>/`, and `/tmp/claude-<uid>` (real directory, owned by you); it ignores any root that is or passes through a symlink, unlinks a symlink argument instead of following it, and refuses everything else.

The Python tool tests step of `pr-checks` ignores failures already present on the PR's base commit and fails only on new ones (`tools/ci_new_failures.py`; owner, 2026-11-04). A push or manual run still runs `tools/run_tool_tests.sh` plainly.

## Registry checks (for `pr-checks`)

Three commands run in the `repo-checks` job of [`pr-checks.yml`](../../.github/workflows/pr-checks.yml) on every PR (you can run them yourself first; they are cheap and stdlib-only): `python3 tools/pattern_guard.py` (registry, ownership of every shared file, regex guards; exit 1 on any error), `python3 tools/components_index.py --check` (exit 1 when `contracts/components.json` is stale; fix with `python3 tools/components_index.py` and commit) and `python3 tools/jev_ask.py sync --check` (exit 1 when the `context.patterns` criteria no longer match `contracts/patterns.json`; fix with `sync`, bump the question's `version`). `python3 tools/pattern_guard.py changed --base origin/main --strict` is the advisory form: it exits 1 when a pattern's files changed without its doc or `contracts/patterns.json`.

## Preflight review

`tools/ship.sh` runs `python3 tools/preflight_review.py --base BASE` after it commits and before it pushes, on the diff `origin/BASE...HEAD` (skipped when `origin/BASE` is unknown). It is **advisory**: every check only prints a `warn [check] file:line` line, nothing fails the ship, and a crash or git error in the tool prints one line and the ship continues (like `base_drift`). It exists because the same three findings kept costing a second review round (post-mortem `build/retro/house-config-runtime.md`, action 3). Blocking can be turned on once the false-positive rate on real PRs is zero (replayed on #368 and #367 it reports nothing unreal). `--base` and `--head` take any rev, so `--base 43951d72 --head 14b913e3` replays a merged PR.

1. **`stale-doc-name`.** A Swift declaration the diff removes that the head no longer declares anywhere in `apple/` (whole names, one `git grep` of the head), and a repo path it deletes or renames. Only type declarations and type members of non-test `apple/Sources` files count (the enclosing type comes from the base file; locals, `case` patterns and test files do not). A `.agents/**/*.md` line (not `.agents/archive/`) is reported when it names a full path, `Type.member`, or a camelCase or type name of 6+ characters inside a backtick code span; plain lowercase words and prose never match.
2. **`facade-guard`.** A new or changed non-private `static` member (property or zero-argument function) in `apple/Sources` that calls `HouseConfigSource.active.read` (or the file's own `read { }` helper) whose enclosing type and name are not in the `facades` map of the `static-let-reads-house-facade` guard in `contracts/patterns.json`. The map is loaded through `pattern_guard`, the one `HouseFacadeGuardTests` exercises; `HouseConfigSource` itself and `read:` parameters are skipped.
3. **`fails-if`.** A test added under `apple/Tests` (`func test…`) or `tools/tests` (`def test…`, found with `ast`) with no `Fails if:` line in its doc comment (Swift `///`, Python docstring or `#` lines above) and none naming it on a `Fails if` line of the PR body (`ship.sh --body`). The line says what change to the code under test makes the test go red.

`ship.sh` is not the merge path; `pr_land` and `lane_land` do not call this.

## What the hook does not stop

`merge_guard` allows exactly `tools/pr_land.sh ARGS` (also `./tools/…` or this repo's absolute path, no shell metacharacters) and scans every other command: it splits on `; && || | &`, parentheses, braces, backticks, `$(` and `then`/`do`/`else`, strips `env`/`command`/`exec`/`nohup`/`time`/`xargs`, compares the program by basename, skips `git -C/-c/--git-dir`, and also blocks the GraphQL merge mutations and a PUT or DELETE on `/contents/`. **One exemption (owner, 2026-11-04):** that scan stays the decision, and a block is dropped only when every simple command of the input is a non-executing one: `grep`, `rg`, `cat`, `head`, `tail`, `less`, `ls`, `wc`, `echo`, `mkdir`, `git log|show|diff|status|commit` (no `-c`), `gh pr view|list`, or `python3` of an allow-listed script (`tools/tasks.py`, `pr_note.py`, `affected_tests.py`, `jev_gate.py`, `retro_digest.py`, which never run their arguments; never `bg_run.py`, `devcap.py`, `ship.sh`, `pr_land`, `lane_land` or `tools/triage`), with no `$'`/`$"`, substitution (in the command, or in a heredoc body the shell expands), subshell, `/dev/stdin`, shell, other interpreter, `find`, `sed` (except a read-only `sed -n N,Mp`), `awk`, `xargs`, `env` or wrapper, and no heredoc but `cat > file <<WORD` (whose body is then data; a quoted `<<'WORD'` body is literal, so backticks in it are text, and a command may follow on the same line after `&&`). So a `grep` for the retired owner flag, or a brief written with `cat > file <<'EOF'` that mentions `lane_land`, passes; anything else, and any parse failure, keeps the raw verdict. `agent_status.py` and `lane_base.py` exist but are not on that list until read. **Protected paths (owner, 2026-11-07):** see "The owner-kept set is enforced on every route" below; `tools/retro_phase.py` and the merge path itself are no longer protected, an independent review is their gate. **Out of scope:** `curl`, interpreters (`python -c`) and script files that call GitHub. The hook stops the model by accident or by habit, not a determined one; the triage deny list and the owner's review cover the rest.

## The verdict

```json
{"verdict": "pass|changes|blocker",
 "findings": [{"severity": "blocker|major|minor", "rule": "system-api-first", "file": "...", "detail": "...", "fix": "..."}]}
```

The verdict must follow from the severities: `pass` means only minors, `changes` a major and no blocker, `blocker` any blocker; `record.py` rejects a mismatch. It adds `head` (the reviewed commit) and `round` (1, bumped only when the head moved after a `changes` verdict; any `round` in the input is ignored), writes `build/review/<branch>.json`, and replaces the `<!-- review:start -->` section of the PR body with a summary. After two rounds a `changes` verdict lands unless a blocker remains; a blocker goes to the owner. `record.py` enforces the round cap: recording round 3 or later is refused unless you pass `--confirm-round "reason"`, and the reason is stored as `round_confirmation`. That is for a confirmation pass that finds no blockers. A `blocker` verdict at round 3 or later is refused even with `--confirm-round`: a blocker after round 2 parks the PR as Needs Decision.

After a push whose head already has a pass, `tools/ship.sh` runs `record.py --post-check SHA --repo SFenton/native-home`; with no pass (the usual case, ship runs before the review) it does nothing. The reviewer runs the same command right after recording a pass, and it posts the check run `ai-review` on the pushed sha as the reviewer App only when `tools/review_verdict.py` finds a pass for that sha (the push gate's own rule, so the check is never greener than the gate): `success`, else nothing. GitHub binds the check to that exact SHA. If it cannot post, it prints `ai-review check NOT posted: <reason>` and ship carries on. `tools/hooks/review_guard.py` allows `record.py` (so `--post-check`) only for the reviewer, so only the reviewer posts it. There is no App approval review: it does not count toward required approvals (spike 2026-11-09).

**Updating a pushed lane branch (`ship.sh --update`).** After an amend or rebase of your own `agents/*` or `port/*` branch (any other branch is refused before it commits), run `tools/ship.sh "Subject" --update`; the new head then needs its own reviewer pass before it is armed. It reads origin's sha with `git ls-remote` and refuses unless this checkout knows it (an ancestor of HEAD, or in the local branch's reflog because this checkout pushed it), so a commit someone else pushed is never overwritten; it then pushes with `--force-with-lease=refs/heads/BRANCH:<that exact sha>`; a branch not on origin yet needs a plain ship. It then posts `ai-review` for the new head only if that head already has a pass, and re-arms the PR through `pr_land.py` (a refusal is a notice). Why this stays inside the review rule: `tools/hooks/review_guard.py` reserves the agent's own `record.py` command for the reviewer, and `--update` never runs it as the agent. `ship.sh` posts the check as a child process (as a plain ship does), and the post still reads only the trusted verdict store, so without the reviewer's pass for the new head ship posts nothing and the arm is refused until the pass exists. Do not hand-run `git push --force` on a lane branch. Every push also runs `python3 tools/jev_ask.py sync --check` first (CI runs it); a stale list blocks the push, and the message names `python3 tools/jev_ask.py sync`, which you run, bump the question's `version`, commit and ship again.

A base merge into a PR branch runs in the branch's own worktree, or detached and pushed with `HEAD:<branch>`, never in a new checkout of the branch.

## The reviewer's checklist

The same ten items are in the PR template.

1. `/swiftui-pro` on the diff ([how](swiftui-pro.md)).
2. `apple-hig` for UI diffs, citing the HIG section.
3. Pattern reuse ([patterns](../patterns/README.md)): `python3 tools/pattern_guard.py changed --base origin/main` lists the patterns the diff touches and whether their docs moved with them; `python3 tools/pattern_guard.py` must report 0 errors.
4. System API first ([rung 0](change-loop.md#rung-0-system-api-first)).
5. Unit tests, and a UX test and an accessibility test per affected device family.
6. The surface's mockup updated and the hub republished.
7. For visible changes, the design decision record ([propose-first](propose-first.md): options judged, the pick).
8. `HassCore` / `HassDesign` / `HassUI` layering.
9. The performance invariants in [AGENTS.md](../../AGENTS.md).
10. An invariants sweep: no secrets in the diff, `Release-Note` trailers, native only, no new `#if os(macOS)`, devcap holds in new tooling, docs updated, DocC.

Open workflow fixes (guards, the lander, CI on the base, coverage classification) and the branch divergence are tracked in [workflow-roadmap](workflow-roadmap.md).

## Triage

The [triage runner](triage-agent.md) works the same way: its worker follows steps 1 to 5 in the `report/N` branch and lands with `pr_land.sh`. It lands with `tools/pr_land.sh N --keep-worktree` (the runner cleans its own worktree). `config.json` keeps the `gh pr merge` and `gh api …/merge` denies, which do not affect the `gh` calls `pr_land.sh` makes itself, and allows `Bash(tools/pr_land.sh*)`; the runner exports `HASS_TRIAGE_PAUSED_FILE`, so its `PAUSED` file stops landing too. If the worker finishes with an open PR (the gate said `blocked`), the runner still labels it `Ready to Merge` for the owner; a PR the worker already merged finishes the issue on the next tick.

## When it goes wrong

| Symptom | Do |
|---|---|
| `blocked: no independent pass for <sha12>` | Run the reviewer (step 4); it records for the exact head, and a push after the review needs a new pass before it is armed |
| `armed #N` | Nothing to do: GitHub merges when its required checks (`pr-checks` and `ai-review`) pass on that head; start `tools/ci_wait.py` for it; a CI failure means fix, push, and review the new head |
| `failed #N: GitHub refused: ...` | Report the message as is (a rule changed on GitHub, or auto-merge is off) |
| `ship: not armed (see above)` | Read the `blocked` line above it, fix that, then `tools/pr_land.sh N` |
| `blocked: ... blocker(s)` | Fix, or report to the owner if it needs a decision |
| `blocked: merge conflicts` | Merge `origin/main`, test the touched area, push, review again |
| `failed: ...` | `gh` or git error; report it as is |

## The local workflow base

Never merge, cherry-pick or commit onto a local copy of the workflow base (`main`, the same as the product base). Lanes reach it only through `pr_land.sh` (product) or `lane_land.py` (self-changes). Local-only commits there are invisible to every tool and have twice needed a rescue PR (#302; 36 unpushed merges in `uikit-port-root`). Run `python3 tools/base_drift.py` (after a `git fetch origin main`) before resetting or aligning any local base: it lists the commits `origin/<base>` lacks on the local base, on each `--branch` and on every non-lane branch tracking the base (lanes `agents/*` and `claude/*` track it by default, so name one with `--branch`), and exits 3 if there are any. The default base is `workflow_base` of the triage config. `tools/ship.sh` prints it as a warning and never fails because of it.

## Kill guard

The `kill_guard` PreToolUse hook (`tools/hooks/kill_guard.py`, registered next to `merge_guard` in `.claude/settings.json`, tested in `tools/tests/test_kill_guard.py`) blocks process kills that are not scoped to the agent's own work. Cause: on 2026-10-30 a machine-wide `pkill -f "swift-test|swift-testing|swift-build|xctest"` killed the self-hosted runner's swift-test job (exit 143). This Mac is shared by agent sessions, the Actions runner, devcap holds and simulators. Blocked: `killall`; `pkill -P 1`; `pkill` without `-f`; `pkill -f` unless every `|` alternative starts with an absolute path inside your own worktree (the git toplevel of the hook `cwd`, never the project root or a sibling lane, and not a bare root or a root plus a wildcard) or the scratchpad `/private/tmp/claude-<uid>/` (`$PWD`, `$CLAUDE_PROJECT_DIR` and `~` are expanded first); the same for the `grep` in `ps … | grep … | xargs kill`; shell keywords and `timeout`/`watch` wrappers are looked through; any pattern naming `Runner.Listener`, `Runner.Worker`, `actions-runner`, `devcap`, `Simulator`, `CoreSimulator` or `launchd` (even inside a scoped path); `kill $(pgrep …)`, `` kill `pgrep …` `` and `pgrep … | xargs kill` with an unscoped pgrep; `xcrun simctl shutdown all` `erase all` and `delete all`. Allowed: `kill PID`, `kill %1`, `pkill -P PID`, and a `pgrep` that kills nothing or only literal PIDs. The override is a real comment, `# kill-ok: reason`. Instead: kill the PID you started, scope `pkill -f` to your worktree path, or add the override. The triage deny list also refuses `killall`.

After a `cd`, `pushd` or `popd` anywhere in the command, `$PWD` and `$(pwd)` are not expanded (they no longer name the hook's directory), so a pattern built from them is unscoped and blocks. `grep` and `awk` count as the lookup only inside a pipeline fed by `ps`; `ps … | xargs kill` with no scoped filter blocks. The shell splitting (comments, heredocs, wrappers) lives in `tools/hooks/shell_parse.py`, shared with the worktree guard; a heredoc marker counts only outside quotes, `# kill-ok:` only outside heredoc bodies, and a comment inside backticks ends at the closing backtick. Also looked through: `find -exec`, `env -S` (also in a cluster such as `env -iS`), `xargs`/`parallel`, `pidof`, `pkill -P 1,2` and a heredoc fed to `bash`/`sh`.

**What the kill guard does not stop:** aliases and shell functions, a command held in a variable (`$cmd`) or built for `eval` from variables, script files and interpreters (`python -c "os.kill…"`, `osascript`), `kill` of a PID taken from a variable the agent got from somewhere unscoped, and `$PWD` tricks the hook cannot see (for example `cd` inside a sourced script, or `find -execdir sh -c '…$PWD…'`, where `$PWD` is the directory `find` entered, not yours). It stops a model by accident or habit, not a determined one.

## Worktree guard

The `worktree_guard` hook (`tools/hooks/worktree_guard.py`, registered in `.claude/settings.json` for Bash, for `Edit|Write|MultiEdit|NotebookEdit` and at SessionStart; tested in `tools/tests/test_worktree_guard.py`; the shell splitting is shared with the kill guard in `tools/hooks/shell_parse.py`) keeps sessions out of a repository's shared primary checkout (owner, 2026-10-30: one session, one worktree). A checkout is primary when git's absolute git dir equals its common dir; a linked worktree is always fine wherever it lives (`.claude/worktrees/*`, the triage runner's `~/hass-agents/worktrees/N`). Git decides, never a path or device name.

- **Session start** in a primary checkout adds a note: call `EnterWorktree` with a short kebab-case topic name before any edit, commit or branch change.
- **Edit tools** are denied for a path in a primary checkout unless git ignores it (`git check-ignore --no-index`: `build/handoff`, `.build` and scratch output stay writable). Outside git, in a linked worktree, or in a worktree nested under a primary, they pass.
- **Bash** is denied when the effective directory is in a primary checkout (`cd`, `pushd`, `git -C` and `env -C` are followed; `$PWD`, `$(pwd)`, `$HOME`, `~` and `$CLAUDE_PROJECT_DIR` are expanded) for: `git commit|add|rm|mv|restore|checkout|switch|reset|merge|rebase|pull|cherry-pick|revert|am|clean`, `git apply` (not `--check`/`--stat`), `git stash` (not `list`/`show`); `sed -i`, `perl -i`, `tee`, `>`/`>>` redirects, `touch`, the destination of `cp`/`mv`/`ln`/`install` (and the sources of `mv`), and `rm`/`rmdir` targets, when the target is in a primary checkout and not git-ignored; and `tools/ship.sh` run from there. `/dev/*` and file descriptors are fine. Allowed: `status`, `diff`, `log`, `show`, `fetch`, `branch`, `push` (the merge guard covers `main`), `git worktree add|list|remove|prune`, `git <sub> --help|-h`.
- **Also blocked in a primary checkout:** `gh pr checkout` and `gh repo sync` (they change the branch), `git branch -m|-M|--move`, `truncate`, `patch` (not `--dry-run`), and a mutating git subcommand aimed at the primary checkout from elsewhere with `GIT_DIR=`/`GIT_WORK_TREE=` (bare or after `env`) or `--git-dir`/`--work-tree`. Reading and creating with `gh` (`pr view`, `pr create`, `issue …`) stays fine.
- **Scope:** only the project's own repository: the guard compares the target's git common dir with that of `$CLAUDE_PROJECT_DIR` (the hook `cwd` when unset), so a scratch `git init` under `/tmp` is never blocked, and a project dir that is itself a linked worktree still guards the primary checkout. If neither is in a repository, nothing is guarded.
- **False positives avoided:** a path made by an earlier `git worktree add` in the same command counts as a linked worktree (`git worktree add ../w -b w && cd ../w && git commit`); `[[ a > b ]]`, `(( 1 > 2 ))` and `$((1>2))` are not redirects. A backslash-newline joins lines. A `"$(…)"` or backtick substitution inside double quotes is parsed as its own context (quotes and heredocs inside it start fresh) and its commands are checked. Ignored-path checks run as one `git check-ignore --stdin` per repository.
- **Override:** a real comment, `# worktree-ok: reason`, outside quotes and heredoc bodies. Use it only when the owner asked for work in the primary checkout.
- **Fails open:** bad input or a git failure allows the call.

**What the worktree guard does not stop:** aliases and shell functions, a path or command held in a variable (`cd $DIR`, `$cmd`), `eval` built from variables, scripts and interpreters that write (`python -c`, `make`, `npm`), `xargs` and `find -exec` writers, `dd`, `mkdir`, `curl -o`, `patch -d DIR` or a patch file that names other paths, `GIT_DIR`/`GIT_WORK_TREE` set by a separate `export` or assignment statement, `git branch -d|-D|-f|-c` and `git tag`/`git update-ref` (ref changes that leave the checkout alone), `git worktree` commands run against the primary itself, `awk -i inplace`, `ed` and `python`-style writers, a substitution's `cd` (its commands are checked in the directory the whole command ends in), and `cd` inside a sourced script. It stops a model by accident or habit, not a determined one.

## Review-only merges and the denylist (owner, 2026-11-07)

- **Review is the gate, GitHub the checks.** `tools/pr_land.sh N` arms auto-merge after an independent reviewer's `pass` for the exact head (a verdict `tools/review/record.py` wrote for the reviewer, read through `tools/review_verdict.py`), the app-UI gate, the owner-kept set check, mergeability, the author and fork check (the author is `SFenton` or the `agent_login` of `tools/triage/config.json`, `sfenton-agent`; read from that pinned file only, never from the environment) and the denylist. `pr-checks` and `ai-review` are enforced by the ruleset on `main`, not here. The release note is not checked by `pr_land`: `tools/ship.sh --note` adds the `Release-Note:` trailer, and a squash carries it. `merge_guard` pins `pr_land.py`, `house_scan.py` and the config to the base branch's copy for `pr_land.sh`, and `lane_land.py` (with `release_closure.py`) and the config for an interactive `lane_land`, so a PR cannot change what the gate asks for.
- **The owner-kept set is enforced on every route.** One list (`lane_land.protected_set`: `DEFAULT_PROTECTED`, the config's `protected_paths` and every file the `ios-release*` jobs run or import, derived by `tools/release_closure.py` from the workflow steps) drives both routes: `lane_land` refuses a lane and `pr_land` (through the app-UI gate, run from the base copy) refuses a pull request that adds, edits, deletes or renames any of it, and nothing merges. The set: credentials (`tools/hass_creds.sh`, `tools/gh_app_token.py`), signing and the release pipeline (`tools/release/**`, `.github/workflows/ios-release*.yml`, `tools/devcap.py`, `tools/ci_hygiene.py`, `tools/release_closure.py`: the release job runs them with the App Store Connect key in reach), the review recorder and identity (`tools/review/**`, `tools/hooks/review_guard.py`, `.claude/agents/reviewer.md`) and git's own plumbing (`.git/**`, `.githooks/**`, `.gitmodules`, `.gitconfig`). The only way past the refusal is the owner approving this pull request on GitHub (their review of this exact head) and merging it there; there is no override flag (retired 2026-11-10). A test derives the release closure and the import closure of the kept set and fails when one of them is not protected; `record.py` imports no landing tool.
- **Review identity.** Only the reviewer (`agent_type` `reviewer`) records a verdict. `tools/hooks/review_guard.py` refuses a file tool writing `build/review/*.json` or `~/hass-agents/reviews/**`, refuses `record.py` from any other session, and leaves an identity stamp when the reviewer runs it; `record.py` copies it into the verdict as `reviewer` (`agent_type`, `session_id`), and `review_verdict.has_pass` (which `pr_land` and `ship.sh` read) and the interactive `lane_land` refuse a verdict without it. That store is the arming gate, so the `review_guard` protection of `~/hass-agents/reviews/**` is the only barrier to a self-written pass (pinned in `test_autonomy_kept_set.py`). `record.py --lane BRANCH` also writes the file the interactive `lane_land` reads. The runner-launched lane review is separate: the runner parses the reviewer's own output and writes the record itself. A tripwire, not a wall: a script that writes the file is out of scope, and the independent review of the change that adds it is the cover.
- **Denylist layer 1.** `tools/ship.sh` runs `python3 tools/house_scan.py denylist --base-ref origin/<base>` before it pushes, and `pr_land` runs the same command on the exact PR head (fetched as `refs/pull/N/head`, checked out in a shared clone) with `--base-root` and `--config` set to the base branch's tree and `contracts/house_scan.json`: the head is judged by the **base's** `skip_prefixes` and allowlists, never its own, and `.plist`, `.svg` and `.xcprivacy` files are read too. Only hits the change adds against the base count, so debt still being scrubbed does not block every PR; without a base the command counts every hit in every file, debt paths included, and applies no skip list. The list is, in order, `HOUSE_SCAN_DENYLIST`, `~/.config/fenton-hass/house_denylist.txt`, then `~/hass-agents/house_denylist.txt` (the list the agents build; the owner approved it, 2026-11-07); house_scan reads it, agents never open it, and the output is counts, the source name (`env`, `config` or `agents`) and `path:line`, never a term. Any hit refuses. A list that is not loaded prints "denylist not loaded" and continues, unless `denylist_required` is true in the config, which then refuses (default false; the owner turns it on once the list exists).
- **Going public.** Build the snapshot with `python3 tools/public_snapshot.py SNAPSHOT_DIR [--ref origin/main]`, then publish it with `tools/go_public.sh SNAPSHOT_DIR SFenton/native-home`; the script is the only way. `public_snapshot.py` writes the blobs of the ref's tree (`ls-tree` plus `cat-file`, so no archive attributes, ignore rules or filters apply) into an empty directory (a non-empty one is refused), leaves out the short `PRIVATE_ONLY` list kept in the tool itself (never read from the tree; today `.gitleaksignore`, whose fingerprints name private commits), and makes one commit as `S+H <noreply@example.com>` ("Initial public snapshot"), with every git call in a scrubbed environment (no `GIT_*` variables, no system or global config, an empty template, hooks off, fixed dates). It then fails closed unless the committed tree equals the ref's tree minus the list (mode, blob id, path), the identity is exactly neutral, and there is no remote, tag, other ref or hook. Add to the list only files private by nature, never to hide a hit. It prints counts and the left-out paths. `merge_guard` refuses `gh repo create --public|--internal`, `gh repo edit --visibility` (anything but `private`), a visibility change through `gh api` (REST or GraphQL) and a `git push` to any remote that is not this repository's origin, and, for an agent session, runs the script only in that exact form from a checkout whose `go_public.sh`, `go_public_gate.py`, `house_scan.py` and config equal the base's. The script runs `tools/go_public_gate.py` first and only then creates the repository **private**, pushes the snapshot and makes it public. The gate refuses unless: the snapshot is one orphan commit on one branch with a clean tree (no history to hide a term in) whose author and committer are exactly `S+H <noreply@example.com>` with 0 remotes; house_scan has 0 hits judged by the **trusted base config** read from `origin/main` (the snapshot's own `skip_prefixes`, allowlists and debt are never read, and the base's are stripped); the denylist is loaded with at least 20 terms and has 0 hits in **every file type**; and gitleaks finds nothing in the files (`dir`) nor in the history (`git`). It prints counts and the denylist source only. Any gate failing keeps the repository private.
