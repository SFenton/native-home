# CI: the Mac runners, pr-checks, ios-release and nightly

> **What:** pull-request CI runs on GitHub-hosted runners (Linux for the checks and tool tests, one macOS job for the app); the release and nightly workflows still use the owner's self-hosted Macs. **Read when:** a check fails or hangs, you touch a workflow, or you wonder what runs when.

The repo is public, so GitHub enforces the ruleset on `main` and [`pr-checks`](#the-merge-gate) is the merge gate (see below); [`tools/pr_land.sh`](../../tools/pr_land.sh) arms auto-merge after the gates GitHub cannot run. The self-hosted runners below serve `ios-release*`, `version-bump` and the nightly run only. While a runner's Mac is asleep or off, its jobs queue. Each runner has one slot, so its jobs run one after another.

- The rule (owner, 2026-11-05): a job that only runs Python tools says `[self-hosted, macOS]` and runs on either Mac; `swift test`, `repo-checks`, `scope` and `tool-tests` say `hass` until hosted runners land (owner, 2026-11-07; they were `host`); simulators and signing say `hass`. The Mac mini's devcap is `{"simulator": 1, "build": 1}` (8 GB), so it never takes journeys.
- **Each runner has one slot.** Nightly `coverage` (up to 150 min from 02:00) holds the Mac mini, and no PR job runs there now, so a `swift-test` pushed during the nightly does not wait for it; only the aggregate takes whichever Mac is idle, and `scope` queues on `hass-mac` with the other PR jobs. Trade-off: PR jobs share `hass-mac` with the nightly journeys and release builds, so they can queue behind them. If the Mac mini is asleep or off at 02:00, `coverage` queues, and the nightly `report` (which needs it) waits up to GitHub's 24-hour queue limit, so no `Nightly Fix` issues are filed for the journeys either until it comes back; keep the Mac mini awake (its `sleep` is 0) and logged in. The owner moved repo-checks and tool-tests to `hass-mac` on 2026-11-07 because the mini lacks disk; the hang seen on `hass-mac` on 2026-11-06 (base rerun silent for 30 minutes, run 42169850422) is still unexplained and stays a known risk there. `scope` and the aggregate need nothing mini-only: both Macs run system python3 3.9, each runner has its own workspace (`clean: false` is per runner), and the disk pre-flight and the primary-clone setting for pruning are read per runner (the owner sets it on each Mac).
- Each is a per-user LaunchAgent (`actions.runner.<owner>-<private-app-repo>.<runner>`) so it reaches the login Keychain (and, on the MacBook, simulators). Commands below use `hass-mac`; on the Mac mini substitute `host-mini` and `~/actions-runner-host`.
- `cd ~/actions-runner-hass && ./svc.sh status|stop|start` controls it. `gh api repos/$PRIVATE_APP_REPO/actions/runners` shows `online` or `offline`. Its environment is `.env` and `.path` there (`DEVELOPER_DIR`, `PATH` with Homebrew).
- Re-register (token expired, runner removed): `T=$(gh api -X POST repos/$PRIVATE_APP_REPO/actions/runners/registration-token --jq .token)`, `./config.sh --unattended --url https://github.com/$PRIVATE_APP_REPO --token "$T" --name hass-mac --labels self-hosted,macOS,hass --replace` (on the Mac mini: `--name host-mini --labels self-hosted,macOS,host`, then reapply the `SessionCreate` fix below). Never print the token.
- Workflows check out with `clean: false` and run `git clean -ffdx -e apple/.build -e build`, so SwiftPM and build caches survive between runs.
- Every compile and simulator run takes a [`tools/devcap.py`](../platforms/apple/capacity.md) hold, the same as agent work on this Mac.

### Signing the IPA

`tools/release/ios_ipa_build.sh` needs an **Apple Distribution** identity for team 3Q9X8JX23S in the Mac's login Keychain and the team's Apple ID signed in to Xcode (so `-allowProvisioningUpdates` can fetch the App Store profiles); an App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH` in the runner's `.env`) works instead. Before archiving it probes every identity the archive and export use (the Distribution identity and each Apple Development identity whose certificate belongs to the team, since automatic signing archives with Development) by codesigning a temp file under a 20 s timeout, and it runs `xcodebuild archive` and `-exportArchive` under an idle watchdog that kills them after 10 minutes without output (`FENTON_IDLE_TIMEOUT_SECONDS`, a positive integer) and forwards TERM, INT and HUP to xcodebuild so a devcap hold overrun or cancel never orphans it. A missing identity, a probe that hangs or fails, or a watchdog kill exits 4 and the job prints `BLOCKED` with exactly what to provide (the `security set-key-partition-list` owner step). Nothing else is needed: no upload, no TestFlight record.

## The nightly run (2 AM)

1. launchd job `com.sfenton.hass-nightly` (`tools/nightly_install.sh`, plist in `~/Library/LaunchAgents`) runs [`tools/nightly_dispatch.sh`](../../tools/nightly_dispatch.sh) at 02:00 local time (2 AM Pacific, DST-safe) from the triage clone, which tracks `origin/main`.
2. The script stops if `~/.config/fenton-hass/NO_NIGHTLY` exists (`touch` it to pause nightly runs, `rm` it to resume), runs `devcap.py reap` (shuts down simulators booted outside a hold, and, from devcap 1.5.0, **deletes this project's pool simulators idle more than 24 h** that are shut down and unheld; see [capacity](../platforms/apple/capacity.md#simulator-lifecycle-devcap-150)), then `caffeinate -i gh workflow run nightly.yml --ref main` and keeps the Mac awake until the run ends.
3. Waking the Mac needs sudo, so the owner runs once: `sudo pmset repeat wakeorpoweron MTWRFSU 01:55:00`.
4. Live-server journeys load `FENTON_HASS_*` in-process with `tools/hass_creds.sh` (from `~/.config/fenton-hass/env`), as in [devices](../testing/apple/devices.md); nothing is stored in the repo or the workflow. The shard step registers the values with `::add-mask::` so the job log hides them.

### Failures become issues

`tools/nightly_report.py issues` merges the shard results into one status per **area**: `journeys-iphone`, `journeys-duo`, `journeys-ipad`, `coverage`.

- **fail:** one issue `Nightly: <area> failing` with the label `Nightly Fix` (deduplicated by title against open issues). If it already exists the run comments the new failures and removes `Awaiting Nightly`.
- **pass:** the open issue gets a comment and is closed, but only in a full run (`filter` empty; the workflow passes `--full-run`). A filtered run never comments on or closes an issue.
- **infra** (hold timeout, simulator did not boot, a shard result missing, the runner's live-server credentials missing or refused): nothing is filed or closed; it is a machine problem, not a code fix.

### The triage runner fixes them

[`hass_triage.py tick`](triage-agent.md) works the owner's requests first, then open `Nightly Fix` issues on this repo (authors `SFenton`, `github-actions`): a worker on branch `nightly/N` (worktree `nightly-N`, state `state-nightly.json`, prompt `tools/triage/prompts/nightly.md`) reproduces with the failing tests, fixes, opens a PR, the reviewer subagent reviews it, `tools/pr_land.sh` lands it. The agent never closes the issue: after the merge it carries `Awaiting Nightly` and the next passing nightly run closes it; a failing one reopens the work. The triage `PAUSED` file stops both intakes, and `pr_land.sh` honours it. `hass_triage.py init-labels` creates the labels in this repo.

## Disk hygiene

The disk filled overnight on 2026-10-29 (simulators 297 GB, DerivedData 142 GB). Every workflow now:

- **Fails early.** The first step of every job is `python3 tools/ci_hygiene.py preflight --min-gb 30`; under 30 GB free it stops with a message saying what to delete.
- **Owns its DerivedData.** `xcodebuild` runs with `-derivedDataPath` under the runner's `_work` (`dd-<run>-<job>` for `pr-checks` and `ios-release`, deleted by an `if: always()` step; `dd-nightly-<run>` for the whole nightly, via `FENTON_DERIVED_DATA` in `ios_uitest.sh`, deleted by the report job). `swift test` keeps `apple/.build`, the one intentional cache.
- **Cleans up after the nightly.** The report job deletes only pool simulators that devcap's `sims.json` registry says it created during the run (`created_epoch` after the snapshot) **and** that this checkout used (`ci_hygiene.py sims-snapshot` records the simulators and the time at the start, `sims-clean` at the end), erases the shut-down simulators this checkout used (`apple/.build/uitest-*.udid`), and does nothing at all when the snapshot, `simctl list`, devcap's gate folders or its `sims.json` registry cannot be read and removes xcresults and nightly logs older than 7 days. It never touches a booted simulator or one devcap holds.

- **Drops orphaned DerivedData.** Xcode's `~/Library/Developer/Xcode/DerivedData/FentonHome-*` folders outlive their worktrees (64 GB from deleted ones on 2026-10-31). The pre-flight runs `ci_hygiene.py derived-orphans` before the free-space check, and `tools/pr_land.sh` runs it after it removes a worktree. It deletes a `FentonHome-*` folder only when its `info.plist` `WorkspacePath` names a path that no longer exists; a folder with no readable `info.plist` or `WorkspacePath`, or whose project still exists, is never touched. `--dry-run` lists them.

- **Reaps before it fails (2026-11-04).** The hass-mac runner failed the 30 GB pre-flight twice on 2026-11-04 (24 GB free). The owner approved one manual prune that day of 22 merged worktrees, 45 simulators and DerivedData (24 GB to 127 GB free). `preflight` now automates a narrower version of it: when free space is under the limit it runs, in order, `prune-worktrees`, `clean-sims` (idle pool simulators), `prune-results` and the DerivedData orphan sweep, prints the GB each freed, rechecks free space after each step and stops as soon as it is enough. It errors only if space is still short after the last step; a step that raises is reported and the chain goes on. The owner approved the manual prune, not these rules; they are the reviewer-hardened subset:
  - `ci_hygiene.py prune-worktrees [--repo PATH] [--days 3] [--dry-run]` removes a linked worktree (`git worktree remove`, never `--force`, then `git worktree prune`) only when its HEAD is merged into `origin/main` or `origin/<workflow_base>` (`tools/triage/config.json`) and the tree is clean (no modified or untracked files), unlocked, idle for the days (directory, `HEAD` and `index` mtimes), holds no `build/handoff/*.md`, has no devcap holder with its `cwd` inside it, and is not the primary, the current worktree, or on `main` or the workflow base. Merged means an ancestor, every commit patch-equivalent (`git cherry`), or, because `pr_land` squash-merges, `git merge-tree --write-tree origin/<base> HEAD` giving exactly `origin/<base>^{tree}`. If `git` or devcap's gate folders cannot be read it removes nothing. Branches are kept; only the checkout goes, **and `git worktree remove` deletes the checkout's ignored files too** (`build/`, `.build`), so a worktree with ignored output you want is not a candidate; `git worktree lock` it.
  - **Which repo.** A runner's own clone has no linked worktrees, so the command prunes the *primary clone* named by `--repo PATH`, else `FENTON_PRIMARY_REPO`, else the one line in `~/.config/fenton-hass/primary_repo`. With none it skips and prints how to set it. The path must be a real primary clone: its `origin` URL matches this repo's and it is not a linked worktree. **The owner creates `~/.config/fenton-hass/primary_repo` once on each runner Mac** (the path of the main checkout, for example `<repo>`); agents do not.
  - **Simulators.** The automatic chain only deletes `(pool N)` simulators that are shut down, not held or awaited by devcap, **and** that devcap's `sims.json` registry names as created by devcap (kind pool or ephemeral; `pick-sim` recreates them). It never erases a simulator and never touches a booted one, a non-pool one, one devcap did not create, or anything when `simctl`, devcap's gate folders or the registry cannot be read. A wider erase is not automatic; it would be a separate manual command defaulting to `--dry-run` (not built).
  - The tests (`tools/tests/test_ci_hygiene.py`) use temporary repos and mock `simctl`; they never run the reaper on real worktrees, simulators or DerivedData. Metric: `Disk pre-flight` failures per week in `gh run list` (target none).

What leaks, measured on 2026-10-29: `devcap pick-sim` creates `<name> (pool N)` devices with `simctl create` (empty, never booted by it) once and reuses them, so devices do not multiply per run (41 devices existed). The space is **data growth inside the devices** the journeys use (the biggest were 20 to 42 GB each); `sim_slim.sh` disables daemons but does not erase data. If the disk fills again, `du -sh ~/Library/Developer/CoreSimulator/Devices/* | sort -h`, then `xcrun simctl erase <udid>` on shut-down ones. `xcrun simctl delete unavailable` clears devices of removed runtimes.

## Keychain on the runner

Two tests (`keychainRoundTrips`, `tokenStoreRoundTripsAndFallsBack`, in `PushTests.swift`) use the login keychain, and `ios-release` signs with it.

**Cause (found 2026-10-29):** the runner's LaunchAgent (`~/Library/LaunchAgents/actions.runner.<owner>-<private-app-repo>.hass-mac.plist`, generated by the runner's `svc.sh`) had `SessionCreate = true`. That gives every job a new security session with no access to the user's unlocked login keychain. The two tests failed with `errSecInteractionNotAllowed` (-25308) and the `ios-release` signing probe failed (codesign exit 1), although both passed in a login shell. The tests no longer skip on the runner; they must pass there.

**Fix** (owner, one time; needs no password for the plist, but the signing keys need the next step):

```
plutil -replace SessionCreate -bool false ~/Library/LaunchAgents/actions.runner.<owner>-<private-app-repo>.<runner>.plist
launchctl bootout gui/$(id -u) <plist>
launchctl bootstrap gui/$(id -u) <plist>
```

Run `bootout`/`bootstrap` while the runner is idle. **Re-running `svc.sh install` regenerates the plist with `SessionCreate` true, so reapply the fix after any reinstall.** The pre-flight (`tools/ci_hygiene.py preflight`, run by every job) prints a `::warning::` naming this fix when it finds `SessionCreate` true on the runner running the job (`RUNNER_NAME`); it never fails the job. Applies to both runners.

Also keep the Mac's user logged in and unlocked while the runner works, and give the signing keys a one-time grant (needs your login password, so it is not done for you): in Keychain Access add `/usr/bin/codesign` to the Apple Distribution private key's Access Control ("Always Allow"), or run `security set-key-partition-list -S apple-tool:,apple: -s -k <login password> ~/Library/Keychains/login.keychain-db`. `tools/release/ios_ipa_build.sh --probe-signing` (a codesign of a temp file with each identity, 20 s timeout) makes `ios-release` stop with `BLOCKED` (exit 4) instead of hanging on a prompt until the grant exists.

## Tests that share the Mac

`swift test` runs inside the `swift-test` devcap pool (one slot) as well as `build`, because every SwiftPM test process on this Mac shares one persistent preferences domain, `swiftpm-testing-helper`, including FestivalNativeApps' test runs. The pool serializes only the runs that take it (this repo's `pr-checks` and `apple_coverage.sh`); FestivalNativeApps' `swift test` does not use it, so a concurrent Festival run can still write the domain. A test that sets a launch switch in `UserDefaults.standard` (`withLaunch`, the gallery's `directionG…` keys) can then change what a concurrent run in another worktree draws, and a run that is killed leaves the switch behind (found 2026-10-29: `directionGOrder = lower` and `directionGSheet = open` left in the domain made `directionGOrdersItsSections…` fail on every later run, in a shell and in CI alike). Tests that depend on a switch clear it first; window snapshots wait for the page to draw instead of a fixed settle. If a UI test fails for no reason, `defaults read swiftpm-testing-helper` shows what is stale.

Two more environment-dependent UI tests, both in `GalleryLaunchTests` (diagnosed 2026-10-29, they failed in a developer shell too): the Chores page's fixtures have due dates relative to now, so after four scroll steps the window could show only empty space (the check now also looks at the unscrolled page), and the shell-header page draws one small control on a wide tablet window that the old coarse pixel grid (40 across) sometimes missed (the grid is now 160 across). Neither was a runner problem.

## The merge gate

Review before push (owner, 2026-11-09: "only submit code once the reviewer has passed it", and "shouldn't any code that gets pushed be reviewed anyways, so GitHub doesn't need to keep track of things?"). Supersedes the 2026-11-08 design (an approving review from the reviewer app on GitHub). The rule: **nothing an agent pushes to SFenton/native-home reaches it without an independent `pass` verdict for that exact commit.** GitHub keeps only a pull request and a green `pr-checks`, with an approval count of 0. The loop is: the Coder commits, the Reviewer passes the exact head, the push, the PR, arm, CI. A CI failure means fix, re-review, push; any new commit needs a new review.

1. **The verdict record.** The Reviewer records with `tools/review/record.py verdict.json --lane BRANCH` from the branch's worktree. Besides `build/review/<branch>.json` it writes the trusted lane store `<branch>-<sha12>.json` under the agent root's `reviews` folder, the file `tools/lane_land.py` already trusts and only the reviewer's identity can write. `tools/review_verdict.py` is the one reader: a record counts only when it carries the reviewer identity, says `pass`, names the full sha as `head` and has no major or blocker finding. A worktree file is never read.
2. **Git's own pre-push hook decides what a push may carry** (`.githooks/pre-push` runs `tools/prepush_review.py` before the house denylist; `tools/setup.sh` sets `core.hooksPath`). Git hands the hook the url (after `insteadOf` and `pushurl`, once per push url) and every `<local ref> <local sha> <remote ref> <remote sha>` line actually being pushed, after every earlier command of the line has run, so no command text is parsed. A push is gated when the url, or any push url of the named remote, is SFenton/native-home (https, ssh or scp form, `user@`, `.git`, any case). The hook refuses unless each pushed ref that is not a delete points at a commit (a tag is peeled) with an independent `pass` in the trusted store (`tools/review_verdict.py`; the account's home from the password database, never `$HOME`), refuses any ref to `main` or `master` (deleting included), allows deleting another remote branch, leaves other repositories and local paths alone, and refuses a url form it cannot read; any error is a refusal. `tools/ship.sh` checks the same early for a friendly message and refuses a native-home origin when `core.hooksPath` is not `.githooks`.
3. **GitHub: a PR, `pr-checks` and `ai-review`.** Ruleset `main-checks` (id 26774461) requires a pull request, squash only, and the status checks `pr-checks` pinned to GitHub Actions (`integration_id` 15368) and `ai-review` pinned to the S+H Reviewer app (5618837), with no bypass. No approvals: an App approval review does not count toward them (spike 2026-11-09), so the S+H Reviewer app posts no reviews. It posts comments (`issues: write`, `pull_requests: read`) and, from `tools/ship.sh` right after a reviewed push, the check run `ai-review` for the pushed sha (`checks: write`, via `record.py --post-check`); that check is the server-side backstop, required by the ruleset (`ai-review` from App 5618837, owner, 2026-11-09). **Who can merge:** SFenton is the only collaborator, so an outsider cannot merge or approve anything; fork workflows need approval before they run (repository Actions setting), and the `pr-checks` author step (the PR must be by `SFenton` from this repository) is advisory because a PR can edit its own workflow.
4. **Arming.** After the PR opens, `tools/ship.sh` runs `tools/pr_land.py N`. It refuses unless the kill switch is off, the PR is not `Needs Decision` or conflicting, the app-UI gate (with the owner-kept set) and the denylist pass, the PR is by `SFenton` from this repository and based on `main`, HEAD has its pass, and `tools/ruleset_gate.py` finds on `main` (`gh api repos/SFenton/native-home/rules/branches/main`, then `rulesets/ID`) a `pull_request` rule (squash allowed), `pr-checks` with `integration_id` 15368 and `current_user_can_bypass` `never`. On any error, malformed answer or missing property it prints a notice and arms nothing. `merge_guard` refuses that raw `gh pr merge --auto` form (and `--admin`) in every session, so `pr_land` is the only way to arm; it allows only `gh pr merge N -R SFenton/native-home --disable-auto` on the agent's own PR (by `SFenton`, from `SFenton/native-home`) ([pr-lifecycle](pr-lifecycle.md)). The pin is checked at arm time only, which is enough: any later push still goes through the pre-push hook. The merge is made by `SFenton`, not `GITHUB_TOKEN`, so the `push` run on `main` and `version-bump` still fire.

**Which guard covers which step.** Push: git's pre-push hook (shas and urls), with `ship.sh` as the early message. Going around the hook: `tools/hooks/push_guard.py`, a Claude PreToolUse hook that is a plain token scan over the command text (a match anywhere is a refusal, and a missing, broken or non-importable script is exit 2, wired in `.claude/settings.json`): `--no-verify`, any `core.hooksPath` or `GIT_CONFIG_*`/`--config-env` injection, `send-pack`/`http-push`, `GIT_DIR`/`--git-dir` with `push`, `gh api` writes to `/git/refs`, `/merges` or `/contents`, and `gh repo sync`. Open and arm: `ship.sh` through `tools/pr_land.py` (the gates above). A raw auto-merge, an `--admin` merge, or a `gh api` write (or `gh repo edit` of the merge settings) to the rulesets, branch protection, repository settings or App installations by an agent, in any session: `merge_guard.py` (the agent runs as the owner's admin login, so this guard is what keeps it from weakening `main-checks`). **`merge_guard` is a tripwire, not a wall (owner, 2026-11-09).** Not stopped: shell indirection (`bash -c` and `eval` strings built from variables, an endpoint or flag held in a variable such as `$EP`, brace expansion, `xargs`-fed arguments), `gh` aliases and shell functions, and a GraphQL body generated at run time; it stops a model by accident or habit, not a determined one. It does read `gh api` input files (JSON-decoded, resolved against the effective `cd` or `env -C` directory) and refuses stdin, `/dev/*` and unresolvable paths. The wall is a GitHub credential for agent sessions without admin rights (planned, separate task). The merge itself: GitHub, on `pr-checks` and `ai-review`. A waiting PR gets `tools/ci_wait.py` through `bg_run`. **Residual risk, not covered:** a push from a clone that never ran `tools/setup.sh`, `curl` or an interpreter calling the GitHub API, a tool editing `.git/config`, and anything outside Claude hooks (the hooks bind agent sessions only). The hook runs from the worktree's own files (`.githooks/pre-push`, `tools/prepush_review.py`, `tools/review_verdict.py`, `tools/prepush_denylist.py`), so an uncommitted edit to them in the working tree disables the gate for the next push; the reviewer pass covers committed content only, and the Claude-side token scan cannot see an edit made by a tool. A config write of `include.path` or `includeIf.*.path` is refused alongside `core.hooksPath`, because an included file can set it (a read-only `git grep` or `git log -S` for the name passes). **The owner's push:** the owner, in their own terminal, puts `SH_OWNER_PUSH=1` in front of their usual push command (an assignment in that command's environment). That skips only the review step of `.githooks/pre-push`; the house denylist still runs and still refuses on a hit, and `--no-verify` is not needed. Only the exact value `1` counts, and only outside an agent session. **Such a head merges only after a reviewer pass.** The escape skips the local review, so the pushed head has no pass in the store and no `ai-review` check: `pr_land` blocks it (`no independent pass`) and, once `ai-review` is a required check, GitHub keeps it BLOCKED. To merge it, the Reviewer passes that exact sha (`record.py --lane BRANCH`) and then `python3 tools/review/record.py --post-check SHA --repo SFenton/native-home` posts the check; there is no ruleset bypass (owner decision O1, 2026-11-09). **What is enforced:** (1) the hook ignores the escape, prints one line saying so and runs the review step as normal when any of `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT` or `FENTON_HEADLESS` is set and non-empty, so a variable name an agent builds at run time (`${X}_PUSH`, `printf`) or sets from a helper script (`os.environ`) does nothing while those markers stand; (2) `push_guard` refuses any agent command that sets or assigns `SH_OWNER_PUSH` (`env`, `export`, a prefix assignment, `bash -c`, a file edit), whether or not it mentions git (a read-only `grep` for the name passes), and refuses any command that unsets or blanks a marker (`unset`, `env -u`, `env -i`, `exec -c`, `MARKER=`). **Residual risk:** a script that deliberately builds a clean environment can still reach the escape, for example one that spawns the push with the markers removed in code. That is accepted: the hook runs from worktree files anyway (above), so an agent determined to defeat the gate already can, and the layers exist to stop accidents and casual circumvention, not a determined one.

## House-data lint and the history secret scan

`python3 tools/house_scan.py` runs in `repo-checks` (about 5 s) and as a tool test. It reads tracked text files and flags entity-id literals, private IPv4 and IPv6 unique-local addresses, `*.ts.net` and `*.local` hosts, VIN-shaped strings, 32/40-hex strings, and the private request repository's name; output is counts and `path:line rule`, never a value. `contracts/house_scan.json` holds the allowlist (`demo_` and generic ids, `example.local`, `homeassistant.local`) and the **debt**: path prefixes with a `reason`, a ledger `check` and a per-rule `baseline`. A hit outside every prefix fails; so does any rule whose count rises above its baseline, which also stops swapping one kind of hit for another. Lower a baseline as a scrub lands (the check prints a note when a count drops). An optional denylist of real names lives in the owner's local `fenton-hass` config folder (`house_denylist.txt`); it is never committed, and its hits are counted apart and never count against the baselines.

`tools/history_secret_scan.sh` is a one-time gate before step 13 (going public), not a per-PR check: gitleaks over every commit on every branch with redaction, report in the git-ignored `build/secret-scan/`, counts by rule only. Exit 0 clean, 1 findings, 2 gitleaks missing or the scan failed. It does not install gitleaks. Findings triaged as false positives are listed by fingerprint (no values) in the root `.gitleaksignore`, which the script passes with `--gitleaks-ignore-path`; add a line only after triaging it as in [secret-scan-triage](secret-scan-triage.md). Fake test fixtures are also path-scoped in the root `.gitleaks.toml` (passed with `--config`, one file and its minimal rule ids per entry, reviewed), because fingerprints do not survive a fresh orphan snapshot; scan from the repo root with relative paths.

## What a pushed branch can do on the runner

Any branch pushed to this repo runs its own workflow files on `hass-mac` and `host-mini`, as the owner's user, with the owner's Keychain and SSH keys within reach, including the mesh key that reaches the owner's other machines. A triage worker can push a branch, so **its deny list does not contain it**: a workflow in the branch could run a command the worker's `--disallowedTools` would refuse, and print the result into the job log. What limits it today: the repo is private and only accounts with write access can push; `pull_request` workflows get a read-only `GITHUB_TOKEN` and no repository secrets (there are none); the workflows here pin every third-party action by commit SHA; the triage runner never gives the worker a token that can approve or merge outside `tools/pr_land.sh`; and `tools/review/record.py` plus the reviewer read the diff, workflow files included, before anything lands. Treat a PR that touches `.github/workflows/` or `tools/ci_*` as needing the owner's eye, and keep secrets out of the runner's environment (`~/actions-runner-hass/.env` on the MacBook and `~/actions-runner-host/.env` on the Mac mini hold only `DEVELOPER_DIR` and `LANG`). The runner has no fork-PR exposure: the repo is private.

The CI house-data job (landing in #380) will read the private denylist from the `HOUSE_SCAN_DENYLIST_B64` secret and report a count only; see [house-data-gate](house-data-gate.md).
## Hosted GitHub Actions (owner, 2026-11-07)

Background and sources: `build/research/hosted-ci.md`. The repo is public, so pull-request CI is hosted only; the private job set is gone (2026-11-08). `pr-checks.yml` is the one workflow for pull requests and pushes to `main`; `tool-tests.yml` was folded into it.
