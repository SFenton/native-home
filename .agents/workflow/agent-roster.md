# Agent roster

> **What:** the agent roles, who dispatches whom, the contracts between them (brief, status, task ledger, evidence pack), the autonomy levels that let loops run without the owner, and the Jev questions each role uses. **Read when:** spawning any agent, writing an agent file, changing a hook that judges agent behavior, or wiring an unattended loop.

Owner decision (2026-11-01): roster, autonomy levels L0–L3 and Designer on Opus approved; "aim for autonomy"; macOS is eventual, nothing now (the [2026-10-20 invariant](../../AGENTS.md) stands: design choices must not foreclose a later macOS target, and nobody writes macOS code). Proposal and evidence: S+H Agent Roster (the owner's private mockup gallery, link kept outside the repo). Evidence in one line: in the UIKit port the owner was the QA (about 15 on-device bug rounds), 57 of 62 subagents were coders, none researched, designed or reviewed, and the Opus orchestrator made 676 Bash calls of its own.

Owner decision (2026-11-03, "Approve"): three fixed-set guards go into code: request-repo write rules for headless sessions (no `gh issue edit`, `gh issue create` only with the `Workflow` label), the app-UI gate on product PRs in `tools/pr_land.sh` (with an owner-only `--owner-ack`), and owner-only signing credentials (`signing_guard`). They are listed below under "What code enforces today".

**Researcher memory** lives in `.claude/agent-memory/researcher/` (committed; source catalogue, versions last checked, dead sources), enforced by `research_write_guard`. Main-thread `--agent` sessions do not run frontmatter hooks in our tests (2026-11-01), so role guards (`orchestrator_guard`, `research_write_guard`) live in `.claude/settings.json` and act only when the payload's `agent_type` matches; the researcher's Bash stays read-only by prompt only.

<a id="guards"></a>**Guards.** (1) Before cutting a lane, run `gh pr list --state open --search "<topic words>"` and `git log origin/main -5 -- <paths>`. If another open PR or a recent commit already covers the work, join it (post findings on it) or stop; never open a parallel PR (#309 duplicated #311). (2) A hook block is answered by changing the work or finishing `needs_decision`, never by rewording, renaming or indirect naming to dodge a match, nor by telling an agent to. The one exception: when a Bash guard matched a word inside prose bound for a file, an agent writes that prose with Edit or Write. A block on the path, the role or the action itself is never answered with another tool (a refused spawn, 2026-11-06).

<a id="questions"></a>**Questions (owner, 2026-11-04).** `AskUserQuestion` is used only for an owner-only decision (the L3 fixed set below, an app-wide change the owner did not request, or a gate park). Everything else is decided by the agents and recorded. When the work truly waits on the owner, say so in one line, post the PR handoff note (`tools/pr_note.py` handoff) and go silent; do not repeat the stop each turn.

**One dispatcher.** Only the orchestrator spawns agents that write (Coder, Verifier, Menial). Researcher and Designer are advisors: they return requests (`research_requests`, `implementation_specs`) in their reports and the orchestrator dispatches them. The Researcher has the Agent tool for read-only helpers only (Explore, web-fetch). The Designer has no Artifact tool: when it writes mockups it sets `"hub_republish": true` in its status block and the orchestrator republishes the hub with the mockup-hub skill before it ends (`mockup_hub_guard` sees the Designer's files because they are in the orchestrator's checkout). No per-area, Swift-review, accessibility or release agents: that knowledge lives in skills and scripts.

**Shared simulator tools (owner, 2026-11-04).** devcap, slim, duo-pose and the pose code belong to the private shared simulator-tools repo; a change to them is delegated with `the shared simulator-tools repo's `tools/delegate.sh`` and the task ends `blocked`. See [capacity](../platforms/apple/capacity.md#changing-the-shared-tools).

## Contracts

**Brief** (orchestrator → any agent): objective, output format, tools and sources, boundaries (files it owns, what not to touch), done check, device families. `brief.complete` (Jev, shadow) lints it.

**Status block** (last thing every subagent prints), JSON in a fenced block tagged `status`. The interactive main session does not paste it into chat (owner, 2026-11-04): it writes the same JSON to `build/status/<task>.json` with `tools/agent_status.py write` and prints one prose line of at most 30 words; a headless session writes the runner's status file:

```json
{"status": "done|blocked|needs_research|needs_decision", "task": "T-0142",
 "summary": "<= 250 words", "artifacts": ["build/research/x.md"],
 "acceptance": {"a1": "pass|fail|not_run"}, "question": "only for needs_*",
 "blocked_reason": "only for blocked, e.g. waiting_bg: <label> or slot_wait: <gate>",
 "research_requests": [], "implementation_specs": [], "hub_republish": false}
```

An optional `"repro": {"class": "timing|visual|state", "instrument": "trace|log|unit|screenshot|recording"}` records how a reported bug was reproduced (see Record first below).

A headless session that pushes self-change lanes adds `"lanes": ["agents/<topic>-<date>", ...]` to its status file (the runner's file, not the agent block). The runner reviews and lands each one; the session never does.

The Steward adds `"actions": [{layer, change, test, metric}]` (at most 3) and `"owner_rules_broken": [{"rule": "...", "source_date": "YYYY-MM-DD", "quote": "...", "run": "<task or archive>"}]`, empty when no run broke a rule the owner already gave (question 6). `tools/retro_weekly.py` trends its length: the "errors keep falling" measure.

The `SubagentStop` hook (`tools/hooks/subagent_report.py`) applies to the roster agent types only (orchestrator, researcher, designer, coder, verifier, steward, menial, reviewer); every other agent type passes. It blocks a stop without a parseable block once, then lets it through with a warning (a hook must never trap an agent). It also sends a `coder` back once when it reports `blocked` with more than 20 dirty files in its worktree (the payload `cwd`) and a `blocked_reason` that does not start with `waiting_bg:`: commit a WIP first. An agent that ends a turn with its own `tools/bg_run.py` job still running reports `blocked` with `"blocked_reason": "waiting_bg: <label>"`, and the orchestrator treats that worktree as live.

**Task ledger** `build/tasks/<id>.json` (git-ignored), schema `contracts/task-ledger.schema.json`, CLI `tools/tasks.py new|show|add-check|add-branch|flip|set-level|check|list`. The orchestrator creates entries and adds checks (a check written `id=text` takes that id, `[a-z][a-z0-9_-]{0,15}`, otherwise `a1`, `a2`, ...; so "count=3 tiles" becomes id `count`: reword it or give it an id; the id is printed); agents may only flip `passes` and attach `evidence` (`tasks.py flip T a2 --evidence PATH`); `tasks.py check` exits 0 only when every check passes. Fields: `id`, `intake`, `level`, `brief`, `acceptance[] {id, check, passes, evidence}`, `rounds {design, review}`, `budget {usd, turns}`, `status`, optional `branches[]` (lane branches, recorded with `tasks.py add-branch T BRANCH`; `retro_digest.py` reads their review records from the trusted store).

**Evidence pack** `build/evidence/<branch>/manifest.json`: per pose (`iphone`, `duo-folded`, `duo-unfolded-portrait`, `duo-unfolded-landscape`, `duo-partial-fold`, `ipad-portrait`, `ipad-landscape`, plus rotate-in and rotate-out), the screenshot path, an accessibility-tree dump, test results and failure class (`real|infra|known-flaky`). Skill: [pose-matrix](../skills/pose-matrix/SKILL.md).

**Research note**: answer, evidence (`repo@sha:path:line` or URL plus date read), fit with our patterns, recommendation (follow / deviate / rearchitect), confidence, open questions. Skill: [research-note](../skills/research-note/SKILL.md).

## Autonomy levels

| Level | Covers | Loop does |
|---|---|---|
| L0 invisible | Logic, performance, tests, tooling, pixel-identical refactors | Runs through merge and deploy |
| L1 visible, decided | Parity with the sibling app, applying a rule the owner already set to more surfaces, atlas-conformant fixes | Designer decides within the existing pattern; runs through merge and deploy; before/after goes in the owner digest |
| L2 design | A new visible choice: what is drawn, worded, animated or navigated changes, with no owner decision on record (a new pattern, layout, copy or motion) | **Autonomous (owner, 2026-11-03).** Build up to 3 options, capture screenshots and behaviour on the affected families; the Designer judges from the evidence and records the pick ([propose-first](propose-first.md)); the chosen option lands like L0/L1; the owner may reverse it later. Nothing waits |
| L2 policy | A trade-off with nothing drawn, worded, animated or navigated changing (a timeout, a retry rule, a default of an existing setting: the owner confirmed that clause 2026-11-03) | The Orchestrator writes a decision note `build/decisions/<task>.md` (question, options with what the owner would notice and the cost, recommendation, what is unmeasured), judges it (or has the Designer) and lands the pick like L1. No mockups |
| L3 fixed set | Only the items listed below, and a broad app-wide UI change the owner did not request (the app-UI gate parks it) | Owner only: the loop files a proposal (`needs_decision` with `owner_only`) and never merges it |

**The fixed set (owner, 2026-11-02, changed 2026-11-03, narrowed 2026-11-07).** L3 is only this:

- credentials, tokens, the Jev key and secrets handling (`~/.config/fenton-hass/**`, the Keychain);
- signing: certificates, provisioning profiles and Apple ID/App Store Connect keys, with the release pipeline that uses them (`tools/release/**`, `.github/workflows/ios-release*.yml`; TestFlight upload of every bumped version is autonomous, a step of the hosted `ios-release.yml`);
- physical-device automation;
- the review recorder and the reviewer's identity (`tools/review/**`, `tools/hooks/review_guard.py`, `.claude/agents/reviewer.md`), and every file the release jobs run or import (`tools/devcap.py`, `tools/ci_hygiene.py`, derived by `tools/release_closure.py`), git's own plumbing (`.git/**`, `.githooks/**`), and `ack-base <sha>` / `--owner-ack`, which stay owner terminal actions in code (`ack-verified`, owner 2026-11-10, accepts only a range of squash-merged PRs that passed the live ruleset's required checks, and agent sessions may run it).

**Unlocked (owner, 2026-11-07, end-to-end autonomy).** The owner said: "I want to unblock you from not being able to approve and merge pull requests so that you're able to start autonomously taking this from end to end ... cleaning up the repo, creating a new repo, creating all of the pull request actions ... every single flow running on hosted macOS flows." So these are no longer owner-only: the merge path (`tools/pr_land.*`, `tools/lane_land.py`, `merge_guard`, the runner), the guard hooks and their wiring (`worktree_guard`, `kill_guard`, `commit_guard`, `signing_guard`, `orchestrator_guard`, `ship_guard.sh`, `.claude/settings.json`), the eval graders and thresholds, and the kill-switch code. Agents change them like any tool: **an independent reviewer's `pass` for the exact head is still the gate and no agent lands its own work**; `signing_guard` keeps blocking real key access. Agent files land after an independent review and the owner's CODEOWNERS approval; everything else lands on the review alone (owner, 2026-11-09). The review runs on the pushed head while CI runs (push, then review, owner, 2026-11-10). `pr_land` no longer reads checks at all (2026-11-09): GitHub's ruleset requires `pr-checks` on the head and `ai-review` (from the S+H Reviewer app) on the head, and `pr_land` only arms auto-merge after the gates GitHub cannot run. Agents may create a repo, push a clean snapshot and make it public only behind `tools/go_public_gate.py` (house_scan 0 hits with the local denylist loaded, and gitleaks clean); either gate failing leaves it private. The unlock itself landed as one PR that the owner merged.

Everything else is autonomous after the eval gate and an independent review (owner, 2026-11-02): agent prompts, hooks, skills, tools, Jev questions and these autonomy rules. A change to agents, skills, hooks or Jev questions may not touch evals, labels, splits or thresholds in the same change.

Neither L2 form parks. Live Home Assistant writes left the fixed set: agents change HA through `tools/ha_change.py` (backup, `ha core check`, change log, revert; [ha-operations](../platforms/apple/ha-operations.md)). Only the fixed set and a `gate: park` from the app-UI gate ([propose-first](propose-first.md#the-app-ui-gate-when-the-owner-is-needed): `design.matches_request` for owner-requested work, `design.app_wide` for agent-initiated work, Jev unavailable parks) finish `needs_decision` with `decision.owner_only` (`fixed_set`, `app_wide`, `unmatched` or `gate_unavailable`); the runner then labels the PR and the issue `Needs Decision` and `pr_land.sh` refuses it. A design or policy pick that finishes `needs_decision` without `owner_only` is sent back to be judged and landed. **Defaults:** a change to the default of an existing setting with the same control, look, words and motion is not visible (owner rule, 2026-11-03), unless it changes what a screen shows when it opens.

**What code enforces today (checked against the implementation, 2026-11-03).** Since every repo session starts as the orchestrator (above), the owner's own sessions carry `agent_type` too, so `merge_guard`'s agent-session rules (only the plain `tools/pr_land.sh N`, no `--owner*` words) and `signing_guard` apply to them; owner-only work (signing material, `--owner-ack`) runs in a plain session or the owner's own terminal. A plain session is `claude --agent ""` on the CLI, or, for a desktop-app session, `{"agent": ""}` in that checkout's `.claude/settings.local.json` (local, never committed; probed 2026-11-03: no `agent_type`, Sonnet, every tool). An interactive orchestrator session has only its allow-list: no Browser pane, desktop session, terminal or connector tools. The hooks' docstrings that describe an unblocked plain session still hold for such a session.
- `ack-verified` is the agent-runnable acceptance of a moved base (owner, 2026-11-10: "update rules to allow agents to run these commands and then update"; decision record [ack-verified](ack-verified.md)). `Runner.verify_pr_range` (also what `check_base` uses) accepts `recorded..origin/main` only when every first-parent commit is one-parent, made and signed by GitHub, owned by a merged PR whose `merge_commit_sha` is that commit (`commits/<sha>/pulls`, else `pulls/N` from the subject's `(#N)`), and the PR head passed every check the LIVE ruleset requires, from the integration it names; the ruleset must be live and not edited inside the range (bypass actors are not checked: the agent login cannot read them, and a bypass could only yield a direct push or a failed-check merge, both refused per commit). `merge_guard` blocks it headless and allows only its exact form, from a checkout whose verifier files match origin/<base>; `ack-base <sha>` and `--owner-ack` are unchanged and owner-only.
- The app-UI gate is enforced in code for agent lanes: `lane_land.check_design_record` requires a dated `Decision:` line the lane itself added (or a `Design: <path>` citation of a record or pattern that exists on the base; a file the lane adds does not count), and `lane_land.verify_gate` asks Jev itself in both cases (the lane's `Gate:` line is documentation and must agree). Jev sees the app-UI paths and diff stat first, then only the record lines the lane added. A `Owner-Request:` ref counts only when the runner vouches for it: the session's own issue, from its pickup snapshot (`~/hass-agents/requests/<n>.json`), filed by an allowed author and not `Workflow` or nightly; otherwise `design.app_wide` is asked. Runner-landed lanes are `Workflow` sessions, whose snapshot is refused, so today they are always asked `design.app_wide`. Product PRs get the same check: `tools/pr_land.sh` starts `python3 -I <gate-trusted clone>/tools/lane_land.py gate --pr N` (the PR's base branch under `~/hass-agents/gate-trusted/`, cloned from `https://github.com/<product_repo>.git` in the config, never from the invoking checkout's `origin` remote, and never the invoking checkout's copy; so a PR that edits the gate is still judged by the base copy; its Jev questions and `agent_eval_measure.py` come from there too) after checks and review are green and before the merge. Mockup-only hits do not count (owner, 2026-11-04, "Mockup-only edits that look the same don't count"): under `.agents/design/mockups/**`, `lane_land.rendered_ui_paths` compares each modified file with its base version after `mockup_drawn_form` strips what is not drawn (`*.md` entirely; HTML comments outside `<script>`; `data-cite` and `cite` attributes and `href` on `<a>` only (stylesheet, icon and `<use>` hrefs draw; text inside script strings draws); the mount config's `source`, `spec`, `patterns`, `hig`, `reviews`, `inFlight` and header `status`; `catalog.json` metadata keys; all whitespace). Identical forms are not app UI; a new file, or any difference, keeps today's gate. A PR that touches the app-UI paths needs the design record (or `Design:` citation) and Jev's verdict from trusted code with the lander's thresholds (`>=0.8` yes, `<0.3` no); anything missing, unreadable or unavailable is `blocked`. The request is vouched only by a request-repo issue an allowed author filed and that is not `Workflow` or `Nightly Fix`: a headless (runner) PR by the pickup snapshot of its own issue, as for a lane; an interactive PR by a linked request-repo issue (`Closes #N`, `Owner-Request: #N`). The PR's own text and a product-repo issue never vouch (agents open PRs under the owner's login), with one exception (owner, 2026-11-04, "Count chat requests as yours"): an interactive PR whose body or commit has an `Owner's request: "<quote>"` line counts as the owner's request when the quote (whitespace and case normalised, at least 20 characters) is inside a prompt the owner typed in the last 14 days. The prompts come from the `UserPromptSubmit` hook `tools/hooks/owner_prompt_log.py`, which appends them (with session, cwd, UTC time and SHA-256) to `~/hass-agents/owner-prompts/<YYYY-MM>.jsonl`, mode 600, outside every worktree, and deletes files older than the previous month. It tells the owner's main thread from a subagent by `agent_id` (the main thread carries `agent_type: orchestrator` from the settings, never `agent_id`) and writes nothing under `FENTON_HEADLESS=1`, SSH (`SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY`), a `CLAUDE_CODE_ENTRYPOINT` other than `cli` or `claude-desktop`, `CLAUDE_CODE_SESSION_ATTENDED=0`, a second `claude` above the session's own in the process tree, a session `claude` whose own exec environment (`ps -E`) carries `CLAUDECODE=1` or `CLAUDE_CODE_SESSION_ID` (everything a session starts inherits them, so a detached `(claude -p --agent orchestrator ... &)` is caught; the owner's desktop `claude` has neither; unreadable fails closed), or a harness-injected prompt (opening with `<task-notification`, `<system-reminder`, `<channel`, `<cross-session-message`, `<teammate-message`, `<fork-boilerplate`, `<local-command-`, `<<autonomous-loop` or `[Artifact comment`: scheduled tasks, `/loop`, background-agent reports, side sessions). **This is a tripwire, not a boundary** (agents run as the owner's macOS user): `tools/hooks/owner_prompt_guard.py` (PreToolUse on Bash, Read, Grep, Glob and the edit tools) refuses Bash whose raw text contains `owner-prompts`, a path tool that resolves into the folder (or a Grep or Glob over `~/hass-agents`), globs that can match the folder, Grep or Glob rooted at the home folder or `~/hass-agents`, and a `claude`, `claude-code` or `@anthropic-ai/claude-code` `-p` or `--print` launch (judged per simple command; also via `ssh` or `npx`) without `--agent <role in .claude/agents>`; the runner's deny list in `tools/triage/config.json` carries the folder too; both hooks are protected paths. A path built from variables, an interpreter that opens the file or a renamed `claude` gets past it, as a deliberate act. `lane_land.logged_owner_prompt` does the match outside pasted blocks, fenced code and `>` quote lines, and Jev is asked `design.matches_request` with 600 characters either side of the quote (yes at `>=0.8` still needed); headless PRs never use the log. Otherwise `design.app_wide` is asked, and an interactive owner PR with no request-repo issue uses `--owner-ack`. Headless sessions reach the gate only through `tools/pr_land.sh N [--dry-run]`; `python3 tools/lane_land.py gate --pr N` is for the owner's terminal (`merge_guard` blocks `lane_land` headless). The gate clones are pinned to that origin, serialised by `~/hass-agents/gate.lock` (`pr_land` holds it until the gate process exits; the gate runs from the gate-trusted clone as its own trusted checkout and never re-fetches it) and re-cloned once after a failed fetch. `--owner-ack` skips the gate for one PR and needs the full head SHA typed at `/dev/tty`; it is refused under `FENTON_HEADLESS`, a runner session (`HASS_TRIAGE_ISSUE`) or a non-terminal stdin. Detection, not prevention (owner, 2026-11-02: agents run as the owner's macOS user), so `merge_guard` makes every route need deliberate evasion. For headless sessions and for any session whose payload carries `agent_type` or `agent_id`: `pr_land` runs only as exactly `tools/pr_land.sh N [--dry-run]`, and only when the checkout's `tools/pr_land.sh` and `tools/pr_land.py` equal `origin/<product_base>` or `origin/<workflow_base>` (an edited copy, a missing ref or a git error refuses), any `--owner*` word given to `pr_land`/`lane_land` is refused, `env -u/-i`, `unset` or an assignment that changes `FENTON_HEADLESS`/`HASS_TRIAGE_*` is refused, `script`/`expect`/`unbuffer`/`tmux` around `pr_land`, `lane_land` or `ack-base` is refused, the deny list has `Bash(*owner-ack*)`, and every parser of `pr_land.py` and `lane_land.py` has `allow_abbrev=False` (`tools/lane_ship` has no parser: `ship.sh` is shell).

- GitHub App keys and tokens are owner-only in code too (owner, 2026-11-04), as **detection, not prevention**: `signing_guard` (now also registered for Glob) scans the raw text of an agent's Bash command for `github-apps`, `.pem`, `fenton-hass` under `.config`, wildcard or quote tricks in a `.config` path, token variables, literal `ghs_` tokens, environment dumps, `gh auth token` and `git credential`; it resolves file-tool paths (symlinks, case) and refuses the `fenton-hass` config folder, its ancestors up to `~/.config`, and `*.pem`. It is a tripwire, not a wall: a symlink to home plus wildcards, and dynamic path construction (variables, encoded text, scripts), can still evade it; the stronger boundary would be a separate macOS user owning the keys plus a token broker (future option). The unattended deny list repeats the Read/Edit and Bash rules, and `tools/redact.py` masks tokens and multi-line PEM blocks. See [auth](../platforms/apple/auth.md#agent-github-app-keys-owner-only).
- Ship safety is split out of `tools/ship.sh` (owner, 2026-11-04, "Approve for the ship.sh updates"): `tools/ship.sh` calls `tools/ship_guard.sh` after `git add -A` (secrets) and before the commit and the push (branch); `tools/hooks/commit_guard.py` (PreToolUse Bash, every session, registered in `.claude/settings.json`) runs the same guard on a raw `git commit`/`git push` (resolving `cd`/`git -C`), refuses `git commit --no-verify`/`-n`, and ignores read-only git and the words inside quotes, comments and heredocs. The tests run on a temporary merge of the lane into the base the trusted side just fetched (a lane cut before the base gained tests is not undercounted; a conflict fails the landing, kind `conflict`). The rerun's trusted side runs after lane code has run once (a weaker ordering; detection, not prevention). The safety net is `.github/workflows/pr-checks.yml` (`tool-tests-core` and `linux-checks`; `tool-tests.yml` was folded into it): the full `tools/run_tool_tests.sh` runs on a hosted runner after every push to `main` and fails visibly and, on a red run, files or updates one `Workflow` issue naming the head SHA and the failing tests (job `GITHUB_TOKEN`, `issues: write` only); the nightly does not run the tool suite. When unsure between two levels, take the higher. Jev `design.user_visible` and `design.new_pattern` may raise a level, never lower one.

## The loop

Route (rules, then Jev `route.role` as a hint) → ledger → design brief (visible work) and rung-0 research (custom machinery) → Coder → Verifier evidence → design verdict (≤ 3 rounds) → Reviewer (≤ 2 rounds) → `pr_land.sh` → version bump and TestFlight (Duo Release install when the owner is reachable) → post-mortem (the Steward procedure below) → one-line report. Triage lands L0, L1 and L2 through `pr_land.sh`. Stops: all checks pass and review passes (land); design rounds > 3 or a blocker after review round 2 (the Designer picks the best built option and records it; `Needs Decision` only for owner-only items); genuinely blocked (infra, an owner-only item, a slot wait over 20 minutes): `Blocked` plus `build/handoff/<topic>.md`; infra failure twice (report as infra). **Advisor briefs carry a done check:** before dispatching a Researcher or Designer, the Orchestrator adds a ledger check for their work, as it does for the Coder.

**Post-research gate.** The plan the gate reads starts with the owner's request in their words, then the result they named (if any), then what research found, then only the choices that remain; a plan that lists every option as open reads as undecided (measured: the same case scored 0.07 written as options A to D and 0.56 written target-first). After rung-0 research the Orchestrator answers one question: does any option change what is drawn, worded, animated or navigated?

| Visible | Already chosen | Owner pick | Next step |
|---|---|---|---|
| no | n/a | no | Coder (L0) |
| no | n/a | yes | decision note, then Coder (L2 policy) |
| yes | yes | no | Designer spec within the existing pattern, then Coder (L1) |
| yes | yes | yes | decision note for the remaining choice plus a Designer spec |
| yes | no | any | Designer options and mockups (L2 design) |

Unsure on any needed answer: a **Designer verdict** brief first (verdict only: visible yes or no with the reason, at most 10 tool calls, no mockups) before any full design.

At the gate run `python3 tools/jev_gate.py --plan-file <plan> --subject <task>`. It asks `design.user_visible`, `decision.needs_owner` and, for a visible plan once its question file exists, `design.target_decided` ("already chosen"), and prints the raise-only lines (a visible hint sends the work to the Designer, a pick hint makes it L2) and then a route hint from the table, `Jev route (hint, the orchestrator decides): ...`, or `Jev: no route hint (unsure)`. "Visible", "chosen" and "pick" mean an accepted yes (not the unsure band). A Jev route that would move work down (L2 design to an L1 spec) is a hint only; the orchestrator decides. Jev never lowers a level by itself, and silence never skips the Designer or lowers a level. For a plan not read as invisible it also prints the app-UI gate and a last `gate: autonomous|park ...` line ([propose-first](propose-first.md#the-app-ui-gate-when-the-owner-is-needed)); a visible or pick hint no longer parks anything by itself, only that gate (or the fixed set) does. A missing or empty `--plan-file` exits 2 with `jev_gate: cannot read <path>`.

**Record first, with the right instrument** (owner-approved 2026-11-03, after a camera run used a screen recording for a timing bug and repeated 34-minute device rounds). Pick the instrument by the class of the report, and reproduce from the cheapest one first (a unit repro or log before a trace, a trace before a device recording):

| Class | Instrument |
|---|---|
| Timing, lifecycle, reconnection, ordering | signposts, `os_log` or a trace with timestamps ([performance](../testing/apple/performance.md)); a recording cannot show a missed deadline |
| Visual, layout, motion look | screenshot or recording (`UK_RECORD=1 tools/uikit_shot.sh` in the UIKit port, or the journey screenshots) on the reported device families |
| State, logic, data | logs or a unit repro |

The Verifier records today's behaviour this way before research concludes a cause, and states what it used in an optional status field `"repro": {"class": "timing|visual|state", "instrument": "trace|log|unit|screenshot|recording"}`; `tools/retro_digest.py` flags `wrong_instrument` when a timing class used a screenshot or recording.

## Post-mortem and follow-up

At the end of every flow the orchestrator runs `python3 tools/retro_digest.py --task T`. A trigger (blocked, timeout or retry, review rounds over the cap, an owner correction, a routing override, waiting narration at the end, budget over, a slot wait, a stop with live children, a tool error class, an empty test run, repeated 30-minute device rounds, a recording used for a timing bug), or work that touched agent or workflow paths, starts the Steward's Entry A. A lane with no ledger task (an interactive subagent flow) uses `python3 tools/retro_digest.py --lane NAME` instead, built from its `build/runs` digests, `build/review/<branch>.json` and commits. The procedure is in [steward](../../.claude/agents/steward.md): six questions, "improvements needed?" (yes only for a recurrence of two or a single serious incident), then at most 3 actions, each with layer, exact change, proving test and metric. Rule 6 is the measure that errors keep falling: did a run break a rule the owner already gave. Each owner course correction becomes a cited rule in its `learning.home`.

<a id="follow-up"></a>**Follow-up.** Each action becomes a lane: a Coder commits it on a branch `agents/<topic>-<date>` cut from the workflow base (`workflow_base` in the triage config, default `main`, the same as the product base), with the touched tests and the eval gate (`tools/agent_eval.py`, [eval-gate](eval-gate.md)) run.

- **Headless** (retro, the weekly Steward job, a `Workflow` issue): the session pushes only the lane (`git push origin agents/...`; a headless hook blocks any other push) and lists it in its status file as `"lanes": [...]`. It never merges, never runs `lane_land.py` and never writes a review verdict for its own lane. The runner then launches the independent Opus Reviewer itself and checks the verdict for the exact commit, the kill switches, the protected (fixed-set) paths and its own fixed test run; it merges `--no-ff` and pushes. A refused lane comes back as a `Workflow` + `On Hold` issue.
- **Interactive**: the orchestrator may run `python3 tools/lane_land.py <branch> --into <workflow base>`. It enforces the same checks, with the reviewer's verdict in `~/hass-agents/reviews/`.

A self-change without a `pass` verdict for its exact head cannot land; any later commit voids the verdict. A self-change is landed by the runner, never by a pull request. Product work still lands only through `tools/pr_land.sh`. Over the bound, failing twice, or in the fixed set: filed as a `Workflow` issue with the spec; a fixed-set proposal also gets `On Hold` (the runner skips it), the rest the runner picks up on idle ticks (Steward entry B, as lanes). Nothing is dropped. Kill switches: `~/.config/hass-triage/PAUSED`, `~/.local/state/hass-triage/PAUSED`, `SELF_CHANGE_PAUSED`; any of them stops all self-changes.

## Safety net (plan section 9)

- **Automatic revert.** The runner records each lane it lands with the section 11 metrics of the flows before it. After the next 10 flows (or 14 days) it compares the same metrics; if two or more are worse by more than 20% (`revert_margin`) it lands `agents/revert-<sha12>` (`git revert -m 1`) through the normal review and files a `Workflow` issue saying which regressed. A revert of a revert is never automatic: an `On Hold` issue instead. Details: [triage-agent](triage-agent.md), "Automatic revert".
- **Kill switches** are visible in `hass_triage.py status`: which are on, why, and the pending `ack-base` SHA.
- **Bloat budgets**, enforced by `tools/tests/test_bloat.py`: an agent file at most 55 lines, `steward.md` 50, a pattern doc 125, `AGENTS.md` 50 (the code is the truth: `AGENT_FILE_BUDGET`, `STEWARD_BUDGET`, `AGENTS_MD_BUDGET`). Changes are small numbered additions; a file over budget is trimmed or split before it grows. The same test is the contradiction check: the design and review round caps, the kill-switch paths, the L3 items and the merge path must read the same in every agent file and here.
- **Weekly prompt audit.** The weekly Steward job runs a prompt audit (the `claude-api` skill's prompt-audit, if available) over `.claude/agents/*.md`, `.agents/workflow/*.md` and `tools/triage/prompts/*.md` and turns at most 3 findings into lanes.
- **Durable owner rules.** `owner_rules_broken` entries (`{rule, source_date, quote, run}`) are listed by `retro_weekly.py` with their source date and quote and counted per rule; the weekly digest leads with any rule broken twice.
