# Triage agent (MacBook)

> **What:** how in-app bug reports and feature requests become merged changes: the private request repo, the runner on the MacBook, labels, owner commands and safety. **Read when:** changing `tools/triage/**`, the feedback form's filing, or diagnosing why a request wasn't picked up. Ported from FestivalNativeApps' release machine (`SFenton/the private sibling triage project`), cut down to one host and one issue at a time.

## Flow

1. **Intake.** Settings → Feedback → Report an Issue / Request a Feature ([feedback form](../pages/settings/feedback.md)) sends the report through Home Assistant's [Fenton Home Feedback](https://github.com/SFenton/ha-fenton-feedback) integration, which holds the owner's GitHub token and files an issue in the **private** request repo (so issues are authored by `SFenton`): labels `Bug`|`Feature`, `From App`, `iOS`|`iPadOS`|`iPhone Duo`, media as GitHub user attachments, a diagnostics table naming the Home Assistant user, and the marker `<!-- fenton-feedback:v1 -->`. Issues typed on GitHub by the owner are worked the same way. Private because screenshots show the house.
2. **Pickup.** launchd runs `tools/triage/hass_triage.py tick` every minute (`com.sfenton.hass-triage`), so a report is picked up within about a minute of being filed. Like FestivalNativeApps' machine (a one-minute tick, plus a controller polling GitHub every 15 s for queued intake jobs), the Mac reaches out to GitHub; nothing reaches into it. An idle tick costs a handful of GitHub API reads. A tick takes a lock, refreshes its own clone (`~/hass-agents/repos/<private-app-repo>`, never `~/repos`), finishes merged work, checks parked pull requests, re-queues issues the owner answered, then works open issues by an allowed author (`SFenton`), `Priority` first, then oldest, one at a time until none are left (10 h budget).
3. **Work.** Before the first launch of a tick the runner runs **`claude auth status`** once; when the CLI is logged out it prints `claude is not logged in; run claude auth login` and stops the tick without touching any issue (no labels, no attempts; `status` shows it too; nothing is cached across ticks). Per issue: label `In Progress` (a label missing on the repository is created from the config table and the edit retried once, so a missing label never stalls a tick), a pickup comment, media downloaded to `~/hass-agents/work/<n>/media`, a worktree `~/hass-agents/worktrees/<n>` on `report/<n>` from `origin/main`, the task-ledger entry and route (below), then `claude -p --agent orchestrator` (Fable 5.2, effort medium, **auto** permission mode, deny list in `tools/triage/config.json`; `agent.agent` in `~/.config/hass-triage/config.json` set to `""` turns the playbook off only while the worktree's base lacks `"agent": "orchestrator"` in `.claude/settings.json`; once the base carries it the worker starts as the orchestrator anyway, so name another agent to change it) with [prompts/worker.md](../../tools/triage/prompts/worker.md), which carries a Jev *Pre-read* of likely patterns when there is a key (the key file `~/.config/fenton-hass/typesafe.key` (or `TYPESAFE_API_KEY` when there is no file), set in the runner's environment) ([decision-models](decision-models.md); `jev.enabled` in the config, empty otherwise). The session is the **orchestrator** ([agent-roster](agent-roster.md)): it routes, keeps the ledger, writes briefs and dispatches `coder` (code and tests in the same issue worktree), `verifier` (journeys on iPhone, Duo and iPad, the evidence pack), `designer` (visible work), `reviewer` and `menial`; it never builds or tests itself (the `orchestrator_guard` hook refuses it; `pr_land.sh`, `hass_triage.py comment|upload`, `gh pr create` and `tools/tasks.py` stay allowed). It triages, posts root cause or approach, gets the work reproduced, fixed and tested, opens a PR and writes `~/hass-agents/status/<n>.json`. `caffeinate` keeps the Mac awake; a 5 h timeout stops it.
4. **Hand-off.** A `done` status with `tests_passed` and an open PR: the runner labels the PR `Ready to Merge`, the issue `Merging`, and comments the summary. The worker lands its own PR through `tools/pr_land.sh` (owner, 2026-10-28; [pr-lifecycle](pr-lifecycle.md)); only a PR the gate blocked stays open for the owner. Once the PR is merged the next tick posts the *Resolved* summary (cause, fix, tests, screenshots), labels `Done` and closes the issue. A PR labelled `Merge Failed` or closed goes back to `Blocked`.
5. **Park path (owner-only items).** L2 does not park (owner, 2026-11-03): for a design pick the worker builds up to 3 options, the Verifier captures screenshots and behaviour, the Designer judges and records the pick ([propose-first](propose-first.md)), and the worker lands the chosen option like L0/L1; a policy pick is judged by the orchestrator the same way. Only an owner-only item parks: the fixed set, or a `gate: park` from the app-UI gate (`tools/jev_gate.py`, [propose-first](propose-first.md#the-app-ui-gate-when-the-owner-is-needed): an owner request Jev cannot confirm the change matches, agent-initiated work that is app-wide or unsure, Jev unavailable). The worker finishes `needs_decision` with `decision.owner_only` set to `fixed_set`, `app_wide`, `unmatched` or `gate_unavailable`. When `pr` is an open product-repo PR the runner labels the **PR** and the issue `Needs Decision`, posts the options with the PR link, marks the PR ready if it is a draft, records it in `state.json` under `parked` and leaves the worktree. A `needs_decision` with an open PR but no `owner_only` is not parked: the runner records `retry` ("design pick not judged"), and the next run is told to judge and land the pick; when attempts run out the issue is blocked `pick_not_judged`. `tools/pr_land.sh` refuses a PR labelled `Needs Decision`. Each tick `check_parked` finishes the issue when the PR is merged (the owner accepted it), blocks it with `pr_closed` when it is closed unmerged, and otherwise leaves it parked however long it takes (no timeout block, one log line past `merge.wait_hours`). An owner reply is a pick or a question/comment: `requeue` drops the parked entry, takes `Needs Decision` off the PR, and the next run is told which. A question is answered with a `--kind decision` comment and the run finishes `needs_decision` again with the same `pr`. If the reply comment has since been deleted, the stored pick is cleared and the run starts without it. L0, L1 and L2 never park: they take or judge the pick, post a `decision` comment and land.
6. **Other outcomes.** `no_changes` closes as not planned (`No Changes`); `split` files child issues and closes the parent (`Split`); `needs_decision` without an open PR labels `Needs Decision` with the options and waits for a reply; `blocked` labels `Blocked`. A session that ends without a status is retried once, then blocked with the redacted log tail.

## The request repository (local setting)

The name of the private request repository is never in this repository. `tools/request_repo.py` resolves it, first match wins:

1. the environment variable `FENTON_REQUEST_REPO`;
2. the first line of the file `request_repo` in the owner's `~/.config/fenton-hass/` folder (plain text, one line, `owner/name`);
3. a non-empty `request_repo` in `tools/triage/config.json` or in the runner's own `~/.config/hass-triage/config.json` (the committed file leaves it empty).

With none of them the repository is **not configured**, and the system fails closed: `hass_triage.py` exits with status 2 and a message naming
the setting before it touches GitHub, `lane_land` counts no linked request, and `merge_guard` refuses every guarded `gh issue`, `gh label`
and `gh repo` write and every non-GET `gh api` call in a headless session, against any repository (it cannot tell which one is the request
repository). Tests pin a neutral `example/private-requests` through the environment variable. The owner creates the setting once per machine;
agents never read or write that folder.

## Owner commands

| To | Do |
|---|---|
| Retry a `Blocked` issue, or answer a `Needs Decision` one | Reply on the issue (`/retry`, or your choice); the next tick re-queues it with your reply in the prompt |
| Pick for a parked PR | Reply on the issue with your pick (the agent builds it on the same PR), or **merge the PR** to accept the recommendation; close the PR to stop (`Blocked`, `pr_closed`) |
| Jump the queue | Add `Priority` |
| Keep the agent away | Add `On Hold` |
| Send a merged fix back | Reopen the issue; it is worked as a follow-up with the earlier comments |
| Send an unmerged PR back | Label the PR `Merge Failed` |

## Task ledger and route (shadow)

After the worktree is ready the runner creates `build/tasks/R-<n>.json` (`N-<n>` for nightly) in it with `tools/tasks.py new` (a rerun keeps the entry; a worktree without `tools/tasks.py` skips this silently). Level from rules: `Bug` L0 (L1 when the text reads as UI), `Feature` L1, nightly L0; the worker may raise it (at the post-research gate with `tasks.py set-level`, to L2 design or policy), never lower it. Default checks: unit tests, journeys on the affected families, reviewer verdict recorded, owner-visible summary posted. The prompt gets `{{TASK}}`, `{{LEVEL}}` and `{{ROUTE}}`. The route is `researcher` first for a `Feature` (the post-research gate then decides design, policy or spec), `coder` for a bug and for nightly, stored in the ledger `route` with Jev's `route.role` answer recorded beside it (`jev.enabled`; the prompt shows the rule route only, a shadow answer is never shown to the worker ([decision-models](decision-models.md)); title and redacted body only; never asked for nightly issues; null when there is no key or on any error; logged to `build/jev/shadow.jsonl`). On a `done` status the runner runs `tasks.py check` and writes `ledger: k/m checks pass` into `state.json` and the result comment. It does not gate: `ledger.enforce: true` in the config would block an incomplete ledger with `ledger_incomplete`.

## Jev intake raise

Before it starts a request (never a nightly item), the runner asks Jev `design.user_visible` v2 about the issue's title and body (redacted). A yes at p>=0.6 raises an L0 request to L1: the ledger is created at the rule level and raised with `tasks.py set-level` (so `level_history` records it), and the prompt's route line says so. A no, the unsure band, a missing key or an API error changes nothing. A rerun keeps the ledger's higher level and does not ask Jev again. Every answer is appended to `build/jev/gate.jsonl` for re-measurement. Measured on the decision-gate corpus: request text AUC 0.925, a yes at p>=0.6 right 44 of 45 ([measurements](../../contracts/jev/derived/measurements.md#decision-gate-corpus-2026-11-02)).

## Known limitation: the SwiftUI app on `main`

The runner bases every request on `main`. The UIKit port landed on `main` on 2026-11-05 (#308), so there is no longer a separate port branch to hold requests for.

## Scheduled jobs

`schedules` in the config (`steward`, `researcher`, every 7 days) run from the request runner's tick only when the request and nightly queues are empty (an error reading the nightly queue counts as not idle; the tick still saves state and the nightly intake still runs), nothing is working and the `PAUSED` file is absent, at most one per tick: worktree `~/hass-agents/worktrees/job-<name>` on `agents/<name>-<YYMMDD>` from `origin/<workflow_base>`, `claude -p --agent orchestrator` with [prompts/steward.md](../../tools/triage/prompts/steward.md) or [prompts/researcher.md](../../tools/triage/prompts/researcher.md), and the same status file (`done | no_changes | blocked`). The Steward reviews the last 7 days (reviews, logs, outcomes, token digests, Jev shadow log), files `Workflow` issues on the product repo (deduplicated), runs `tools/jev_measure.py` where labels exist and acts on at most 3 actions per post-mortem. Agents, hooks, skills, tools and Jev questions are autonomous after the eval gate and an independent review (owner, 2026-11-02) and ship as lanes (`agents/<topic>-<date>`) that the runner reviews and lands, as under Post-mortem queue; only the fixed set (credentials and the Jev key, signing, physical devices, live HA writes, the merge path and its guard hooks, eval graders and thresholds, the kill switches) is owner-only, filed as a `Workflow` + `On Hold` issue the runner skips. The Steward's own weekly run is never itself post-mortemed. The Researcher re-checks its source catalogue (HAKit, Home Assistant frontend and websocket API, Apple HIG and SwiftUI notes for iOS 17+, FestivalNativeApps tooling), writes `build/research/weekly-<date>.md`, lands memory updates as an L0 PR and files product implications as `Workflow` issues, never code. Each job has its own `timeout_minutes` (default 60, not the worker's 300), so a weekly job cannot hold the intake for hours. A job the runner has never seen records `last_run = now` on first sight and runs after `every_days`, never right after a merge. Before launching, the runner ensures the `Workflow` label exists on the product repo (best effort). Every ending of a worker (done, blocked, needs a decision, no changes, split, retry, timeout, worker failure) and `cleanup` archive the issue's evidence to `~/hass-agents/archive/<request|nightly>-<n>/` (best effort; an archive failure never fails a tick), because the Steward's own worktree holds none of it: `build/review/*.json`, `build/tasks/*.json`, `build/retro`, `build/handoff/*.md`, the `bg_run` digests, `build/jev/shadow.jsonl` and `gate.jsonl`, the status file, the last 400 lines of the worker log and the owner's reply. Every archived file goes through `tools/redact.py` (JWTs, Bearer and Authorization values, credentials in URLs, `token=`/`key=`/`password=` parameters, `sk-`/`ghp_`/`github_pat_` tokens, `TYPESAFE_API_KEY`/`FENTON_HASS_TOKEN`/`FENTON_HASS_PASSWORD` values, long hex or base64 runs), never a plain copy. After each ending the runner runs `tools/retro_digest.py --archive` on the archive and writes `retro/<task>.json` (no LLM; it lists the triggers that fired and the evidence, and the Steward reads it). Its prompt gets absolute paths for the archive, the clone's `build/jev/shadow.jsonl` (the runner's `route.role` log), `~/hass-agents/logs` and `state.json`. `state.json` keeps `jobs.<name> = {last_run, outcome}`; a failed job is logged and retried next week and never blocks issues; `status` shows each job's next due time (`after first idle tick + 7d` for a job not seen yet); `run-job NAME` runs one now.


## Post-mortem queue (retro)

Every ending of a worker or nightly flow archives its evidence and runs `tools/retro_digest.py`. A digest trigger, a `phase_cost` in `retro/phase-N.json` (the runner runs `tools/retro_phase.py --pr N` for the flow's PR, read from the archived status file, best effort), or a flow that touched `.claude/agents`, `.agents/workflow`, `tools/hooks`, `tools/triage` or `contracts/jev`, queues the archive for a post-mortem in `~/.local/state/hass-triage/state-retro.json` (one entry per archive, shared by the request and nightly runners, capped, finished entries kept). The runner is the only place that queues one: the worker and nightly prompts do not run the Steward themselves, and the weekly Steward job is archived with no post-mortem of itself (`enqueue=False`), as is a retro.

`run_retro` runs only on an idle tick, one at a time (the queue is empty of work, nothing is running, no `PAUSED` file): the oldest entry gets a worktree branched from `workflow_base` on origin (config, default `main`; if the branch is not on origin the queue waits) and `claude -p --agent orchestrator` with [prompts/retro.md](../../tools/triage/prompts/retro.md) (`retro.timeout_minutes`, default 90). The orchestrator dispatches the Steward, then a Coder per action (at most 3), who commits on a lane branch `agents/<topic>-<date>`; the session pushes only that lane and lists it in its status file as `"lanes": [...]`. It never merges, never runs `lane_land.py` and never writes a review verdict for its own lane.

**App-UI gate in the lander.** For a lane that changes app UI, `lane_land` asks Jev itself (trusted `jev_ask`, fresh `JEV_HOME`, before any lane code runs) rather than trusting the record's `Gate:` line: `design.matches_request` (p>=0.8) when a commit carries `Owner-Request: <ref>`, else `design.app_wide` (p<0.3); Jev unavailable or a contradicting `Gate:` line refuses with kind `gate`, filed `Workflow` + `On Hold`. The runner vouches only for the session's own request snapshot (`~/hass-agents/requests/<n>.json`, taken at pickup), and lanes are landed for `Workflow` sessions, whose snapshot is refused: today every runner-landed lane is asked `design.app_wide`.

**Landing (the runner merges).** Agent sessions run as the owner's macOS user with the owner's git and GitHub credentials, so no hook can fully stop a push. The design therefore makes the **runner** the only trusted actor and adds detection. After a session ends, the runner kills the session's whole **process group** (every agent session, the reviewer and the test run start in their own group via `start_new_session`; the group is SIGKILLed and checked gone before any landing step; a survivor makes the lane wait, or files it `Workflow` + `On Hold` when it is the reviewer or the tests). Then for each lane: (1) in the land clone, git runs with hooks, fsmonitor and ssh command overridden and the clone scrubbed (`clean -ffdx`, hook scripts removed); (2) the lane's diff against `origin/<workflow_base>` is refused (kind `paths`, `On Hold`) when it touches the fixed set: the built-in list in `tools/lane_land.py` `DEFAULT_PROTECTED` (merge path and guard hooks, `shell_parse.py`, `agent_model.py`, `tools/release/**`, everything the runner imports from the repo (including the Jev `tools/jev_*.py` modules and `contracts/jev/derived/{measure,baselines}.py`), `tools/triage/*.py`, `config.json` and `tests/**` (the prompts under `tools/triage/prompts/` stay autonomous), `.claude/settings*.json`, the reviewer agent, `.gitmodules`, `.git/**`, `.githooks/**`, workflows, signing and credentials scripts, eval graders and rubrics: `evals/**/*.py`, `schema.json`, `README.md`, and the tier-2 budget `config.json`; the eval harness `tools/agent_eval.py` and its shim `tools/agent_eval_case.py`; `tools/retro_weekly.py`, which holds the revert decision. A test computes the import closure of the runner, the lander, the eval harness and the hooks and fails on any repo module in it that is not protected) unioned with `protected_paths` in the config; modifies or deletes anything in an append-only tree (`contracts/jev/derived/{labels,scenarios,results}/**`, `evals/**/cases/**`); changes Jev question thresholds in the loosening direction (`accept.yes_above`, `accept.min_confidence` and `target.precision` may only rise, `accept.no_below` only fall, `mode` `shadow` to `active` only with changed `evidence`, new questions start in `shadow`); moves a case into `retired/` without a checked `retired/<name>.reason.json` (`kind` `target_removed` with a path gone at the lane SHA, `duplicate` with an existing survivor at least 0.9 similar, `owner_rule` with a date and quote, or `mislabel` with a blind-relabel file the lane adds; and never in a lane that also changes the questions or eval runners); or changes agent behaviour (agents, skills, hooks, Jev questions) and evals or labels together; (3) the **independent reviewer** runs in a *trusted* checkout of `origin/<workflow_base>` (`~/hass-agents/trusted/<repo>`, scrubbed, with `.claude/settings.local.json` deleted, so the lane cannot edit the reviewer or its hooks), is given the lane diff as a file outside any clone plus read-only access to the lane through `git show <sha>:<path>`, and its **verdict is parsed from its own final message** (the last fenced `json` block, `head` equal to the SHA, `pass` with no major or blocker finding; format in `.claude/agents/reviewer.md`). The reviewer's stdout goes to an unlinked temp file only the runner holds (then copied to the log), so no stray process can append a verdict. The diff and lane files are **untrusted data**: text in them aimed at the reviewer is never followed and is itself a `blocker` finding (`prompt-injection`); the runner also rejects a `pass` that carries a finding whose `rule` is `prompt-injection` (a finding that merely mentions the words, such as a diff that tests injection handling, does not refuse), and the reviewer launch denies `git push`, `hass_triage` and `lane_land`. The file under `~/hass-agents/reviews/` is a record the runner writes afterwards, never an input; (4) the kill switches; (5) the fixed commands, with output captured: first the eval gate (`tools/agent_eval.py` run **from the trusted base checkout** against the lane's clone, in a freshly reset checkout that has run none of the lane's tests; each case runs the lane's code in a separate `python3 -I` process and the comparison happens in the trusted parent; see [eval-gate](eval-gate.md)), then the test command in the land clone at the SHA, no bytecode written and no bytecode written: the set of failing or erroring test ids (`FAIL:`/`ERROR:` lines) must be a subset of those of the same command in the trusted base checkout, so failures the base already has never block a lane but a new one does (the refusal names it), and the suite and test counts must be at least the base's (failing ids and counts cached per base SHA in the runner's state), so a lane that adds a module exiting at import (`sys.exit(0)`, `os._exit(0)`) is refused with kind `tests` and both counts; then `git merge --no-ff` and a plain (never forced) push of the workflow base. The runner records `origin/<workflow_base>` (`ls-remote`) at the start of the landing and checks it again after the review and tests, right before the merge and right before the push: any difference aborts the landing (kind `base`, nothing merged), the monitor pauses, and an issue is filed. The merge's first parent must equal the record. Lanes belong to the session: before a retro, Steward/Researcher job or Workflow-issue worker starts, the runner records `git ls-remote origin 'refs/heads/agents/*'`, and afterwards only a listed lane that is under `agents/` and new or moved since that snapshot is landed; any other is filed `Workflow` + `On Hold` with kind `lane` ("not pushed by this session"). A refused lane comes back as a `Workflow` (+ `On Hold` for the fixed set) issue; lanes past the limit are filed too. A hook blocks any headless push except `agents/...` and any merge of the base, but hooks run from the agent's own worktree, so they are not relied on. Interactive orchestrators may use `python3 tools/lane_land.py`, which enforces the same checks with a verdict file a human reviewer left in `~/hass-agents/reviews/`. Product work still lands only through `tools/pr_land.sh`.

**Base-integrity monitor.** The runner keeps the last SHA it landed (or first saw) for `origin/<workflow_base>` in `~/.local/state/hass-triage/workflow-base.json`. At the start of every tick and before and after each landing it compares `git ls-remote` with that record. If the base moved to anything the runner did not land (an agent push, or the owner's own), it writes `SELF_CHANGE_PAUSED` with the reason and files a `Workflow` + `On Hold` issue naming the SHA, its author and committer and the diff stat. It never resets or force-pushes. `ack-base <sha>` is **owner-only**: it refuses when `FENTON_HEADLESS=1` or `HASS_TRIAGE_ISSUE` is set or stdin is not a TTY, needs a pending `SELF_CHANGE_PAUSED` and the exact current SHA, and is blocked for headless sessions by `merge_guard.py` and the deny list. The SHA that **first** tripped the pause is stored beside it (`SELF_CHANGE_PAUSED.json`) and never overwritten while the pause lasts; every later unexpected move is appended to its `moves` list (and gets its own issue), and `status` and the pause text list them all. `ack-base <sha>` must name the current origin SHA **and** the pause must already list every move up to it: if origin moved since the pause last looked, the move is added to the list and nothing is accepted. A successful ack prints every move, so one ack never silently absorbs a second one. After checking the change, the owner runs `python3 tools/triage/hass_triage.py ack-base <sha>` in a terminal. `status` shows whether self-changes are paused, by which switch, why, and the pending `ack-base` SHA. If `workflow_base` is not on origin at all, the lanes and post-mortems would wait silently, so the runner files one `Workflow` + `On Hold` issue per process saying so. Since 2026-11-05 `workflow_base` is `main`, the same as `product_base` (owner: "Main, fix runner"), so merged product pull requests move it too. When the workflow base is the product base, a move the runner did not make is accepted (the record is updated, no pause, no issue) only if the recorded SHA is an ancestor of the new one and every first-parent commit in between (at most 200) is the merge commit of a merged pull request into that branch on the product repo (`gh api repos/<repo>/commits/<sha>/pulls`: `merged_at` set, `base.ref` equal to the branch, `merge_commit_sha` equal to the commit). A direct push, a force push, a longer walk or a failed lookup (retried once) pauses as above; no answer is never taken as a PR. When the two bases differ the monitor behaves exactly as described. The monitor also fires when the owner (or an interactive `tools/lane_land.py` landing) moves the base, so acknowledge those the same way. The runner checks the base again after each landing and a failed push.

**Kill switches.** `~/.config/hass-triage/PAUSED` (the runner's `pause`), `~/.local/state/hass-triage/PAUSED` and `~/.local/state/hass-triage/SELF_CHANGE_PAUSED`. Any one stops self-change landings and the revert check (`SELF_CHANGE_PAUSED` is also what the base-integrity monitor writes), and the runner's `PAUSED` also stops retros. The Steward then writes the note and no actions. (`build/retro/PAUSED` is not a kill switch: `build/` is git-ignored and absent from worker worktrees.)

**Automatic revert (plan section 9).** Every merge the runner makes is recorded in `~/.local/state/hass-triage/landings.json` as `{lane, merge_sha, base, landed_at, metrics_before}`, the metrics being `tools/retro_weekly.py`'s over the 10 flows before it (`revert_flows`). On an idle tick, once 10 flows have finished since it (or `revert_days`, 14, passed with at least `revert_min_flows`, 3), the flows after are compared with the flows before on six per-flow metrics: owner corrections per task, flows needing a nudge, routing overrides, tokens per task, review findings per PR and owner-rule repeats. Two or more worse by more than `revert_margin` (default 0.2; from zero any rise counts) make the runner cut `agents/revert-<sha12>` from the base with `git revert -m 1`, push it (a plain push) and land it through the normal `land_lane`: independent review, tests, protected paths, kill switches, the base record. It records the SHA it pushed in `landings.json` (`revert_sha`) and lands the branch only while origin's tip equals it; a pre-existing `agents/revert-<sha12>` the runner did not push (or whose tip differs) is refused and filed `Workflow` + `On Hold`. A failure while preparing the revert files an issue and never crashes the tick. It files a `Workflow` issue naming the metrics. It never force-pushes and never bypasses `lane_land`. A revert that conflicts, or whose lane is refused, is filed (`On Hold` for a conflict). A revert that itself regresses is not reverted again: an `On Hold` issue asks the owner. Landings are not judged while a kill switch is on. The revert code is in the runner's landing code, so it is part of the fixed set.

**Workflow issues.** A `Workflow` issue on the request repository routes to the worker, which runs the Steward first (Entry B) per [prompts/worker.md](../../tools/triage/prompts/worker.md). Its fixes go out as `agents/...` lanes, branched from `workflow_base` and listed in the status file; after the worker session the runner lands them as above (the issue is closed `Done` only when the status state is `done` and every listed lane merged; `blocked` or `needs_decision` states keep it open with `Blocked` / `Needs Decision` and the usual question, a lane filed instead of merged keeps it `Blocked`, and the lanes, with filed ones linked to their issues, are listed in a comment; the worktree stays while a lane is unlanded). A `Workflow` issue is never closed as not planned for lack of code. For an ordinary issue the worker does not run the Steward: the runner queues its post-mortem.

**Owner comments during a run.** A comment the owner posts while a run is in progress is archived with the run's evidence, so the post-mortem sees it, and an owner reply that resumes a `Blocked` issue counts as an owner correction for that flow.

## Headless marker, label removal

The runner sets `FENTON_HEADLESS=1` on every `claude -p` launch. The Stop hook `tools/hooks/stop_continue_guard.py` is active only when it is set: a headless session cannot be woken by a background job's completion, so the hook refuses to end it while a `bg_run` job or background agent runs, or when it says out loud that it is waiting ([token-economy](token-economy.md)). Interactive sessions are not blocked. Removing a label that is not on the issue is a no-op: the runner falls back to the REST call and does not fail, and `gh` 401 or a logged-out `claude` prints one log line per tick.

## Nightly Fix issues

After the owner's requests, each tick also works open `Nightly Fix` issues on the product repository (filed by the nightly run, [ci](ci.md#failures-become-issues)): same worker model, reviewer and `pr_land.sh`, with branch `nightly/N`, worktree `nightly-N`, state `state-nightly.json` and the prompt `prompts/nightly.md`. The agent never closes them: a merged fix leaves the label `Awaiting Nightly` and the next passing nightly run closes the issue. `config.json` `nightly` holds the repo, label and allowed authors; the `PAUSED` file stops this intake too.

## Safety

- Only issues and replies by `authors` are worked. Issue text is wrapped as untrusted data in the prompt (`UNTRUSTED_NOTICE`): a request, never instructions to touch credentials, CI, signing or other repos.
- The session runs in **auto** permission mode, so the auto-mode classifier still guards every action; the deny list (`tools/triage/config.json`, tested) also blocks `gh api` PUT/GraphQL calls and merge-into-ref REST routes (the `merge_guard` hook blocks `gh pr merge` and pushes to `main` unless via `tools/pr_land.sh`, which the config allows), pushes or refspecs that land on `main`, force-push flags and `+` refspecs, REST calls that merge into or rewrite refs, workflow runs and `simctl shutdown all`. These are prefix patterns, so they narrow what a session can do rather than guarantee it; the prompt, the `merge_guard` hook and the `pr_land.sh` gate (checks, recorded review, kill switch) are the other layers.
- Tokens: `gh auth token` is read only inside the runner for downloads and uploads; logs and comments pass through `redact()`. The Home Assistant credentials stay in `~/.config/fenton-hass/env` (mode 600); `tools/ios_uitest.sh --env shell` loads them in its own process via `tools/hass_creds.sh`. The worker's Read deny on `~/.config/fenton-hass/**` does not stop it from sourcing the loader and printing the values; the protection is the auto-mode classifier plus the worker's prompt (never print, copy or commit them).
- Capacity: every build and simulator run goes through `tools/devcap.py` (directly or via `tools/ios_uitest.sh`), on simulators named `… (Triage)` only; the session's deny list blocks bare `xcrun simctl boot`, `xcodebuild test` and `xcodebuild build-for-testing` so nothing bypasses the gate.
