# Shared mobile_app registration

> **What:** the one `mobile_app` registration each phone keeps per Home Assistant user, which push, location and sensors share. **Read when:** touching registration, sign-out, the webhook, or adding a feature that sends through `mobile_app`.

One phone is one Home Assistant device. Push ([push](push.md)), location and sensors ([location](location.md)) all go through the same registration, so the phone gets one `notify.mobile_app_<device>_fenton`, one `device_tracker` and one set of sensors.

## Shape

| Piece | Where | Role |
|---|---|---|
| `MobileAppRegistrar` | `HassCore/MobileApp` | Register, `update_registration`, sign-out (unregister, with an `app_data: {}` fallback), notification button events |
| `MobileAppRegistration`, `MobileAppDevice` | same | The webhook per user and server; the device facts sent |
| `MobileAppRegistrationStore` (`KeychainMobileAppRegistrationStore`, `InMemoryMobileAppRegistrationStore`) | same | One webhook per user and server, plus the active one, the `PendingUnregister` removals to retry (`PendingUnregisterRetrier`) and the install's `DeviceTokens`. Also the `MobileAppWebhookSource` location and sensors send through |
| `SensorReporter` | same | `register_sensor` once per webhook id and app version, then `update_sensor_states` with what changed; a new registration or a 410 registers again ([location](location.md#sensors)) |
| `HomeAssistantPushClient` | `HassCore/Push` | `GET /api/fenton_home/config` and the registration endpoints |
| `MobileAppCoordinator` | `HassUI/App/MobileApp` | The session's registrar and user, and the install's APNs and push-to-start tokens (seeded from the store, gated by permission); publishes `registration` and tells listeners when it changes |
| `PushCoordinator.mobileApp` | `HassUI/App/Push` | Push owns the coordinator (the app delegate's object), asks for notification permission, then syncs |

## Rules

- **When:** after sign-in, once the websocket is up and the user is known (`MainTabView.loadProfileName` → `PushCoordinator.didConnect`), on every new APNs token, and once more after a webhook answers 410.
- **S+H Home Integration optional (contract change, 2026-10-15):** `GET /api/fenton_home/config` (falling back to the pre-rename `/api/fenton_push/config` on a 404) answering **404 on both paths, or `available: false`, registers websocket-only** (no `push_url`, `push_token` or `apns_environment`), so location and sensors work on a server without the integration. A later sync adds the push details once the integration answers. Other config errors (5xx, network) stop the sync, so a broken integration never clears working push details. This replaces push's earlier "404 registers nothing"; `SFenton/ha-fenton-push` `docs/CONTRACT.md` §1 needs the same change.
- **Sensors follow the registration:** the sensors are registered per webhook id (`mobileapp.sensors.registered` in `UserDefaults`), so a new registration, or one made after a 410, registers them all again; the entities belong to the device the registration created.
- **One per user:** the webhook is reused on the next sign-in as the same user; a 410 forgets it and registers again.
- **Keychain item:** service `com.sfenton.home.push` (push's original name, kept so phones that registered before the move keep their device), this-device-only, after first unlock.
- **Device tokens persist (2026-11-13).** The last APNs token and the Home activity's push-to-start token are saved (`DeviceTokens`, in the same Keychain item as the webhooks: this-device-only, after first unlock, no new storage) and seed `MobileAppCoordinator` at launch, so the first sync after any launch carries them. Before this, a launch synced before `LiveActivityTokenReporter` delivered the start token, so `app_data` lacked `start_live_activity_token` and Home Assistant ended the phone's cards (a 03:00 background launch was suspended before the second sync). They belong to the install, not the user: sign-out and `remove` keep them, so a new sign-in's first registration, by the same or another user, carries them. A new token from the system replaces the saved one and syncs (an APNs rotation too). Gates: the APNs token (and with it the start token, which only rides beside push details) goes only while notification permission is granted (`PushCoordinator` reads it before the first sync; permission turned on or off in iOS Settings syncs again; unknown until read means no gate, so a sync never drops a token for lack of an answer); a launch with Live Activities off removes the seeded start token, and turning them on restores the last known one. A reinstall keeps the Keychain item, so a stale saved token can go out until the system issues the new one a moment later. The simulator still never sends (`Refusal.simulator`).
- **Sign-out:** removes the registration from Home Assistant (`POST /api/fenton_home/devices/unregister`, S+H Home Integration 1.1) before the refresh token is revoked, and forgets the saved webhook, so no stale device remains; the next sign-in registers fresh. The store's active webhook is cleared first, which stops location at once. A server without 1.1 (404), a 403 or other HTTP error gets `update_registration` with empty `app_data` instead and keeps the webhook. If the request gets no answer it is saved as a pending removal and retried without a token at launch and when the network returns, signed in or not (details in [push](push.md#registration-contract-rules-1-2)).
- **Simulator never registers (2026-10-15).** Every simulator signs in as a real person, so each one (and each erase) used to add a `mobile_app` device and a `notify` service to that person. `MobileAppRegistrar` refuses `sync` in the simulator (`Refusal.simulator`, nothing sent) unless the launch sets `FENTON_MOBILE_APP_REGISTER=1` (`MobileAppRegistrationPolicy`), and `MobileAppCoordinator` ignores a webhook saved before the rule. Journeys that need a registration use stubs (`StubHTTPTransport`, `InMemoryMobileAppRegistrationStore`); push journeys don't need one (`simctl push` targets the bundle, and buttons and `clear_notification` run through the debug hooks).
- **Journeys:** a test-token, reset or gallery launch never registers (`PushLaunchPolicy`, unless `FENTON_PUSH=1`) and keeps webhooks in memory, so a journey sign-out never touches a real registration.
