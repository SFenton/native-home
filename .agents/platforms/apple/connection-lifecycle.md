# Connection lifecycle and caching

> **What:** how the app avoids reloads when reopened. **Read when:** touching the websocket, scene phase handling or the entity cache.

| Moment | Behavior |
|---|---|
| Cold launch | `EntitySnapshotCache` loads the last saved states from disk into `EntityStore` before the first frame, so Home draws real values immediately. `EntityStore.freshness` is `.snapshot(savedAt)` until the first live update. **No intro and no spinner** (owner, 2026-10-17): the launch screen's plain ground (`#121722`) is held over the first frame and cross-fades (0.2 s) onto the snapshot; live values then update in place. The old "Updating" spinner by Profile is gone |
| First sign-in (no snapshot) | `freshness` is `.empty` until the first live delivery, so `EntityStore.hasReceivedFirstState` is false (owner, 2026-10-24, `proposals/loading-states` section 5). `EnvironmentValues.valuesPending` follows it: tiles, `StatusPill`s and the controller row keep their names and show a soft pulsing bar where the value goes (`PendingValueBar`, VoiceOver "Loading"), never "Unavailable"; and the header shows **one** shared "Connecting to Home Assistant" arc (the reconnecting arc, no 2 s delay: `ReconnectingPolicy.showsArc`, `ReconnectingIndicator.isFirstConnect`). A real "Unavailable" appears only once Home Assistant says so. No full-screen spinner anywhere |
| First sign-in, no layout (`HouseConfigSource.current` is nil: no cache, no server document yet) | A page that draws from the house layout shows its own **skeleton** while `HouseConfigStore.status` is `idle` or `loading` (offline included): `UKConfigSkeletonView`, `UKPendingValueBar`'s fill and pulse (static 65% under Reduce Motion), `home.skeleton` / `page.skeleton`, one VoiceOver element "Getting your home from Home Assistant"; the header keeps its one "Connecting" arc (or the offline chip). When the server answers with a problem and there is still no document, the skeleton fades to a **state message** (`HouseLayoutState`, `houseConfig.state`; `integrationMissing`, `notConfigured`, `invalid`, `newerSchema`, and `timedOut` after 10 s connected with no reply, which offers Try Again). A saved layout always wins: with a document nothing changes whatever the status. When the document arrives the layers fade out (`quick`) and the page fades in rising 4 pt (170 ms). Decision: [house-config-states](../../design/house-config-states.md) rules 10 to 16 |
| Connection lost | A 20 pt white arc spinner left of Quick Links, no text, only after the connection has been down 2 s (`ReconnectingPolicy`, `ReconnectingIndicator`); it fades in and out (0.35 s) and goes when live again; values stay. With no network path the app is offline instead: the offline chip and the Profile badge, no arc |
| Connected | `HassConnection` holds its own `subscribe_entities` subscription (no HAKit states cache): the first message is the whole house, every later one a compressed diff. HAKit calls back on the connection's serial queue (`deltaQueue`); `EntityDeltaEngine` merges each message there, a burst is batched (`EntityDeltaBatch`), and one main-thread hop applies only the entities that really changed (`EntityStore.apply`). Nothing on the main thread is proportional to the house. See "Live delivery path" below |
| Background | The connection stays up for a grace period (`ConnectionLifecycle.backgroundGrace`, 30 s) so a quick app switch costs nothing, then disconnects. The snapshot is saved on entering background |
| Foreground | Reconnect; HAKit resends the subscription on the new socket and the engine diffs the fresh full set against what it has (about 40 changed entities, not the house), so views keep their identity and scroll position |
| Camera streams | Suspended on background (snapshot back over the player), restarted on return only after `HassConnection.ensureLive` shows the socket answers; see below |
| Signed out | Disconnect, clear the store and delete the snapshot |
| At home | `LocalServerRoute` moves the websocket (and HAKit's REST calls) to Home Assistant's home network address. HAKit re-reads `connectionInfo` on every `connect()` and swaps the socket only when the URL changed, so the subscription, store and views stay put |

Rules:

- **`hasReceivedFirstState` is "have we heard anything", not "are we live".** It is `freshness != .empty`: true from the first frame of a snapshot launch (so a reopen never swaps a value for a placeholder; offline with a snapshot is unchanged), true after the first live set (even an empty one), false only on a first sign-in and after `reset()`. It is derived, written only where `freshness` already is (`replaceAll` / `apply(_:removing:freshness:)` on the main actor, after the delta queue has diffed the delivery), so it adds nothing to the hot path. Tests: `HassCoreTests/FirstStateTests.swift`. Offline with no snapshot keeps the placeholders and shows the offline chip, not the arc.
- **Sign Out needs a connection (owner, 2026-10-24).** Confirmed Sign Out asks the server to unlink this phone from the person (`AppSession.confirmedSignOut`), so offline it fails and the alert says why (`AlertCopy.signOutFailed`). There is no local-only "Sign Out Anyway": the phone would keep reporting presence for an account it left. While it waits, `SignOutRow` shows an arc and "Signing Out" and the rest of the screen is disabled.

- **Nothing on the main thread is proportional to the number of entities.** The house has thousands; a change to one of them must cost the main thread one box update. A closure passed to HAKit (`send`, `subscribe`) runs on `deltaQueue`: write it `@Sendable` or build it in a `nonisolated` function, because a closure that inherits `@MainActor` traps the first time HAKit calls it (`dispatch_assert_queue`, seen 2026-10-16). Measure with `tools/ios_scrollcost.sh` (`upd ms`, `>8ms`) and `testLiveEntityUpdatesStayOffTheMainThread` ([performance](../../testing/apple/performance.md)).
- Never set a screen back to a loading state on reconnect. Show staleness with a quiet indicator (the reconnecting arc), not by clearing content.
- The snapshot is written with `.completeUntilFirstUserAuthentication` protection, debounced (10 s) and encoded off the main thread while live updates stream; entering background saves synchronously.
- Optimistic UI goes through `OptimisticActions` ([optimistic-actions](../../patterns/optimistic-actions.md)): the intent shows until the matching live state arrives, the call fails, or the revert time passes.
- Pages that load asynchronously show what they have as soon as they can; only the region that waits shows an arc ([content gate](../../patterns/content-gate.md)). A page full of `EntityStore` tiles is never gated; a gate that starts ready never shows a spinner.

## Live delivery path (2026-10-27, round 5)

- **One subscription per connection.** `connect()` calls `connection.subscribe(to: .subscribeEntities(data: [:]), initiated:handler:)` once (idempotent; `disconnect()` cancels it). The request keeps `shouldRetry = true` with `retryDuration = nil`: HAKit resends it on every new socket when the socket is ready, and never gives up (its default 10 s retry window would drop it on a reconnect later than 10 s after launch). Do not use `caches.states()`: `HACache` switches HAKit's retry off and re-sends on every connection state transition, so one reconnect delivered the whole house about twice.
- **`initiated` marks a full set.** It runs once per socket; the engine treats the next message as the full set, diffs it against what it holds and removes entities it lacks (gone while the socket was down). The first set ever replaces the disk snapshot (`EntityStore.replaceAll`).
- **"Changed" means state, attributes or `lastChanged`.** Never `HAEntity ==`: HAKit fills a missing `lu` with `Date()`, so a resend looked entirely changed. `lu` and the context are not kept. A diff `+` replaces state and `lc` and merges attributes per key; `-` removes attribute keys; `r` removes entities. Fixtures: `EntityDeltaEngineTests`.
- **Cost model.** A message costs `deltaQueue` work in proportion to what it carries and the main thread one `store.apply` of the changed entities; the values that apply replaces are freed on `deltaQueue`. A reconnect: one subscribe, one full set, about 40 entities compared on the main thread, about 0.8 ms (was about 4,450 and 11 ms). Measure with the scroll cost line (`deliveries`, `full`, `compared`, `boxes`, `transitions`, `subscribes`, `fullsets`, `delivery_ms`; [performance](../../testing/apple/performance.md), "Round 5").
- **Whole house, not per page.** The app can show about 755 of 4,723 entities, but a filtered or per-page subscription would not reduce main-thread work and per-page subscribing means a round trip and a blank before values (the "no reload on reopen" invariant). Numbers and the option comparison are in performance.md, "Per-entity subscriptions".

## Resume rule

Every resume-time registration is idempotent and torn down on background (or released with its owner): `connect()` twice is one states subscription, `didEnterBackground()` twice is one pending disconnect, a block observer is removed in `deinit`. The scene phase can change dozens of times a day on a phone that stays alive (location and push relaunches keep the process), so anything a resume adds and a background doesn't take away becomes steady cost. Owner report 2026-10-16: scrolling got worse after every background and foreground. How to add and check a registration, the heap method for system objects and what the investigation found: [resume-lifecycle](../../patterns/resume-lifecycle.md). Gauges: `HassConnection.liveResources`, `ConnectionLifecycle.liveResources`; tests `HassCoreTests/ResumeLifecycleTests.swift`, journey `ResumeCyclesJourneyTests`.

## House config

`HouseConfigStore` (`HassCore/Config`, plan `build/research/house-config-runtime.md`) follows the house document the `fenton_home` integration serves and publishes it to `HouseConfigSource.shared`, which every `*Config` facade reads ([architecture](architecture.md#house-config-facades)). The app compiles in no house data: with no document the facades answer empty and the layout pages draw the missing-layout skeleton or message.

- **One subscription, no get.** `AppSession.start` creates the store after the connection and starts it. It sends only `fenton_home/house_config/subscribe` through HAKit's subscription API (`shouldRetry`, `retryDuration = nil`, like the entity subscription): the server sends the current document first and HAKit resends the subscription after every reconnect, so a reconnect needs no store logic. There is deliberately no one-shot get: a `shouldRetry: false` request queued before the socket is up is dropped without a completion when the socket resets (see Camera streams below).
- **Cold launch.** The cached document loads before the subscription starts (off the main thread, or inside `start()` when the app asks for it), so `current` is set without the socket and a page draws its saved layout on the first frame with no network; a clear during that load wins.
- **Threads.** The reply is decoded and validated (`HouseConfig.decode`, including the roles the app reads) on HAKit's callback queue; the main thread gets one update per changed hash, in arrival order, and compares only the hash.
- **Cache.** `HouseConfig.json` in the app group container (readable by widgets, Live Activities and the Watch app), `.completeFileProtectionUntilFirstUserAuthentication`, keyed to the server and a format version; a file for another server, version or schema is deleted. Writes go through one lock with the clear, so a write that finishes after sign-out is dropped.
- **Resubscribe while there is no document.** A store whose status is not `ready` calls `resubscribeIfNeeded()` on every reconnect (`HassConnection.didBecomeReadyNotification`, observed by `AppSession`) and every return to the foreground (`UKRootViewController`), because HAKit retries a live subscription, not a refused one. A subscription with no reply for 10 s (`timeout`) sets `Status.timedOut`; a late reply still applies. A status change never clears `current`.
- **Failure kinds keep the last good document** (the cache, or `nil`) and set `status`: `unknown_command` (integration missing or older), `{"configured": false}`, a newer `schema`, an undecodable reply, a missing required role.
- **Sign-out.** `AppSession.signOut()` clears the store and deletes the cache file. The cache is also removed by `FENTON_UITEST_RESET`.

## Profile photos

People's photos (`PersonAvatars`, [avatar](../../patterns/avatar.md)) follow the connection without a second request path for state: they watch `person.*` boxes and `EntityStore.freshness`, and act only once the store is `.live` (a snapshot never deletes or replaces a photo). A reconnect re-arms nothing new: the same picture is confirmed once per launch. A cold launch draws the cached photo on the first frame. **Sign-out and an expired session** (`AppSession.signOut()`) delete every cached photo and the in-memory images with `snapshotCache.clear()`.

## Camera streams

HAKit loses commands across a socket reset, and the old restart ran straight from `willEnterForeground` (before the app was active and before the socket was back). Evidence, simulator, 2026-10-16: after 60 s in the background the trace read `pool foreground, connection disconnected`, then `open webRTC` for all four cameras and never `opened`: `auth/sign_path` had been requested on a socket that was being replaced, HAKit dropped it without calling its completion (`HARequestControllerImpl.resetActive` removes `shouldRetry: false` requests), and `sendCommand` awaited forever. The tiles stayed on the snapshot; Home's tiles also sat on a black frame reading "Live" between background and restart because a stopped model kept its live phase.

- **Commands that something waits on take a timeout.** `HassConnection.sendCommand(_:data:timeout:)` fails with `CommandTimeout` and cancels the request; `signPath` and `cameraStreamPath` use `streamCommandTimeout` (10 s).
- **`awaitConnected(timeout:)`** polls `status` until `.connected` (or `.rejected`/timeout). `ensureLive(timeout:pingTimeout:)` adds a `ping` command (3 s) and, if it goes unanswered, `reconnect()` (disconnect then connect, as `reconnectOnRoute` does; the subscription, store and views stay). HAKit itself only pings once a minute, so after a suspension it can report `.connected` over a dead socket.
- **`HassConnection.didBecomeReadyNotification`** posts every time `status` becomes `.connected`, including reconnects. The camera pool restarts wanted streams that are not running or failed on it.
- **Rule:** nothing that asks Home Assistant for something must be started from `willEnterForeground` or assumed to survive a reconnect without `ensureLive`, a timeout, or a restart on `didBecomeReadyNotification`. Details and tests: [camera-streams](../../patterns/camera-streams.md).

## Home network address (`LocalServerRoute`)

The public URL resolves to Cloudflare even at home, so every call left the house and came back: 40–65 ms per request against about 14 ms to Home Assistant's home network address (measured from the Mac on home Wi-Fi, 2026-10-15). The route uses the home address whenever it is safe to.

- **Finding it.** On every `connect()` and network change, browse Bonjour `_home-assistant._tcp` (1.5 s) and read the TXT record's `internal_url`. Use it only when the same record's `external_url` or `base_url` is the signed-in server's public URL, the address is private (RFC 1918, 169.254/16, IPv6 unique-local or link-local, or `.local`), and `GET /manifest.json` answers 200 within 1.5 s. Home Assistant's own `internal_url` setting may be empty; the TXT value is then the address Home Assistant derives (a private LAN address and port 8123).
- **Not any Wi-Fi.** The token goes to that address, so a café network posing as home must fail. The route also requires the TXT `uuid` (the instance id, only sent on the home network) to match a pinned id. It pins the id the first time it sees the advertisement while Home Assistant, in live states over the public TLS socket, says the signed-in user's `person` is `home`; until then it never probes. After pinning, the id alone decides, so presence lag can't let an impostor in. Pins live in `UserDefaults` per server.
- **Switching sockets.** `reconnect()` calls HAKit `disconnect()` then `connect()`. Letting `connect()` swap sockets keeps the old socket's delegate, so its late close could tear down the new one.
- **One session.** `AppSession` is made once by the app delegate and handed to `RootView`. Made in `RootView.init`, SwiftUI rebuilt it dozens of times a minute and each copy opened its own socket (found on the simulator, 2026-10-15).
- **The policy lives in one place: `ConnectionRouter`** (`HassCore/Connection/ConnectionRouter.swift`), a pure `Sendable` struct with no HAKit, tasks or clocks. `HassConnection` is the adapter: it feeds the router one event per HAKit, route or watcher notification (`networkChanged`, `homeFound(url:)`, `socketOpened(url:)`, `socketReady`, `socketFailed`, `tick(idle:)`, `wantsConnection(_:)`, `online(_:)`) and performs the returned actions (`.forgetHome` = `route.reset()`, `.checkRoute` = `refreshRoute()`, `.reconnect(to:)`, `.scheduleSwitchCheck(after:)` = the switch timer that reads `ScrollActivity`, `.cancelSwitch`). Change a rule in the router and its `ConnectionRouterTests`; `HassConnectionReconnectRuleTests` are the integration tests. A make-before-break "warm up, then swap" would replace `.reconnect` with `.warmUp` plus `.swap` there.
- **The socket dropping reconnects; a network change reconnects only a home socket (owner, 2026-10-27, refined 2026-10-28).** The phone measured 1 to 3 reconnects per 8 s lying still, about 50 ms of main thread each (a path update dropped to the public URL, then found home and reconnected again). The rules, in `ConnectionRouter` (adapter: `HassConnection`):
  1. **Network change** (`networkDidChange`): always forget the home address (`route.reset()`, which also bumps the generation so a stale check cannot apply it) and re-check in the background. If the socket is on the **public URL** it stays (no churn on cellular or public Wi-Fi). If it is on a **home address** it is replaced by a public socket at once: walking out of the house (Wi-Fi to cellular keeps the path satisfied) leaves a dead socket that HAKit's ping would only notice after a minute or two, and service calls would go nowhere. The check then finds home again if it is still reachable (rule 2).
  2. **Home found** (`homeWasFound`): switch only if the socket was not opened on that URL (`SocketURLRecord`, written by the `connectionInfo` closure HAKit calls on every connect, lock-protected). A socket that is not ready (connecting, waiting to reconnect) connects on the home address now. A ready public socket switches only once nothing has scrolled for 1 s (`ScrollActivity.idleDuration`, re-checking that the route is still local and the socket still public at that moment).
  3. **Home drops** (socket on a non-public URL goes to `waitingToReconnect`, `socketDidFail`): forget home and reconnect on the public URL immediately instead of waiting out HAKit's backoff, once per failure (the record is public afterwards, so a second notice does nothing). **Failover re-check:** when that public socket is ready (`socketBecameReady`), the route is checked once so home is found again in the same session (rule 2 applies); one check per failover. A public socket's own `waitingToReconnect` does not reset the route (that would discard a correct check in flight).
  4. **Never move to public on purpose while the home socket still works,** except on a network change (rule 1). Only a drop or a network change does.
  5. **`connect()` never changes the URL under a live socket.** HAKit swaps a socket in place when `connect()` reads a different URL, and the old socket keeps its delegate. With no socket (`.disconnected`) `connect()` is plain. With a socket, `ConnectionRouter.connectRequested()` decides: URL unchanged, plain connect; URL would change and the socket works, leave it (a pending deferred switch stays pending and still fires); URL would change and the socket is not ready, safe `reconnect()` on the right URL (which ends the pending switch). `disconnect()` and going offline cancel the pending switch through the router, so `hasPendingSwitch` cannot drift from the timer.
  6. **A home address is not trusted across a suspension.** `NetworkPathChangeFilter` only de-duplicates path churn; it is **not a network identity**: two Wi-Fi networks with the same gateway (for example a common default gateway address) look identical, so a move between them reports no change. Therefore the route is reset when the app enters the background (`HassConnection.didEnterBackground()`, called by `ConnectionLifecycle`, immediately, because the process may be suspended before the 30 s grace timer runs) and in `disconnect()`. A foreground `connect()` and HAKit's retries then start on the public URL (rule 1 of the security invariants: the token never goes over plain HTTP to an address the route has not verified) and home is found again only through the verified route check (pinned instance id, `manifest.json`) and the deferred switch. A socket still open at foreground is not a leak (a connection to a LAN address dies on another network, then rule 3 applies).
  7. **Path filter.** `SystemNetworkPathWatcher` forwards a path update only when the network really changed (`NetworkPathSignature`, `NetworkPathChangeFilter`: satisfied, local, primary interface, gateways); tunnels, a USB link or cellular beside Wi-Fi do not count. Cellular never looks for home.
- **Scroll signal.** `ScrollActivity.shared` (HassTelemetry, so HassDesign can report and HassCore can ask) stores a timestamp: `UIKitScrollOffset` notes every contentOffset change and `.reportsScrollActivity()` (on every scroll surface and applied by `.scrollTelemetry`) marks a surface active from the first scroll phase until idle, so sheets, the flyout, sign-in and Vacation count too. No SwiftUI state, no allocation per frame.
- **Counters.** `connection.pathUpdates` (every NWPath update), `connection.networkChanges` (those that passed the filter), `connection.route.local` / `connection.route.public` (reconnects by chosen URL). The scroll cost probe prints `path_updates net_changes route_local route_public`; on a phone lying still `net_changes` and the route counters should be about 0 per 8 s.
- **Identity stays public.** `HassServer.baseURL` is still the public URL: snapshot caches, push links, camera and image URLs, the settings web view, token refresh and the `mobile_app` registration and webhooks (location reports run from background zone events with no connection or route) use it unchanged. Only the websocket and HAKit REST requests move.
- **Plain HTTP.** Port 8123 serves HTTP only, so the bearer token travels unencrypted on the home Wi-Fi, as it does with the official app's internal URL. `NSAllowsLocalNetworking` permits HTTP to local names and addresses only. iOS asks for Local Network access the first time.
- **Tests.** Off for UI test launches (`FENTON_UITEST_RESET`, `FENTON_HASS_TOKEN`, `FENTON_GALLERY`) unless `FENTON_LOCAL_ROUTE=1`; `FENTON_LOCAL_ROUTE=0` turns it off anywhere. Unit tests: `HassCoreTests/LocalServerRouteTests.swift` (`HassConnectionReconnectRuleTests` is one test per rule above).

## Restoring pushed pages (owner, 2026-10-24)

A cold launch within 30 minutes of the last use puts back each section's pushed pages, not just the selected tab. `MainTabView` writes `ShellNavigator.restorableRoutes` (a `ShellRoute` list per section, `RouteRestore.encode`) to `SceneStorage` whenever it changes and when the scene leaves the foreground, with the time; `restoreRoutes()` reads it back if `RouteRestore.isFresh` and no notification is waiting. A stack holding a page the navigator did not push (a `NavigationLink` value) is not restored. Rooms' sheets and scroll offsets are not. Signing out clears it. Quick Links pops to a page already in the stack instead of pushing it again (`ShellNavigator.push(_:in:)`), and a refused token skips the intro on the welcome back screen (`AppSession.sessionExpired()`).
