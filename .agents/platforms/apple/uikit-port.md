# UIKit port

> **What:** the rules for the UIKit iOS app, which is the app (owner, 2026-11-01: the UIKit app replaces the SwiftUI app; before that, owner request 2026-10-29: port the whole app to UIKit, UX identical). **Read when:** writing or reviewing anything under `apple/Sources/HassUI/UIKitPort/` or `apple/Apps/iOS/`.

## Shape

Decision record: [decision-uikit-replaces-swiftui](decision-uikit-replaces-swiftui.md).

- **One app (owner, 2026-11-01).** `FentonHome` (`com.sfenton.home`, "S+H") is the UIKit app: `UKAppDelegate` + `UKSceneDelegate` in `Apps/iOS`, every screen in `HassUI/UIKitPort`. The SwiftUI iOS app, its screens and the side-by-side `FentonHomeUIKit` target are deleted. It runs the shared `AppSession`, `HassConnection`, `EntityStore`, configs, models, copy and gallery fixtures. Widgets, Live Activities, the notification extensions and the Watch app stay SwiftUI (Apple requires it); they use `HassCore`, `HassDesign` and `FentonActivityViews`. HassUI keeps only the non-UI types the port calls (routes, `ShellNavigator`, policies, models, configs, fixtures, copy) plus a few static helpers that used to live in SwiftUI view files; `Features/` and `App/` hold those, not screens.
- **Where the code lives.** `apple/Sources/HassUI/UIKitPort/<Area>/`, inside the HassUI module so it can use HassUI's internal models, routes, fixtures and policies without making them public. Areas: `Foundation`, `Design` (the HassDesign components), `Common`, `App` (root, shell, layout, motion), `Features/<Feature>`, `Gallery`, `Diagnostics`.
- **Every file is wrapped in `#if os(iOS)` … `#endif`**: HassUI also compiles on the Mac host for `swift test`. Galleries and fixtures stay inside `#if DEBUG` as their SwiftUI counterparts do.
- **Every new type is prefixed `UK`** (`UKGlassTileView`, `UKSecurityViewController`), so a grep finds the whole UIKit layer and it never collides with a shared model.
- **No SwiftUI on screen.** Never `UIHostingController`, `UIHostingConfiguration`, `_UIHostingView` or a SwiftUI `View` in the port. No file under `UIKitPort/` imports SwiftUI: read a HassDesign token that is a SwiftUI `Color` with `UIColor.token(_:)` (defined in HassDesign, `UIColor+Token.swift`), or use the raw `UInt32` palette values where they exist; a shared model that holds a SwiftUI type gets a helper outside the port (`ShellNavigator.trimPath`). Widgets and Live Activities stay SwiftUI (WidgetKit has no UIKit), as does the watch app (no UIKit on watchOS): they are extensions, not the app's UI.

## Reuse, never fork

- **Logic is shared.** Models (`ChoresModel`, `LoginModel`, `RecipeCollectionModel` …), configs (`SecurityConfig` …), routes (`HomeRoute`, `ShellRoute`, `ShellNavigator`), policies (`SplitPolicy`, `OrientationPolicy`, `ShellChrome`), metrics (`TileMetrics`, `ModuleRowMetrics` …), copy (`LoginCopy`, `AlertCopy` …) and fixtures (`SecurityFixtures`, gallery recorders) are used as they are. When a SwiftUI view computes something inline that the port needs (a label, a colour choice, a state mapping), move it into a `static func` on the existing type in the SwiftUI file's own area and call it from both, leaving the SwiftUI behaviour unchanged. Never copy-paste logic.
- **Service calls** go through `HassServiceCalling` (`context.caller`), state reads through `EntityStore` (`context.store.entity(id)` boxes). Same rules as AGENTS.md: one state path, one call path, no polling.
- **Identifiers and labels are stable.** Every `accessibilityIdentifier`, label, value, hint and trait the old SwiftUI view set is set on the UIKit view, in the same reading order, so the `iOSUITests` journeys (in `apple/Apps/iOSUITests`, retargeted to the UIKit app in the next lane) keep working. `tools/uikit_journeys.sh` is gone; `tools/ios_uitest.sh` runs the journeys.

## Binding state

- `UKObservation` / `UKObservationBag` (`Foundation/UKObservation.swift`) are the port's `@Observable` binding: a closure that reads observable state and writes it into views; it re-runs once per run-loop turn after anything it read changes. Bind each view to the `EntityBox` it shows (`store.entity(id)`), never to the whole store, so a live change costs one box's views.
- Cells: a cell keeps a bag, `removeAll()` in `prepareForReuse`, and binds again in `configure`.
- `UKContext` (`Foundation/UKContext.swift`) is what `@Environment` hands down in SwiftUI: store, caller, connection, session, navigator, section, surface (page or sheet), `valuesPending`. Pass it to every screen and view you create; copy with `context.with { $0.surface = .sheet }`. Add a field here (orchestrator-owned file) rather than reaching for a singleton.

## Look and motion

- **Same tokens.** Spacing, radii, palette, metrics and motion come from HassDesign (`HassTokens`, `MotionTokens`, `TileMetrics`, `ModuleRowMetrics`, `SegmentTokens` …). Never retype a number that exists as a token.
- **Wrapping labels give way.** A label that may wrap (`numberOfLines = 0`, the `UILabel.uk` default) never gets `.required` horizontal compression resistance: beside another wrapping label it leaves a self-sizing row's measurement undecided, and the row can come out with its neighbour wrapped a letter a line (owner, 2026-10-31: tall Expired Food and Food Spaces rows, only some of them). A count or value beside a row's main text is a `UKValueLabel` (`Design/UKValueLabel.swift`): it wraps, but within at most a share of the row (half by default), so its size is definite. A title that must wrap beside a control takes `.defaultHigh`.
- **A wrapping label wraps at a reference width, never its own.** A `numberOfLines = 0` label with automatic `preferredMaxLayoutWidth` wraps at its last laid-out width; where its container takes its width from the label (a centred or `.leading` stack, a capsule that hugs its title) width feeds wrap and wrap feeds width, a layout loop. Set `preferredMaxLayoutWidth` from something whose width its own constraints or frame fix (a host, a cell's fitted width, the window) through `UKWrapWidth` (`Design/UKWrapWidth.swift`: `set(label, in: reference, reserving:)` writes only on change; `UKWrapHost` for a plain holder; `UKWrapSync` uses it for fill stacks), or pin the text to the container's margins guide. Call it from the host's `layoutSubviews`. Never read the label's own bounds.
- **A hidden overlay stays out of the layout.** An overlay that hides stays out of the layout: remove it from its host, or at least deactivate its constraints, and reset its transform; never leave a hidden view in an Auto Layout host with a non-identity transform (the folded Duo rotation hang: `UKOfflineChip`).
- **Text.** SwiftUI `.font(.body)` is `UIFont.preferredFont(forTextStyle: .body)` with `adjustsFontForContentSizeCategory = true`; weights and `.monospacedDigit()` through `UIFontDescriptor`. Dynamic Type up to AX5 must lay out as the SwiftUI page does (wrap, stack, scroll).
- **Appearance.** Pages are always dark (`overrideUserInterfaceStyle = .dark` on the shell); sheets follow the system (direction G, Layers).
- **Motion.** SwiftUI springs map to `UIView.animate(springDuration:bounce:…)` (iOS 17) with the token's duration and bounce; `.easeInOut(duration:)` to `UIViewPropertyAnimator` curves. Reduce Motion, Reduce Transparency and Increase Contrast are honoured exactly where the SwiftUI code honours them (`UIAccessibility.isReduceMotionEnabled` …, and their change notifications).
- **Layout.** Grids and long lists are `UICollectionView` with a compositional layout and a diffable data source (self-sizing cells); short fixed pages may be a `UIScrollView` with `UIStackView`s. Inset grouped lists use `UICollectionLayoutListConfiguration(appearance: .insetGrouped)` or the module row metrics, matching the SwiftUI page's insets, radii and hairlines. Sheets are `UISheetPresentationController` with the detents and grabber the SwiftUI `.presentationDetents` gives (`HassModal`, `SheetFit`).
- **Navigation.** Each section is a `UINavigationController`; the shell is a `UITabBarController` (compact) or the flyout (regular width), as `MainTabView` decides with `ShellNavigationStyle` / `ShellChrome`. Large titles, back buttons, toolbar items and the header buttons match the SwiftUI bar.

## Galleries and probes

- `FENTON_GALLERY=<page>` (and the gallery's other variables) opens the fixture page (`Gallery/UKGalleryRouter.swift` dispatches; each feature lane owns its `Gallery/UK<Feature>Gallery.swift`). Measurements and side-by-side screenshots depend on it.
- `ScrollCostProbe`'s driver and `MainThreadCostMeter` are shared: the port runs the same measurement code (`Diagnostics/`).

## Lanes

Each lane works in its own worktree and branch off `claude/uikit-port`, owns the files it creates under its area, and may make the minimal shared-logic extractions described above in HassUI/HassDesign (keep the SwiftUI app's behaviour and tests unchanged). The orchestrator merges.

## Shell rules from the third round (owner, 2026-10-30)

- **Bar items are the system's.** A count on a bar button is the `UIBarButtonItem.badge`, never a drawn view: the iOS 26 bar renders a custom view's subviews through its own foreground treatment, so a drawn red capsule came out a white blob on the Profile photo. The drawn badge stays only for bars before iOS 26.
- **Every sheet page is a `UKPageViewController`; the shared modal wraps anything else (owner, 2026-10-31).** A page in a sheet has the sheet surface (`context.surface = .sheet`), puts its content in `contentView` (inset by the side safe areas, so the folded Duo's rail never covers it) and names its scroller with `install(scrollView:)`; its own full-bleed ground goes through `setSheetBackdrop(_:ground:)`. `UKHassModalController` hosts any root, pushed or set controller that is not a page in `UKPageHost.sheetWrapped(_:)`, so nothing can bypass the inset. See [modal-sheet](../../patterns/modal-sheet.md#safe-area-and-the-rail-owner-2026-10-31).
- **A page at rest stays at rest.** `UKPageViewController.followTopInset()` moves a resting scroll view to its new top whenever the bar above it changes height (fold, unfold, rotation, tab switch, return from a sheet); without it the old offset is a scroll of the difference and the bar collapses the large title into the header on a page nobody scrolled. A drag in progress is never moved.
- **Page content tracks the safe area.** ``contentView`` is re-framed on every layout, on `viewSafeAreaInsetsDidChange` and after a size transition.
- **Self-sizing cells are measured at the proposed width.** Lists and grids of self-sizing cells use `UKWidthAwareCollectionView` (drops measured heights when the width changes) and call `ukFitted(_:)` from `preferredLayoutAttributesFitting` (`Design/UKSelfSizing.swift`). A cell measured while its sheet was still taking its width wrapped to one word a line and stayed that tall.
- **A handoff blocks touches.** From the moment Quick Links chooses a page until it has finished arriving, the section's pages ignore touches, and the sheet takes one choice per opening: Home shows camera tiles under the same finger position as the room tiles, so a second tap during the dismissal opened the Driveway camera over the page that was about to push.
- **Large title versus content margin.** The system large title sits on the navigation bar's layout margin (20 pt at regular width, 16 pt compact), and page content sits on the 16 pt page padding. SwiftUI shows the same 4 pt offset at regular width (measured on the unfolded Duo, Home); it is the system's design and is not changed.

## Rotation hang (owner, 2026-10-31): open, instrumented

A folded Duo rotated portrait, landscape, portrait was killed by the scene-update watchdog (0x8BADF00D, 10 s) with the main thread inside `UIWindowScene _computeMetrics` -> `window:willAnimateRotationToInterfaceOrientation` -> `layoutIfNeeded`. The simulator does not reproduce it (see the lane report; a window-scene rotation settles in 3 to 11 layout passes per page, 2 shell passes, 1 root pass, no value flips). To catch it on the device by hand, launch with `-UKLayoutCensus YES` (an Xcode scheme argument; Release included) or `FENTON_LAYOUT_CENSUS=1`: `UKLayoutCensus` then writes one `os_log` line per rotation (subsystem `com.sfenton.home`, category `layout-census`, `settled`, or `busy` every 2 s while layout passes keep arriving) with the layout passes per page, root and shell and the ordered values a pass wrote (`hinge`, `bar`, `style`, `cap`, `fixedTitle.write`). Off, each call is one Bool read. Debug builds also have `notifyutil -p uk.debug.landscape|uk.debug.portrait|uk.debug.tab.<section>` (a window-scene rotation and a tab switch for simulator loops).
- **Duo postures (owner, 2026-11-01).** `UKDeviceSignals` publishes `UKShellEnvironment.windowFold` (the hinge in either pose; presence: the shell style, `UKSheetPlacement`) and `windowHinge` (the band, only while partly folded; every avoidance consumer). A posture change (same window size) is applied once from `UKDeviceSignals.refresh` (also run from the `UIHingeInteraction` update) and animated by `UKReflow` with `MotionTokens.standard`, or a 0.2 s snapshot cross-fade under Reduce Motion; never write layout inputs from a layout pass (`FENTON_LAYOUT_CENSUS=1` checks). See [split-view](../../design/apple/split-view.md) and [hinge-avoidance](../../patterns/hinge-avoidance.md). First-layout exception (section sides): `UKFoldColumns` sets the initial pose on the first layout pass of a view that was never laid out, so nothing is on screen yet and nothing animates; every later pose change is decided outside layout (`updateSplit`), and `UKFoldColumns.splitWritesInLayout` stays 0 in the census test.
- **Page grids follow the fold themselves (owner, 2026-11-01).** `UKHinge` (`Design/UKHingeAvoidance.swift`) is the one source for grids that sit in a view hierarchy of hand-laid columns: `UKHinge.frame` is the band (partly folded only), `UKHinge.hasFold` is the hinge in either pose, both written once by `UKHinge.publish(_:)` from `UKDeviceSignals.refresh`, which posts `didChange`. `UKDynamicGridView.followsFold = true` makes a page grid read both: it applies them one turn after the notification (so `UKReflow`'s `layoutIfNeeded` animates the reflow) and calls `remeasure()` up through the grids and columns above, which hold the measured height. Partly folded the tracks split around the band; lying flat the track count stays even (symmetric about the page's midpoint) with no gap. `UKRoomsGrid` sets it unless `avoidsHinge = false` (sheets), so the room page's two-column section grid, each section's tile grid, the Media page, Kitchen groceries and the app-launch grid all follow; also on Security (Doors, Guests, Cameras), Climate contacts, Vacuums robots, Sprinklers, Custom Lights, Chores quick links and the Food hub grids. `UKFlexGridView` (household settings, Vacation) keeps its own copy of the fold with the same deferred apply. The Recipes card grid (`UKRecipeResultsController`) builds its tracks from `DynamicGridMetrics` with the same inputs whenever a hinge exists, as one horizontal group per row with absolute item widths and trailing edge spacing (the band is the spacing after the last leading card). Sheet grids stay off: a sheet sits in the leading half.
- **Page base (owner, 2026-11-01).** Spacing, the scrolling body, the pinned bar and the ground belong to `UKPageViewController` and `UKPageBody.swift`: `UKPageMetrics`, `UKPageScrollView`, `bottomAccessory`/`UKPagePinnedBar`, `UKPaneViewController` (a pane or tab never paints a ground), `UKPanePlaceholderViewController` (the one split empty state) and `UKContext.isPane` (a page in a split's pane makes no wallpaper of its own). A page sets none of `contentInset`, `contentInsetAdjustmentBehavior`, a top constant, a bottom-bar inset or `view.backgroundColor`. See [page-base](../../patterns/page-base.md).
