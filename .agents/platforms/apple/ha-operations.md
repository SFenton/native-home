# Changing the live Home Assistant

> **What:** how agents change the live Home Assistant: config, restarts and HACS installs. **Read when:** the cause of a bug, or the right place for a feature, is on the server (an automation, a package, a template, an integration). **Decision:** owner, 2026-11-03, full control for agents. These are guardrails, not approvals: nothing waits for the owner, everything is backed up, checked, logged and reversible.

The app still never duplicates automation logic ([AGENTS.md](../../../AGENTS.md)): the app signals intent and Home Assistant decides. What changed is that an agent may fix the server side itself instead of stopping and describing it. Pick the right side: behavior that must work for every client or while the app is closed belongs in Home Assistant; display, input and navigation belong in the app. Do both when both are wrong.

## The one path: `tools/ha_change.py`

Every change goes through [`tools/ha_change.py`](../../../tools/ha_change.py) (stdlib, tested with a fake `ssh`). Never hand-edit `/config` over a raw `ssh hass` session and never call the restart or reload services yourself.

| Command | What it does |
|---|---|
| `backup NAME` | `ha backups new`, waits, prints the slug. |
| `check` | `ha core check`. |
| `apply --files LOCAL:REMOTE ... --reason TEXT` | Full backup, remember the old copies, write the files, `ha core check`, then reload the affected domain (or restart Core when no reload covers it). `/config/fenton_home/house.yaml` and `house.json` reload through the admin service `fenton_home.reload_house_config` (no restart); the `fenton_home` config entry must be `loaded` first (otherwise the apply fails and rolls back), a failed reload call also rolls back, and afterwards the Repairs list is read, and a `house_config_invalid` issue from `fenton_home` counts as a failed apply: every target is put back, the house config is reloaded again and the error names the backup slug (log result `house_config_invalid_restored`). Every target is read before the first write (an unreadable one aborts the apply; only a missing one counts as new). Any failed write or failed check puts **every** target back (a new file is removed), reloads nothing and exits 1; if putting a file back also fails, the log says `rollback_failed` and the error names the backup slug. **Sources** are only files inside the checkout you run it from (realpath, so a symlink out is refused), never a dot-file or dot-directory, never a name that looks like a secret (`*.env`, `*.key`, `*.p8`, `*.p12`, `*.pem`, `*.cer`, `*.mobileprovision`, `id_*`), and never a git-ignored file except under `build/ha/` (the scratch place). **Targets** are under `/config` only; `/config/www` is refused (Home Assistant serves it without authentication). |
| `restart --reason TEXT` | Backup, `ha core check`, then `ha core restart`. |
| `hacs-install OWNER/REPO --reason TEXT` | HACS 2.x has no `hacs.*` services and its update entities cannot refresh themselves, so the tool drives HACS's own websocket commands from the add-on (a stdlib client run over `ssh hass`, authenticated with the add-on's `$SUPERVISOR_TOKEN`, so no token reaches the Mac): `hacs/repositories/list` resolves OWNER/REPO by `full_name` among HACS repositories only (case-insensitive; an unknown repo fails with "add it as a custom repository in HACS", so OS/Supervisor/other update entities can never match), `hacs/repository/refresh`, then it compares HACS's `available_version` with GitHub's truth read locally with `gh` (latest release tag, else the full 40-character head sha) and refuses a stale HACS (nothing changed; a sha compares by prefix only when one side is a full 40-character sha, tags exactly). After the download the commit HACS reports installed must match the GitHub head. Already at the target: `up_to_date`, nothing else runs. Otherwise: backup, list `custom_components` with a checksum per directory (per-file `cksum`; `__pycache__` ignored; a failed listing stops the command), tar it (without `__pycache__`) to `/root/ha-changes/custom_components-<time>.tar` on the HA host, `hacs/repository/download` with `version` set to the release tag, or for a commit-tracked repo to its default branch (what HACS's own UI sends; a sha would be stored as `installed_version`, never equals HACS's short available commit and leaves the update entity on, `update/__init__.py:361-368`; a short sha 404s on both archive URLs, `utils/url.py:6,28`) (also covers a repo registered but never downloaded), verify HACS now reports the target as installed (a mismatch fails, naming the backup slug and the kept tarball, with no undo or restart), `ha core check`, then restart Core. A failed check removes the directories the install added, puts back from the tarball **only** the pre-existing directories that changed, and runs the check again; the tarball is deleted after a successful install and after a successful undo, and kept on `rollback_failed` and on any other failure after the backup so it can be recovered by hand; every failure message names the backup slug (and the tarball when made); the command never runs a full `ha backups restore` by itself. If the partial undo fails or the check still fails, the log says `rollback_failed`, the command exits 1 and the error prints `ha_change.py revert <slug>` as the manual full restore. HACS source: `custom_components/hacs/websocket/repositories.py:23` (list), `repository.py:214` (download), `repository.py:274` (refresh). |
| `revert SLUG` | `ha backups restore SLUG` (the slug `apply` and the others print and log). |

`REMOTE` is a path under `/config` (relative paths resolve there). Refused outright: `secrets.yaml`, `.storage`, `.cloud`, `deps`, the database, `*.bak`, `..` segments and anything outside `/config`. Local files from the credentials folder are refused too. Write the new YAML to a scratch file first (a whole replacement file; `apply` does not patch).

Reaching Home Assistant is the `ssh hass` alias in the owner's local SSH config (the HAOS "Advanced SSH & Web Terminal" add-on, reached through a jump host on the owner's network, so the Mac must be on that network or the owner's VPN). Host names, addresses and users stay in that local config, never in the repo. Reloads and the HACS call use the add-on's own `$SUPERVISOR_TOKEN` on the far side: no token is read, passed or printed on this Mac, and this tool never touches `~/.config/fenton-hass/`. Reading live state for a reproduction still uses `tools/hass_creds.sh` as before ([build-and-run](build-and-run.md)).

### The test instance: `--host`

Every command takes `--host ALIAS` before the command name (default `hass`, the house). `tools/ha_change.py --host hass-test apply ...` changes the **test Home Assistant** ([`tools/test_ha/`](../../../tools/test_ha/README.md), the VM that serves the synthetic DemoHouse) over its own ssh alias (template: `tools/test_ha/ssh_config.template`). Nothing else changes: the same backup, `ha core check`, rollback, source rules, `/config` limits and security-device flag apply, and each log line now carries a `host` field (`hass` or the alias). The alias is validated (letters, digits, `.`, `_`, `-`; never a leading dash, so it cannot read as an ssh option). The test instance shares no alias, key, token or credentials file with the house; its own `FENTON_TEST_HA_URL` and `FENTON_TEST_HA_TOKEN` are used only by `tools/test_ha/verify.py`. The log file is shared, so read the `host` field before acting on an entry.

### Core 2026.11: http settings and the port

- **Stored http settings.** Core 2026.11 keeps the http settings (proxy, ban, port) in `.storage/http`, in a stable and a pending slot. Once `yaml_migration_done` is set, the `http:` YAML block is **ignored**. Change them with the websocket commands `http/config` (read), `http/config/configure` (write; Core restarts on it as the pending config) and `http/config/promote` (make it stable before the auto-revert). `tools/test_ha/http_config.py` does this inside the SSH add-on (`$SUPERVISOR_TOKEN`, `supervisor:80/core/websocket`) and never prints the token; `provision.sh` runs it after the apply, and it skips when stable already matches. The test instance's values: `use_x_forwarded_for: true`, `trusted_proxies` set to the Supervisor add-on network (the `WANTED` table in `http_config.py`), `ip_ban_enabled: true`, `login_attempts_threshold: 5`.
- **Port.** On a **fresh** Supervisor install, Core 2026.11 binds **port 80** by default (the test instance), so a route that targets Core directly must use `http://homeassistant:80`. An install that migrates an existing `http:` block keeps its configured port, 8123, and that includes the main instance; read `server_port` from `http/config` before pointing a route. Supervisor-proxied paths are unaffected.
- **The main instance** is on an older Core. Its upgrade to 2026.11 will run the same migration: the `http:` block becomes stored settings and the port stays as configured (8123), so check `http/config` after that upgrade.

## Patching the house document: `tools/house_config_patch.py`

A one-off for schema-2 fields the app used to derive from names (a climate room's occupied-only switch; an air purifier's AQI, auto-mode, fan and fan-mode entities). It reads the live document (`ssh hass cat` of the house file) and Home Assistant's entity, device and area registries over the add-on websocket (the add-on's own token, never printed), fills each missing field from what exists on the server (a purifier's fan is the `fan.*` entity on its PM2.5 sensor's device; a room's switch is the occupied candidate whose registry name starts with the room's title), never touches a field already there, and writes `build/ha/house.json` (compact, key-sorted, under 256 KiB). What the registry cannot answer comes from the git-ignored `build/ha/patch-rules.local.json`. It prints counts only. `--check` (optionally `--input FILE`) exits 0 only when every climate room and purifier has its fields and every id exists in the registry. Upload with `tools/ha_change.py apply --files build/ha/house.json:/config/fenton_home/house.json --reason ...` **before** merging the app change: a build that meets a document without the fields leaves those controls not configured.

## Reload or restart

| Changed | Applied by |
|---|---|
| `automations.yaml`, `scripts.yaml`, `scenes.yaml`, `groups.yaml`, `template.yaml` | The matching `<domain>.reload`. |
| Any `packages/*.yaml` | `homeassistant.reload_all` (YAML integrations that support reload). |
| `configuration.yaml`, anything under `custom_components/`, any other file, a HACS install | Core restart, only after a passing check. |

Prefer a package file under `/config/packages/` over `automations.yaml` for anything the agents own (the Live Activity package is the model: [live-activities-ha-automations](live-activities-ha-automations.md)). A restart takes the house's automations offline for a minute or two: batch config changes into one `apply`, do not restart at night for a cosmetic change, and never restart twice in a row to retry.

## The log

Every attempt appends one JSON line to `~/hass-agents/ha-changes.jsonl`: `time`, `command`, `reason`, `files` (paths only, never contents), `backup` (the slug), `result` (`ok`, `failed`, `check_failed_restored` (the check failed and the previous state is back), `write_failed_restored` (a write failed and every target is back), `rollback_failed` (something could not be put back: restore by hand with `revert <slug>`)), `security`, a short `detail`. It carries no secret. The owner digest summarises it. `check_failed_restored` and `write_failed_restored` mean the previous state is back; there is no check-failed result without a restore. **A `rollback_failed` entry reaches the owner by code:** every triage tick (`check_ha_changes` in `tools/triage/hass_triage.py`) reads the lines added to the log since a stored byte offset (`state.json`, key `ha_changes`) and files one `Workflow` + `On Hold` issue in the request repo per such entry, giving the command, the redacted reason and detail, the target paths, the backup slug and the manual `tools/ha_change.py revert <slug>` step (never file contents; the text goes through `tools/redact.py`). Entries are deduplicated by a hash of the log line, so a restart never refiles one; a malformed line is skipped and a missing log does nothing. No alert is filed while the runner is PAUSED (PAUSED means no GitHub writes); it is filed on resume, because the stored offset has not moved. The log's inode and device are stored with the offset, so a rotated or replaced log is read again from the start. The fields are labelled as coming from the agent-writable log, stripped of backticks and `@`, and capped; the `revert` command is printed only for a slug of 8 hex characters. A try counts against an entry only when the open issues were read and creating the issue then failed; an unreachable GitHub (the read itself fails, auth or network) never counts, and the whole alert is tried again next tick. After 3 counted failures the entry is set aside as unfiled (the count is `ha_changes_unfiled` in `status`) so later entries go on, but it is kept in state with its last-try time and retried about once an hour until it is filed; it is never dropped. The last-try time is wall-clock time (`time.time()`, so a reboot does not skew it; a time in the future counts as due). When the issue list cannot be read, `state.json` records when that began (`ha_changes.unreachable_since`, cleared by the next successful read) and `status` shows it as `ha_changes_unreachable_since`. The runner has no push-notification path, so the issue is the alert. To undo a change: `tools/ha_change.py revert <slug>` (restores the whole backup taken before it, which restarts Core).

## Security devices

Locks, alarm panels, garage doors and sirens use the same path (backup, check, log) and nothing extra to wait for, but `apply` flags any change whose content mentions `lock.`, `alarm_control_panel.`, `garage` or `siren.` (`"security": true` in the log and a printed notice), and **the worker must put a line about it in the issue resolution and the owner digest**: what changed, why, the backup slug. A change must never make one of them easier to open without an explicit owner request for exactly that. Test with a read of the state afterwards, never by actuating a real lock, door or alarm.

## Guardrails that stay

- The HA SSH add-on runs busybox (`tar` 1.37.0): its `find -exec cksum {} +` and `tar --exclude=__pycache__ -cf …` (either option order) were checked on the live add-on on 2026-11-03.
- Back up first; the check must pass before any reload or restart; a failed check restores the old files and stops. Never skip `check`.
- Never read or print `secrets.yaml`, `.storage`, tokens or the cloud config; a secret an automation needs is named (`!secret name`) and the owner adds it.
- One purpose per change, a real `--reason`, and after a restart confirm Core is back (`tools/ha_change.py check`, then one entity read) before the next step.
- Core/Supervisor updates, OS updates, add-on installs or removals and network settings are not covered here: file them for the owner.
- A server fix ships with what it needs on the app side in the same issue, and the resolution says which side changed.
