## Test tiers

One table; every other doc links here instead of restating it (owner, 2026-10-28; reshaped 2026-10-29 after the [test-speed research](../../../build/handoff/test-speed.md)). A full three-device journey run took 13 h 52 m, so the full runs belong to CI and the release, not to a lane.

| Tier | When | Runs | Hook |
|---|---|---|---|
| **T0 edit loop** | While editing | `swift test --filter` for the suite you touch (seconds); one journey class with `tools/ios_uitest.sh --quick --only <family> -only-testing:FentonHomeUITests/<Class>` | none |
| **T1 per change** | Before the PR | `swift test --filter` on the touched suite; `tools/lint_motion.sh`; one journey class on the **primary family**, iPhone (`--changed` for the whole affected set); a simulator look when something is visible. CI runs the rest on every app PR: Smoke on all three families, the journeys the diff reaches, the affected (for HassCore or HassDesign, the full) Swift suites and the changed-file coverage. Run Smoke on Duo and iPad yourself only for a layout-sensitive change. Each family has its own list (`journeys_by_family`): iPhone runs every affected journey, Duo and iPad only the **layout journeys** among them (a class a rule names in `layout_journeys`, such as a pose, split or wide class, or a `layoutJourneys` class whose own file changed). A rule tagged `layout_sensitive` without `layout_journeys` (shared HassDesign components, shell, split policy, settings) is blanket and runs all of its journeys on all three families. `--changed` does this for you, and the passed-run ledger key carries each family's own filter. Changed-file coverage (`apple_coverage.sh --changed`) now runs in CI as the required `coverage-changed` job, so locally it is optional: run it only to debug a failing gate | `tier_guard.py` refuses unfiltered runs |
| **T2 merge gate** | Every PR, the `pr-checks` job | `scope` sorts the diff: **docs** and **tools-only** changes (`tools/`, `contracts/test-map*`, `.agents/`, mockups, docs, `*.md`) run the repo checks (including `tools/test_plans.py --check`) and the Python tool tests and compile nothing; an **app** change adds the affected `swift test --filter` suites (a path `affected_tests.py` cannot place runs everything). The Release build runs only when `apple/` changes. A push to `main` runs the full `swift test` | none |
| **T3 nightly** | Daily, on hosted runners ([`nightly.yml`](../../../.github/workflows/nightly.yml), [ci](../../workflow/ci.md)) | **Gate** on three families (one runner per family and shard), **Capture** on Sundays, and the full `tools/apple_coverage.sh` with the >=95% gate. Each failing area becomes a `Nightly Fix` issue. Nothing is certified until a full run passes | `FENTON_TIER=nightly` |
| **TC release** | Before a tag is cut | The same full runs with `FENTON_TIER=release` (or read the last green nightly on the commit): Gate and Live on three families, full coverage | `FENTON_TIER=release` |

**Hosted tier (owner, 2026-11-07).** On a public repo the T2 gate runs on GitHub-hosted runners with `FENTON_CI_HOSTED=1` ([ci](../../workflow/ci.md#rules-for-workflows)): no devcap holds or pool, the image's simulators (`iPhone 17`, `iPhone Duo`, `iPad Pro 11-inch (M5)`, or `FENTON_SIM_IPHONE|DUO|IPAD`), the Smoke plan plus `--changed` journeys per family (the `macos` job's Smoke and journey steps, required: a failed one fails `pr-checks`), fixtures only, no credentials. T3 and TC stay on the Macs. Locally nothing changes while the variable is unset. Python tool tests run in three parts (`tools/run_tool_tests.sh core|triage|release`); the macOS-only ones skip on Linux.

**The base of a per-change run (owner, 2026-11-04).** `--changed` diffs against the branch the work came from, never a fixed `origin/main`: `tools/lane_base.py` picks it (`--why` says which rule): `FENTON_AFFECTED_BASE`, the open PR's base, the parent recorded in `git config branch.<name>.sh-base` (`tools/lane_new.sh` writes it from `--base`; a worktree made any other way records it with `git config branch.$(git branch --show-current).sh-base origin/<parent>`), else the nearest of the remote default branch and `product_base` / `workflow_base` in [`tools/triage/config.json`](../../../tools/triage/config.json) (read-only; that file is the one place to edit when a long-lived branch is added or retired; a missing branch is skipped). `lane_new.sh` records the parent only when it creates the branch or `--base` is given. `--base` and `FENTON_AFFECTED_BASE` still override.

**Coverage runs in CI.** Changed-file coverage (`apple_coverage.sh --changed`, 36-57 min on a wide diff) is the `coverage-changed` job of `pr-checks` on every app PR, so a lane does not run it before the PR. Check an added test with its targeted `swift test --filter` or one journey class run; the local per-change tier is `swift test --filter` on the touched suite, `tools/lint_motion.sh` and one journey class. Run `apple_coverage.sh --changed` locally only to reproduce a red `coverage-changed`.

**Failures the base already has (informational, orchestrator decision 2026-11-04).** After a failing `--changed` run, the journey and coverage scripts print a summary from `tools/lane_base.py`: "Already failing on <base> (inherited)", "New failures" and "Unaccounted" (a crash, restart, GAP/EMPTY/infra line or a count that does not match the runner's totals). **It never changes pass or fail**: both scripts keep their original status logic, and a failing run stays failing. The store is `build/baselines/<base-sha>.json` in the main checkout (journeys keyed by family). It is recorded from a log produced on the clean base commit: run the script there (the summary records it) or `lane_base.py baseline record --command swift_test --log FILE`, which refuses anywhere else and takes no ids from the command line. The parser reads Swift Testing lines with or without the SF Symbols glyph; the scripts do not turn the glyph off, because `tools/log_digest.py` and the coverage classifier read it.

The >=95% coverage bar is **certified by the nightly and release full run**; a PR's `coverage-changed` job checks only the files it changed (`apple_coverage.sh --changed`, `coverage_gate.py --files`). Run the full `tools/apple_coverage.sh` yourself only when you changed the classification in `contracts/coverage-rules.json`.

**Failures in a coverage run are classified (2026-11-04, [coverage_classify.py](../../../tools/coverage_classify.py), [coverage_phases.sh](../../../tools/coverage_phases.sh); details in [coverage](coverage.md)).** Each phase (hosted, each journey part, swift) records its exit status and the ids it named. Named ids rerun once without instrumentation, same holds. The digest prints `coverage-only: <ids>` (the rerun log shows the id **passed**), `real: <ids>` (everything else, including an id the rerun never reported) and `timeout: yes|no`. Exit is non-zero for any `real` id, for a `coverage-only` id not listed in `apple/coverage-quarantine.json` (entries `{id, issue, date}`; the issue must be an open `Workflow` issue, checked with `gh`), for a timeout, and for a phase that exited 124, 125, 126 or above 128 or failed without naming a test, whatever the quarantine says. Quarantine only lets the *run* exit 0: the 95% logic and UX bars are unchanged and quarantined tests still count in them. **Reviewer checklist:** a diff that adds a quarantine entry needs scrutiny: the issue is open and is about that test, the reason is stated in the PR, and the entry is not hiding a `real` failure; never accept a quarantine entry that came in with the change it excuses.

### Test plans

`apple/TestPlans/{Gate,Smoke,Capture,Perf,Live}.xctestplan` are generated by `python3 tools/test_plans.py` from the journey sources in `apple/Apps/iOSUITests` (`--check` fails when one is stale; pr-checks runs it; suites marked `"plan": true` in `contracts/test-suites.json` also get a `Suite-NAME.xctestplan`; named suites and ad-hoc selectors run with `--suite`/`--tests`, see [suites](suites.md); run the generator after you add, rename or move a UI test). Attached to the `FentonHome` scheme (`apple/project.yml`, Gate is the default); `tools/ios_uitest.sh --plan NAME` runs one. Gate has code coverage off and test timeouts on (300 s default, 900 s maximum). Each journey is in exactly one of the first four plans, by a mechanical rule (first match wins):

| Plan | Holds | Rule |
|---|---|---|
| **Perf** | XCTest metric and signpost runs | class `*PerformanceTests` or `PerformanceJourneyTests` |
| **Capture** | screenshots and gallery sweeps | method `testCapture*` or ending `Screenshots`; class `*Capture*`; the Motion gallery sweep (`Gallery`, `EveryComponent`, `ToggleAll` in `MotionJourneyTests`) |
| **Live** | tests that need the real house | the test calls `FentonHomeApp.launchSignedIn(` or `FentonHomeApp.requireServer(` (directly or through a helper of its class), is named `testLive*`, or is in a camera class (WebRTC, HLS). They skip without `FENTON_HASS_*` credentials |
| **Gate** | everything else: fixture galleries and signed-out screens, deterministic | the rest |
| **Smoke** | not a partition: 11 named tests (the `smoke` list in `contracts/test-map.json`) | a signed-out audit, AX5 relaunch, the tab shell, a sheet opening, an audit, the Duo hinge, a rotation |

`TempScrollWedgeTests` is in no plan. An `-only-testing` filter on a test the chosen plan skips runs nothing, and `ios_uitest.sh` fails such a run (`EMPTY: no tests ran`, `xc_watch --require-tests`): pass the plan that owns the test (`--plan Live`) or use the filter without a plan. For the slow-exit case the script also hands `xc_watch --expect-tests` the exact count of tests the plan, its skips and the `-only-testing`/`-skip-testing` filters run (`uitest_support.py exact`, built on `test_plans.py`; the hold-size estimate is a looser count), so an xcodebuild that exits slowly after fewer tests than that fails as `INFRA` instead of passing; when no exact count exists (no plan file, a filter naming a class or method the sources lack, `--changed`, `--suite`/`--tests`) it passes no `--expect-tests`.

**An empty run is not a pass (2026-11-03).** A run that executes no test, or whose every test skips (journeys that skip for lack of Live credentials), is `EMPTY`. Per family, `xc_watch --require-tests` (always on in `ios_uitest.sh`, and for `swift test` in `apple_coverage.sh`; `FENTON_COV_ALLOW_EMPTY=1` opts out there) fails only when nothing executed at all (`EMPTY:`, exit 1). "Every test skipped" is decided over the whole run, because family-gated journeys (iPad-only, skipped on iPhone) legitimately skip on other families: `ios_uitest.sh` fails EMPTY when no family ran a test or `--only` names one family that ran none, and prints a `NOTE:` for a family that skipped while another ran the tests. `ios_navperf.sh` fails a family with no NAVPERF row. The `bg_run` digest reads `RESULT: EMPTY` (whatever the exit code, unless a test or build really failed) and exits non-zero; grep'd `Test Case … skipped` lines from the perf scripts count. The digest line is `executed N, skipped N, failed N`. `--allow-empty` (on `ios_uitest.sh`, `ios_navperf.sh` and `bg_run.py`) accepts one on purpose.

**Pick the instrument before the device round.** Timing, lifecycle and reconnection bugs are reproduced with signposts/`os_log`/trace timestamps ([performance](performance.md)), visual and layout bugs with a screenshot or recording, state bugs with logs or a unit repro, cheapest first ([agent-roster](../../workflow/agent-roster.md), "Record first").

**Every PR** also runs `pr-checks`: a Release build on the MacBook runner and, on the Mac mini runner, the affected Swift suites (`tools/affected_tests.py`; the full suite for a file it cannot place; a push to main runs the full suite), the mockup and motion checks and the Python tool tests (the scope and aggregate jobs run on either Mac) ([ci](../../workflow/ci.md)). The coverage gate is the nightly tier's: run `tools/apple_coverage.sh` yourself only when you changed the classification in `contracts/coverage-rules.json`.

### How to pick

1. `python3 tools/affected_tests.py` prints the `swift test` filters, the journeys, the primary families and the **smoke families** (`--plan Smoke` there), from `contracts/test-map.json`: path prefix, then file-name convention, then the file's module test target (`apple/Sources/HassUI/…` runs `HassUITests`). A file none of those place prints `NEEDS A PICK` and exits 3: choose the suites by hand and add a rule. It never falls back to the full suite. The longest matching prefix wins, so a feature folder with several journey classes (Chores, the light-appearance sheets, Settings) maps its files one by one, each rule repeating the feature's own class when the file belongs to it; the folder rule stays as the fallback for a file nobody mapped. A rule tagged `layout_sensitive` marks a file whose layout depends on pose or width and sends all of its journeys to every family. When only some of the rule's classes depend on pose or width (the split suites), the rule uses `layout_journeys` instead, naming those classes (it replaces `layout_sensitive`, and each name must be in the rule's `journeys`): iPhone runs all the rule's journeys, Duo and iPad only the named ones, and a family with none of them falls back to the Smoke plan. `affected_tests.py --journeys --device duo|ipad|iphone` prints one family's list (no `--device` prints the iPhone list); `--json` adds `journeys_by_family`. `--journeys --plan Gate` keeps only the classes that plan runs (a class Gate skips whole, such as the Live-plan `ShellJourneyTests`, matches nothing and the runner reports EMPTY); the hosted `macos` job's journeys step (`tools/ci_macos.sh journeys`) uses it and skips, with a log line, only when the diff reaches journeys and Gate runs none of them (a selection-tool crash fails the step; exit 3 still fails in the runner). Per-family selection (2026-10-30): a `HumidifierSheet` edit runs 3 journey classes on iPhone and only `RoomDevicesHumidifierPoseJourneyTests` (10 s) on Duo and iPad; `VacuumSheet` 7 classes (about 546 s) on iPhone and only `VacuumSplitPoseJourneyTests` (10 s) on Duo and iPad.
   - **Host-covered journeys (owner, 2026-10-30).** A journey may move to a nightly-only `*HostCoveredJourneyTests` class (no source rule selects it; it runs in the nightly Gate plan and in a pull request only when its own file is edited) only when a host suite in `apple/Tests` **fully** asserts what the journey asserts. Full means every assertion the journey makes has a host counterpart, including the UI-level ones: alert ids, labels and the taps on them, tile and row values, enabled states, closing of a sheet, the exact service call, 44 pt targets and audits. A journey whose twin stops short anywhere (a controller test without the sheet or alert, a different fixture, a looser call match, no target size) is partial and belongs in the area class it exercises, so a source change in that area runs it in a pull request. Move tests unchanged. A class left empty is deleted. As of this rule no class qualifies: `VacationHostCoveredJourneyTests`, `InventoryHostCoveredJourneyTests` and `ChoresHostCoveredJourneyTests` were dissolved into their area classes.
   - **Light-appearance sheets (2026-10-30).** `LightAppearance<Sheet>JourneyTests` (Security, Climate, MediaRemote, RoomDevice, Bed, Vacuum, QuickLinks, Weather, Account, Lights, System) over `LightAppearanceJourneyTestCase`: each audits one sheet in light and is selected by that sheet's own source files (`VacuumSheet`/`VacuumTabs`/`VacuumComponents`/`VacuumMapPanel`, `ClimateSheet`/`ClimateComponents` and the tab files split out of it, `Features/MediaRemote`, `AirPurifierSheet`/`HumidifierSheet`/`HumidifierDials`/`GrillSheet`/`RoomDeviceSheetChrome`, `BedSideSheet`/`BedroomComponents`, `SecuritySystemSheet`, `QuickLinksSheet`, `WeatherSheet`/`WeatherSurface`, `Features/Settings/Profile`), together with the feature's own journeys. `BrightnessTile` and `Features/CustomLights` select `LightAppearanceLightsJourneyTests`; `HassDesign/SystemAppearance` selects `LightAppearanceSystemJourneyTests`. `HassModal` and the other sheet-chrome files do not select the system class (it would add 146 s to every chrome edit); `ios_uitest.sh --appearance light` covers them.
   - **Room devices (2026-10-30).** `RoomDevicesJourneyTests` is split by device over `RoomDevicesJourneyTestCase` (the gallery launch with `startApp`, `segment`, `expectCall`, `reveal`, `audit`): `RoomDevicesFanJourneyTests` (9 tests, about 260 s on iPhone), `RoomDevicesHumidifierJourneyTests` (7, about 138 s), `RoomDevicesPurifierJourneyTests` (2, 34 s), `RoomDevicesGrillJourneyTests` (2, 25 s), `RoomDevicesHumidifierPoseJourneyTests` (1, 10 s) and the unselected Capture class. The AX5 test that visited the fan and the humidifier is one test per sheet. Each sheet's files select only its class (`BathroomFanSheet`, `FanTimer*` and `TintedCapsuleButtonStyle` the fan, with `BathroomFanSheetFit` on the host; `HumidifierSheet`/`HumidifierDials`/`HumidifierSchedulesTab` the humidifier, with `HumidifierFlow`; `AirPurifierSheet`, `GrillSheet`), together with the light-appearance class where it audited that sheet. `RoomDeviceSheetChrome` selects every device class; the folder rule is the fallback. `HumidifierSheet` is `layout_sensitive`, so it adds the pose class and runs its selection on every family.
   - **Food (2026-10-30).** `FoodJourneyTests` is split by area over `FoodJourneyTestCase` (the gallery launch through `AppReuse`, the orientation handling, `audit` with the recipe cards' reflow allowance, `expectCall`, `reveal`, `waitForGrid`; it is an `XCTestCase`, not a `JourneyTestCase`): `FoodHubJourneyTests` (8 tests, about 220 s on iPhone), `FoodSuggestionsJourneyTests` (4, 41 s), `FoodRecipesJourneyTests` (5, 133 s), `FoodRecipeSheetsJourneyTests` (2, 79 s), `FoodRecipeDetailJourneyTests` (4, 98 s), `FoodWideLayoutJourneyTests` (landscape split; skips on iPhone) and the unselected `FoodLiveJourneyTests`. ## The demo house (2026-11-06)

Tests, fixtures and the DEBUG gallery must not use the real house: use `DemoHouse` (module `HassDemoHouse`, `apple/Sources/HassDemoHouse`, all `#if DEBUG`; `HassTestSupport` re-exports it), a synthetic `HouseConfig` with matching entity states. Scope a test that reads a `*Config` facade with `HouseConfigSource.$scoped.withValue(DemoHouse.source)` and fill an `EntityStore` with `DemoHouse.seed(_:)`. `DemoHouseTests` checks its structure (synthetic ids, demo people, neutral titles); the generator that built it is never committed. The DEBUG gallery installs it as `HouseConfigSource.shared` (`GalleryHouse.install()`, from `UKGalleryRouter.requested()`), so its fixtures key states by the ids the facades answer with; a hosted test that builds a gallery page or fixture subclasses `DemoHouseTestCase` (iOSTests), which installs it for the test and clears it after. **Hosted tests share one copy of HassCore and HassDesign.** The `FentonHomeTests` bundle links only `HassUI` (`apple/project.yml`), the dynamic framework it shares with the host app, and imports `HassCore`, `HassDesign` and `HassDemoHouse` through it. Never add a package product to the bundle that `HassUI` already carries: that links a second copy, and a model changed from test code then never redraws the screen observing it; an `is implemented in both … FentonHomeTests` log line shows it. `DemoHouseTestCase` installs the demo document (`GalleryHouse.install()`); a hosted test installs through it and never sets or scopes a source itself, because a task-local scope does not reach a built screen. Code-bound ids (the Media Room scripts in `ScriptPowerActions`, the `Resident` keys) come from their constants, never a literal.

Suite traits in `HassTestSupport/DemoHouseTrait.swift` do the scoping for you:

- `@Suite(.demoHouse)` runs each test inside `HouseConfigSource.$scoped.withValue(DemoHouse.source)`. Use it for logic that computes from config; write demo ids and titles in the test. The scope does not cross a main-queue hop, so a test that hops injects `DemoHouse.source`. That is for the Swift Testing suites on the Mac host; a hosted test (app-hosted `FentonHomeTests`) subclasses `DemoHouseTestCase` instead, because a scope or source set from test code does not reach the screens under test (above).
- A suite that reads a facade without a scope sees **no document**, and every facade answers empty (the app compiles in no house, so there is no "compiled house" to test against). Put `.demoHouse` on every suite that reads a facade; to test the empty case scope an empty source: `HouseConfigSource.$scoped.withValue(HouseConfigSource()) { … }`.
- Name a demo thing by its place in the demo document, never by a real value: `BathroomFanConfig.all[0]`, `HumidifierConfig.all[0]`, `ScriptPowerActions.all[0]`, `MediaRemotes.all[0]`, `Vacuums.mainFloor` (`HassTestSupport/VacuumsByPosition.swift`) read inside the scope. Test a literal only when it is a `demo_` id.

## Journey health rules (2026-10-17)

Found by running the whole journey suite per family on main; each was a stale or racy journey, or a real app issue, fixed at its cause.

- **A full journey run is sharded.** `tools/devcap.py` caps one hold at 2 h and a family's suite is longer, so run the classes in groups of about 60 tests, one `tools/ios_uitest.sh … -only-testing:FentonHomeUITests/<Class>` per group, and read the results per group. A hold timeout kills the run mid-test and says only `BUILD INTERRUPTED`.
- **Journeys run animations fast, never off.** `FENTON_UITEST_NO_ANIMATIONS=1` sets every window's `layer.speed` to 10 (`Apps/iOS/FentonHomeApp.swift`). `UIView.setAnimationsEnabled(false)` was tried and dropped (2026-10-30): an iPhone sheet's drag settles through an animation, so with animations off a swipe on the sheet's content dismissed the sheet (Food Filter sheet), in the test's own scrolling and in the audit's AX5 measuring.
  - **The speed is tunable.** `TEST_RUNNER_FENTON_UITEST_ANIMATION_SPEED=<n>` (a positive number) replaces the 10 for a run: the journey launch helper (`FentonHomeApp.makeApp`) forwards it to the app as `FENTON_UITEST_ANIMATION_SPEED`, and an absent, non-numeric or non-positive value keeps 10. Debug builds only; use it to measure what a faster setting saves before changing the default.
- **An audit with an `ax5Page` leaves the app at AX5** (relaunched, or in a reuse launch switched in place, [app-reuse](app-reuse.md#the-audits-ax5-check-runs-in-place)). The `app` the journey holds then shows the AX5 page, whose galleries hide their Last call line, so a later `expectCall` finds nothing. Audit last, or in its own test (`testRecipesPagePassesAccessibilityAudit`, `testSortSheetPassesAccessibilityAuditAt{Top,Reset}`).
- **A gallery's debug bar never covers a control an AX5 journey taps.** The Food and Vacuum galleries leave the Last call line out at accessibility sizes; the vacuum one grew over the section bar and took its taps.
- **Find Close with `app.buttons["Close"]`**, never `app.navigationBars.buttons["Close"]`: the folded Duo's rail takes bar buttons into its toolbar.
- **`isHittable` is true for a tile whose top edge shows.** Scroll until `window.contains(element.frame)` before tapping at its centre. And the first match of a card's identifier can be a label-less twin that reports not hittable although the card takes taps: tap it and assert the selection instead of asking `isHittable`.
- **Spinner journeys stretch the load.** The simulator's launch outlasts a 900 ms demo load, so the spinner (which shows after 150 ms) is gone before the first query: `FENTON_GALLERY_GATE_DELAY_MS` on the Performance gallery, `FENTON_GALLERY_FOOD_DELAY_MS` on Food.
- **Gallery data is seeded before the screen builds.** A screen reads its log when it appears, and SwiftUI starts a `.task` before an outer `.onAppear` runs (Performance gallery); seed once per process with a static.
- **A lazy Form drops rows that scrolled away.** A reveal helper for an element that is not in the tree searches down, then up (`ClimateJourneyTestCase.reveal`): on the folded Duo's short screen the row is above the end the page was left at.
- **Never drag a sheet down to "go back to the top" unless the first row is off screen.** A content-height sheet at the top closes (the Scan Item steps audited the Pantry page behind it).
- **A frame-growth check cannot pass a row with a fixed floor.** Rows that keep a 44 pt minimum height stay the same height while their text triples (iPad Filter sheet Reset row, 74 → 93.5 pt). Give such rows padding that scales (`@ScaledMetric`) rather than a floor, and the Dynamic Type evidence holds without a waiver. The audit's "none shrank" allows half a point (the same fixed text measures 52.0 and 51.99 in two launches).
- **An accessibility element drawn from a clear shape needs `.contentShape(.accessibility, …)`** or it comes back with a zero frame (camera viewer video).
- **Core and hosted tests wait on state with margins wider than a stall.** Poll the condition against the clock; a 20 to 200 ms production timeout, a 150 ms grace or a 50 ms "let the hop land" lost to a busy main actor (`HassConnectionLivenessTests`, `HouseholdAwayControllerTests`, `InventoryListModelTests`).

## Order-independent tests

A full `swift test` runs every `@MainActor` suite in one process, interleaved on the main actor, and a run-loop pump (`RunLoop.main.run`) runs other suites' work nested inside it. A test that passes alone with `--filter` but fails in the full run is depending on that timing or on process state. Run the full suite before calling such a test fixed (2026-10-16).

- **`@MainActor` on a suite only when the code under test needs it (2026-11-04).** Swift Testing runs suites in parallel in one process, and a `@MainActor` suite runs serially. Put it on a suite that touches a `@MainActor` production type (`EntityStore` boxes, models, coordinators), a UI framework or a hosted window; leave it off a suite of nonisolated logic. Do not move suites for speed while the whole host run is about 20 s (journey-speed.md, "Host swift test"): the order-independence risk outweighs the saving.
- **No wall-clock budgets for work to happen.** Wait for the condition (`settle(until:)`, or a bounded poll of the state), and count settle passes rather than seconds (`HostedWindow.settle`). A fixed sleep is fine only for asserting that nothing happens.
- **Production timeouts race the main actor too.** A `Task.sleep` whose timer already fired returns normally even if the task is cancelled before its continuation runs, so check `Task.checkCancellation()` after a timeout sleep. Cover the race by blocking the main actor past a shortened timeout (`CameraLiveViewTests.aFirstFrameBeatsATimeoutThatHasNotRunYet`).
- **Compare renders with a tolerance.** The first `ImageRenderer` render in a process is a level or two off on a few antialiased pixels, so byte-equal `Data` depends on which test rendered first. Compare channels with a small threshold (`ValetudoMapDrawingTests.differs`).
- **Only expect a difference the view draws.** A "this changes the pixels" check on a configuration that draws nothing new passes only by render noise; assert the no-op instead (a vacuum without room selection hatches nothing).

## Driving hosted windows (2026-10-16)

The UX bar is 95%, which needs the code behind taps, sheets and rows to run, not only the first screen. Three tools in `apple/Tests/HassUITests` do that on the Mac host (a test runner only; macOS is not a supported platform, so there is no Mac UI, journey or checklist step):

- **Launch switches** (`withLaunch(environment:defaults:)` in `GalleryLaunchTests.swift`). Set the `FENTON_GALLERY_*` variables and launch arguments the journeys pass, host `ComponentGallery` in a real window and check what it drew (`HostedWindow.snapshot()`, `distinctColors`, `differs(from:)`). `GalleryLaunchMatrixTests` opens every sheet, tab, scenario and fixture each gallery offers and checks the sheet is up. A lazy `List` builds only the rows in view, so `scrollThrough()` wheel-scrolls the window or sheet to run the rows below the fold. Add a launch to the matrix when a gallery gains a switch.
- **`AXWindow`** (`AXDriver.swift`). Hosts a view and drives it through the accessibility tree: find by `accessibilityIdentifier` or label, `press`, `type(_:into:)`, read values and enabled state, and wait on them (`wait`, `waitFor`, `text(_:where:)`). It needs the test host to be a regular application and the process to be trusted for accessibility (`AXWindow.isAvailable`): flow suites carry `.enabled(if: AXWindow.isAvailable)`, so on a machine without that permission they skip and the coverage gate reads low rather than passing without them.
- **View-model tests** for logic that sits in a view (`LoginModel` was split out of `LoginView` for this): drive the model against a stubbed session (`LoginStubProtocol`) and host the view over it for each state.

Rules learned the hard way:

- **Presses are real mouse events, never `AXPress`.** An accessibility action in this process ends the test host (it exits through `swift_task_asyncMainDrainQueue`), and so does posting events to `NSApplication`. `AXWindow.press` scrolls the element into view, then sends mouse moved, down and up to the window straight after each other (an `await` between them lets another test's window take the key place and drops the click).
- **Reads run on the main actor.** In this process an accessibility query runs on the calling thread, and AppKit builds table cells there, so a background query trips its auto layout checks.
- **An inactive host swallows the first click.** The test host is not always the active application (another one has the front, the screen is locked), and AppKit takes the first click on an inactive window as the one that wakes it, unless the view accepts first mouse. `AXWindow` replaces `acceptsFirstMouse(for:)` on every view class under the window before it clicks, which made list rows, switches, bordered and destructive buttons, `onTapGesture` rows and drags all answer the same way whoever has the front. Without it a click works or not depending on which window the machine happens to have active. Menus (`Picker` pop-ups) are the exception: a click opens an `NSMenu` tracking loop that holds the main thread, so sweeps leave pop-ups, pickers, the photo and file panels, the share sheet and camera access alone (`ControlSweepTests.endsTheSweep`), and `SweepWatchdog` ends the host with the last press named if a sweep stops advancing for 240 s (a click or a read of the tree counts as advancing, so a loaded machine is not a hang).
- **Windows are told apart by position**, not title (SwiftUI renames a window after its navigation title): `AXWindow` gives each one its own origin, so another test's window with the same identifiers is not read.
- **Poll the state a press changes** (`press(_:until:)` retries at other points along the element), never a fixed sleep: a full run keeps the main actor busy for seconds at a time.

The hosted suites add about ten minutes to a full `swift test`; the gate's devcap hold is an hour.

## Running hosted UI tests and their pitfalls (2026-10-25)

Run them from `apple/` as background commands under a devcap build hold, one suite at a time:
`python3 ../tools/bg_run.py LABEL --timeout 1500 -- python3 ../tools/devcap.py run --pool build --purpose LABEL -- swift test --filter <Suite>`.
Several names go in one regex (`--filter 'a|b|c'`; repeated `--filter` flags are not accepted by the runner script wrapper). A flow suite's tests take 5 to 30 s each when the machine is free.

- **The screen must be unlocked.** On a locked screen (or with the screen saver up) the app still lists its windows, but every window attribute read fails with `kAXErrorAttributeUnsupported` (-25205), so `AXWindow.nodes()` is empty, every `waitFor` and `press` runs to its timeout, and the test fails 90 to 360 s later with "identifier not found". That is how 19 flow tests failed on a green main (sprinkler, security, settings, login, feedback, wake light, camera controls and more) while the same suites passed earlier in the run: the screen locked part way through. `AXWindow.screenLocked` (`CGSSessionScreenIsLocked`) now makes `AXWindow.isAvailable` false, ends every wait at once, and `AXWindow.init` cancels the running test, so a locked run reports the flow tests as skipped in seconds. A skip is not a pass: unlock the machine and keep it from locking during the run (a long run needs the display awake) and run again. Suites that cannot carry `.enabled(if: AXWindow.isAvailable)` because some tests need no accessibility start the AX test with `try AXWindow.require()`.
- **Toolbar items are not in the content view.** `HostedWindow.snapshot()` reads the window's content view; a gallery whose point is toolbar items (`ShellHeaderGallery`) draws only its body there (three colours), so its launch checks use `drawsMoreThan: 2`. Assert the header through a `NavigationStack` and `AXWindow`, not pixels.
- **Waits count passes, not seconds** (see the order-independent rules above); the lock guard is what bounds a wait that can never succeed.
- **App-hosted tests (FentonHomeTests) run on every family, so they must not depend on the device (2026-11-04).** A split window
  takes `HostedPage.splitSize` (wide enough to split, inside the scene's width): an 1100 pt window in the iPad's 834 pt portrait
  scene never finished laying out a recipe pane. The system text size is reset to the default before each family
  (`ios_uitest.sh`, `simctl ui content_size large`): a Duo simulator left at AX5 failed 36 hosted tests. A phone window is
  `HostedPage.phoneSize` (`show`'s default; 393 by 852 clamped to the scene, which is 466 by 678 on the folded Duo), and
  `HostedShellRig` is a phone on every family (compact width unless `regular:`; a window in the iPad's scene is regular otherwise).
  The folded Duo simulator has the system's vertical bar: a test of the phone answer pins `UKDeviceSignals.verticalBarOverride`
  and `regionsOverride` there, and a side-inset expectation reads `window.safeAreaInsets` instead of assuming none. Wait on the
  condition (`HostedPage.until`), not a fixed time, for an animated scroll; let a large title finish collapsing before the next tap.
- **Journey drags start clear of floating chrome (2026-11-04).** A drag that starts on the floating Add bar (interactive glass
