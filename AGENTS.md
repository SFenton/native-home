# Fenton HASS Native: agent entry point

Read this file first, then [.agents/README.md](.agents/README.md) for the page, pattern, platform and test rules. For the current plan, lanes and file ownership read [PROGRESS.md](PROGRESS.md).

## Invariants

- **Name.** The app is **S+H** to people (owner, 2026-10-17); bundle ids, app group, Keychain group and the `mobile_app` registration name stay as they are. See [app-name](.agents/platforms/apple/app-name.md).
- **macOS is not a target (owner, 2026-10-20).** Supported: iPhone, iPhone Duo, iPad, plus Watch, widgets and Live Activities. Do not write macOS-specific UI, add `#if os(macOS)` branches, build or test the app for Mac, add Mac destinations, schemes, CI jobs or journeys, or Mac steps in checklists or test plans. The one exception is tooling: `swift test` (and `tools/apple_coverage.sh`) runs the Core, Design and hosted UI tests on the Mac *host*, so `Package.swift` keeps `.macOS` purely as the test host, not a product platform. Existing `#if os(macOS)` code is legacy: never extend it. Owner, 2026-11-01: macOS is an *eventual* target, nothing now; design and layout choices must not foreclose it (geometric layout policies, no iPhone-only assumptions in shared components). See [testing](.agents/testing/apple/README.md).
- **Native only (owner, 2026-11-01).** The iOS and iPadOS app is **UIKit** (`HassUI/UIKitPort`, [uikit-port](.agents/platforms/apple/uikit-port.md)); there is no SwiftUI app ([decision](.agents/platforms/apple/decision-uikit-replaces-swiftui.md)). SwiftUI stays only where Apple requires it: widgets, Live Activities and watchOS. No WebView UI, except the in-app Home Assistant settings modal (the backend's own config pages), which is a full-screen modal so the app stays usable underneath.
- **Home Assistant is the source of truth.** The app signals intent through one service call path (`HassConnection.callService`) and may show optimistic state only for immediate feedback. It never duplicates automation logic. Agents may fix the server side themselves (config, restart Core, HACS) through `tools/ha_change.py`, with a backup, a passing check and a log (owner, 2026-11-03; [ha-operations](.agents/platforms/apple/ha-operations.md)).
- **One state path.** Every entity read goes through `EntityStore`; every connection goes through `HassConnection` (HAKit). Do not open a second websocket or poll REST for state.
- **The main thread does not scale with the house.** A live change to one entity costs it one box update; the diff of the thousands HAKit sends runs off it, on `HassConnection.deltaQueue`, and a scrolling page writes no state per frame. Measure with `tools/ios_scrollcost.sh` ([performance](.agents/testing/apple/performance.md)).
- **No reload on reopen.** Views bind to per-entity observable boxes in `EntityStore`, which updates them in place. A reconnect or a cold launch from the disk snapshot must never blank, re-fade or reorder a screen. See [connection-lifecycle](.agents/platforms/apple/connection-lifecycle.md).
- **Credentials.** Users sign in with username and password through Home Assistant's login flow ([auth](.agents/platforms/apple/auth.md)); only the refresh token is persisted, in the Keychain. Never store the password, commit a token or ship a long-lived one. `*.env` files are git-ignored. Live-server validation takes `FENTON_HASS_USERNAME` / `FENTON_HASS_PASSWORD` / `FENTON_HASS_TOKEN` in-process (`--env shell`, loaded in-process by `tools/hass_creds.sh`, never exported; see [devices](.agents/testing/apple/devices.md)), not from a repo file; host tests ignore them. `signing_guard` refuses agents the owner's `gh` login ([roster](.agents/workflow/agent-roster.md)). House data stays out of the repo behind a private denylist ([house-data-gate](.agents/workflow/house-data-gate.md)).
- **Shared capacity.** Every simulator, physical device and heavy compile runs inside a `tools/devcap.py` hold (machine-wide FIFO slots shared with FestivalNativeApps): `python3 tools/devcap.py run --sim <UDID> -- <command>`. `tools/ios_uitest.sh` and `tools/apple_coverage.sh` already do. Never boot a simulator outside a hold. Simulators you boot are slimmed with `tools/sim_slim.sh` (simslim; the test and perf scripts do it for you) so more fit in the slots. See [capacity](.agents/platforms/apple/capacity.md).
- **One session, one worktree (owner, 2026-10-30).** Every session works in its own linked worktree (`EnterWorktree`, an Agent with `isolation: "worktree"`, or the triage runner's), never in the shared primary checkout. The `worktree_guard` hook blocks edits, commits and branch changes there and tells you to call `EnterWorktree`; reading, `git fetch`, `gh pr view|create` and Agents with `isolation: "worktree"` stay allowed; `gh pr checkout` and `gh repo sync` count as branch changes. See [pr-lifecycle](.agents/workflow/pr-lifecycle.md#worktree-guard).
- **Token economy.** Never poll or sleep-loop: launch `tools/bg_run.py LABEL -- CMD` (`run_in_background`), end the turn, and read the notified digest, not the log. A session carries its task to the end; no context or turn hand-off. Fable 5.2 medium orchestrates and designs; Opus reviews; Sonnet (`coder`) implements and Haiku (`menial`) runs re-runs, logs and git chores. Full coverage and three-device runs are the nightly tier, not per-change ([test tiers](.agents/testing/apple/README.md#test-tiers)). See [token-economy](.agents/workflow/token-economy.md).
- **Propose, build, judge, record (owner, 2026-11-03).** A change the owner will see or feel is decided by the agents: build up to 3 options, capture screenshots and behaviour on the affected families, the Designer judges and records the pick, the chosen option lands; the owner may reverse it later. The owner is needed only for broad, app-wide changes they did not explicitly request: the app-UI gate (`tools/jev_gate.py`) parks owner-requested work Jev cannot confirm matches the request, and agent-initiated work that is app-wide or unsure. Parks: [agent-roster](.agents/workflow/agent-roster.md#questions). See [propose-first](.agents/workflow/propose-first.md).
- **Mockup atlas (owner, 2026-10-23).** Every page, modal, component and flow has a mockup of how it looks and moves today on iPhone, Duo and iPad, in [.agents/design/mockups](.agents/design/mockups/README.md) (`catalog.json`). Look the surface up there before you change or propose anything, reuse its kit, and update its mockup in the same PR. Mockups map the app; code and owner decisions win. **The owner browses them in one hub Artifact in the Claude app.** Any change under that folder ends with `python3 tools/mockups_hub.py`, a publish to the hub link in the mockups README and `--mark-published`, always, unasked ([skills/mockup-hub](.agents/skills/mockup-hub/SKILL.md); the Stop hook `tools/hooks/mockup_hub_guard.py` blocks ending the session otherwise). Never publish a mockup as its own Artifact. Current designs only: a shipped change removes its "was" and clears `inFlight`. Hub rules: mockup-hub skill.
- **Versioning (owner, 2026-10-26).** `YYMM.DD.NN` per FestivalNativeApps: annotated tags `ios/v<version>` on `main`, cut by `tools/release/versioning.py bump`, never a commit. Release builds are stamped with `versioning.py build-settings`; local builds stay `0.1.0 (1)`. A change users will notice carries a `Release-Note:` trailer (`tools/ship.sh --note`), or `Release-Note: none`. See [versioning](.agents/workflow/versioning.md).
- **Land through the gate (owner, 2026-10-28).** Sessions end with `ship.sh`, the reviewer and a merge, one line: merged, armed, blocked, failed. Native-home is push, then review (owner, 2026-11-10): `ship.sh` pushes and opens the PR, the reviewer reads the head during CI, `changes` means fix and push; on `pass` the reviewer posts `ai-review` and `tools/pr_land.sh N` arms it. The pre-push hook runs the denylist. Hooks block other merges. See [pr-lifecycle](.agents/workflow/pr-lifecycle.md), [ci](.agents/workflow/ci.md#the-merge-gate).
- **End-to-end autonomy (owner, 2026-11-07).** Agents may change the merge path and guards; independent review gates. Owner keeps credentials, signing. Agent files land after an independent review and the owner's CODEOWNERS approval; everything else lands on the review alone (owner, 2026-11-09).
- **System API first.** Custom scroll, blur, mask, material, list, header, sheet, paging or layout machinery needs a rung-0 note: the system API on iOS 17, 18 and 26, a precedent, and why it is not enough ([change-loop](.agents/workflow/change-loop.md#rung-0-system-api-first)). Audit of what exists: [system-api-audit](.agents/design/apple/system-api-audit.md).
- **Pattern first.** A behavior that appears on more than one screen (grids, tiles, status chips, modal sheets, section headers) has one record in [.agents/patterns](.agents/patterns/README.md) and one canonical component. Extend it and sweep its consumers; never add a parallel implementation.
- **Apple design guidance.** Every UI decision goes through the Apple HIG (and the `apple-hig` skill where installed, including `/duo` for iPhone Duo). Cite the HIG section in the page or control note. HIG wins over web parity where they conflict; record the departure.
- **Web parity source.** The React dashboard `SFenton/ha-sfenton-react-dash` defines behavior and entity IDs. Read it; never edit it to make a native test pass. Cite files as `ha-sfenton-react-dash@<sha>:path:line`.
- **Shared code.** iPhone, iPad, Duo and Watch share `HassCore` and `HassDesign`; the phone and tablet share `HassUI` (its UIKit screens under `UIKitPort`, plus the models, routes and policies they use). Form-factor differences live in layout policies, not forked screens.
- **Devices (owner, 2026-10-10).** Every automation and accessibility test is written for iPhone, iPhone Duo and iPad; a change runs its affected journeys on iPhone and the Smoke plan on the other two; a layout-sensitive change (its layout journeys only), the nightly and a release run all three (owner, 2026-10-29; [test tiers](.agents/testing/apple/README.md#test-tiers)). iPhone is locked to portrait; Duo and iPad rotate freely. Folded Duo, unfolded Duo portrait and iPad portrait are always single-page and never split; unfolded Duo landscape and iPad landscape may split. The rule is geometric (`SplitPolicy`), never a device name. See [split-view](.agents/design/apple/split-view.md).
- **Tests ship with the change (FestivalNativeApps rules).** Unit tests for new logic; with every UI change, a UX test and an **accessibility test** on each device family it affects (name/role/state, reading order, 44 pt targets, AX5 text scaling). A missing one is a major finding. Certification needs **≥95% logic and ≥95% UX line coverage (owner decision 2026-10-16, raised from 90)** (`tools/apple_coverage.sh`) plus the full device journeys (`tools/ios_uitest.sh`), both certified by the nightly and release run; a PR checks the changed files' coverage (`tools/apple_coverage.sh --changed`) and runs only its affected tests, and `tools/hooks/tier_guard.py` refuses unfiltered runs (owner, 2026-10-29). See [testing](.agents/testing/apple/README.md).
- **SwiftUI Pro skill.** Scope: the SwiftUI that remains (HassDesign's views, `FentonActivityViews`, the widget extension and the Watch app). Load [`.claude/skills/swiftui-pro`](.claude/skills/swiftui-pro/SKILL.md) (twostraws/swiftui-agent-skill v2.0.0, MIT) while writing it and run it as a review (`/swiftui-pro`, or a focus such as `/swiftui-pro accessibility`) on your diff before a PR. App screens are UIKit and follow [uikit-port](.agents/platforms/apple/uikit-port.md) instead. The deployment target is iOS 17: iOS 26/27-only rules apply only behind `#available` or when the target moves. Where it conflicts with these invariants or a pattern record, the repo rule wins (record the departure in the pattern doc). How we apply it: [workflow/swiftui-pro.md](.agents/workflow/swiftui-pro.md).
- Document Swift with DocC `///` and `// MARK: -` regions. Test behavior changes, not only compilation.

## Change loop

1. Read the web source for the page or control and its spec (`.agents/pages/<id>/spec.md` + your platform file). Identify entities, states, services and navigation edges.
2. **Visible choice? Build up to 3 options, the Designer judges and records the pick** ([propose-first](.agents/workflow/propose-first.md)); nothing waits on the owner.
3. Implement in your lane's folders. Add unit tests for non-UI logic as you go, and a UI or accessibility test with each UI change.
4. Build, then run the per-change tier: `python3 tools/affected_tests.py`, the affected `swift test --filter`, `tools/ios_uitest.sh --changed` on the affected families, and a simulator look when something is visible; the full suite is nightly ([build-and-run](.agents/platforms/apple/build-and-run.md)).
5. Record durable findings as rules in the right `.agents` file, pattern doc first. Commit small cohesive commits and update PROGRESS.md.
